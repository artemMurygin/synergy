## Context

Мотивация описана в proposal.md (раздел Why), требования — в `specs/`. Ниже только то, что влияет на реализацию.

- Модуль `backend/src/modules/portal` из Э0. `Skill` — агрегат с методом `advance`, правило переходов собрано в `SkillStatus.canAdvanceTo` (только соседний вперёд). `Agent` и `Product` — простые интерфейсы без поведения, их создаёт только сидер (`CatalogRepository.seed`, `ON CONFLICT DO NOTHING`).
- Конкурентность смены статуса сейчас обеспечена так: `SkillRepository.findForUpdate`, затем `save(skill, expectedStatus)` с условием `WHERE status = expectedStatus`. Событие `SkillStatusChangedEvent` пишется в outbox в той же транзакции. На нём построено правило `request.status-changed` (in-app и Telegram).
- Статус заявки для автора выводит `RequestStatusPolicy`, подписи берутся из `contracts/skill-status-labels.ts`. Правила уведомлений тоже используют этот словарь.
- Схема БД (`db/migrations/028_portal_catalog.sql`): `portal_agents.product_id NOT NULL` (у агента ровно один продукт), `portal_skills.status` с встроенным `CHECK (status IN (...))`. Признака архива нет ни у навыков, ни у агентов.
- Продукт агента читают `SlonikCatalogRepository.listAgents`, `SlonikSkillQuery`, ответы `AgentResponse`/`SkillResponse`, сидер (`PORTAL_CATALOG` — список продуктов с вложенными агентами), а на портале — `SkillPicker`, `SkillsTable`, фильтр продукта в `SkillsPage`. Модуль `notifications` продукт не использует.
- Портал: фича `features/skills` (таблица навыков, `SkillStatusAction`, `SkillPicker`). Следующий статус вычисляет `nextSkillStatus` в `lib/status-labels.ts`, то есть правило переходов продублировано на фронте. `useSkillStatus` сравнивает статусы по порядку в цепочке (`order(changed) >= order(skill.status)`). С `rework` статус перестаёт расти монотонно, и это сравнение ломается.

## Goals / Non-Goals

**Goals:**
- Правило переходов статуса навыка задаётся в одном месте, на бэкенде. Портал его не дублирует.
- Статус агента и статус заявки для автора выводятся при чтении и нигде не хранятся.
- Архив работает как признак (`archived_at`). Агент и навык архивируются независимо, видимость навыка определяется обоими признаками.
- Каталог и роадмап читаются одним запросом.

**Non-Goals:**
- Ручное создание и редактирование продуктов и агентов. Это Э3, через решение по заявке.
- Пагинация и поиск по каталогу на сервере: каталог небольшой (единицы продуктов, десятки агентов и навыков).
- История статусов и аудит архивации.
- Уведомления об архивации и восстановлении.

## Decisions

### 0. Агент в нескольких продуктах — таблица связей

Таблица `portal_agent_products (agent_id, product_id, PRIMARY KEY (agent_id, product_id))` с индексом по `product_id`. Колонка `portal_agents.product_id` удаляется после переноса данных. Навыки, `archived_at` и выведенный статус остаются у агента, поэтому они общие для всех его продуктов.

- *Инвариант «минимум один продукт»* в БД не проверяется: для этого нужен отложенный триггер. Он держится на том, что связи создаёт только сидер (агент создаётся сразу со своими продуктами), а удалить связь в Э2 нельзя. В домене `Agent.productIds` — непустой список, `Agent.create` без продуктов бросает ошибку. В Э3 это же правило проверит создание агента при решении по заявке.
- *Сидер.* Формат `PORTAL_CATALOG` не меняется: агент с одним `slug` у двух продуктов — это один агент и две связи. Агенты вставляются с `ON CONFLICT (slug) DO NOTHING`, связи — с `ON CONFLICT DO NOTHING`, так что новые связи из начального набора добавляются, а существующие не удаляются.
- *Контракт API.* Поле `product: {id, name}` у агента и навыка заменяется на `products: {id, slug, name}[]`, отсортированные по `slug`. Портал обновляется в том же change, внешних потребителей у этих эндпоинтов нет.
- *Альтернатива:* «основной продукт» плюс дополнительные. Отвергнута: такой сущности нет в предметной области, и вопрос «какой продукт основной» ничего не даёт пользователю.


### 1. Переходы статуса — таблица в домене, разрешённые шаги отдаются в API

В `domain/skill-status.ts` вместо `next`/`canAdvanceTo` появляется таблица `SKILL_TRANSITIONS: Record<SkillStatus, readonly SkillStatus[]>` и функции `SkillStatus.allowedNext(from)` и `SkillStatus.canMove(from, to)`. Метод `Skill.advance` переименовывается в `Skill.changeStatus(to, now)`. Он проверяет архив, проверяет переход и при первом `launched` записывает `launchedAt`.

Навык в ответах API (`SkillResponse`, навыки в каталоге) получает поле `nextStatuses`: какие переходы разрешены из текущего статуса. Портал строит действия смены статуса по этому полю и перестаёт вычислять их сам. `nextSkillStatus` и `SKILL_STATUS_FLOW` из `lib/status-labels.ts` удаляются.

- *Почему не дублировать таблицу на фронте:* после добавления `rework` правило уже нелинейное. Две копии разойдутся при следующем изменении.
- *Альтернатива:* отдельный эндпоинт с графом переходов. Он лишний: переходы нужны только рядом с конкретным навыком.

### 2. `launchedAt` вместо истории

Колонка `portal_skills.launched_at TIMESTAMPTZ NULL`. Её заполняет `Skill.changeStatus` при первом переходе в `launched` и больше никогда не меняет. Инвариант в БД: `CHECK (status <> 'launched' OR launched_at IS NOT NULL)`. Статус агента выводит доменная функция `AgentStatusPolicy.statusOf(skills)`: `working`, если среди переданных неархивных навыков есть навык с `launchedAt`, иначе `in_development`. Подписи «Работает» и «В разработке» лежат в `contracts/agent-status-labels.ts`.

- *Альтернатива:* считать статус в SQL (`bool_or(launched_at IS NOT NULL)`). Это быстрее, но правило тогда живёт в SQL и в тестах домена не проверяется. Каталог маленький, поэтому применяем политику в application-слое к уже загруженным навыкам.

### 3. Архив — `archived_at` у агента и навыка, видимость считается по двум признакам

Колонки `portal_agents.archived_at` и `portal_skills.archived_at` (`TIMESTAMPTZ NULL`). Навык виден, если `s.archived_at IS NULL AND a.archived_at IS NULL`. При архивации агента навыки не трогаются. Поэтому восстановление агента само собой не возвращает навыки, архивированные отдельно.

`Agent` становится агрегатом (`AggregateRoot`) с методами `archive(now)` и `restore()`. Методы идемпотентны: повторный вызов ничего не меняет, use-case не сохраняет агрегат и возвращает 200. У `Skill` такие же методы. Восстановление навыка при архивном агенте запрещено: use-case проверяет агента и бросает `AgentArchivedError`.

Новые ошибки домена: `SkillArchivedError` (`PORTAL_SKILL_ARCHIVED`) и `AgentArchivedError` (`PORTAL_AGENT_ARCHIVED`). Обе регистрируются в `portal-error-status.ts` как 409. Портал выбирает текст сообщения по коду.

- *Альтернатива:* каскадно ставить `archived_at` навыкам при архивации агента. Отвергнута: после этого нельзя отличить навыки, архивированные отдельно, а спека требует их не возвращать.
- *Альтернатива:* статус `archived` у навыка. Отвергнута: архивный навык потерял бы текущий статус, а автор заявки должен продолжать его видеть.

### 4. Проверка архива и блокировки

Действия, которым нужен неархивный агент (смена статуса навыка, принятие заявки в навык, создание навыка, восстановление навыка), читают агента через `CatalogRepository.findAgentForShare` (`SELECT … FOR SHARE`). Архивация и восстановление агента читают его через `findAgentForUpdate` (`FOR UPDATE`). Навык по-прежнему блокируется через `SkillRepository.findForUpdate`. Так параллельные «архивировать агента» и «сменить статус его навыка» выполняются по очереди, и ни одно действие не проходит по устаревшему признаку.

Порядок блокировок везде один, чтобы не получить взаимную блокировку: сначала навык (`FOR UPDATE`), потом его агент.

### 5. Чтение каталога: один запрос, дерево собирается в application

- `GET /portal/catalog` (любой вошедший). `CatalogQuery.loadVisible()` одним запросом с `LEFT JOIN` возвращает продукты, связи агентов с продуктами, неархивных агентов и видимые навыки. `GetCatalogUseCase` собирает дерево `продукт → агенты (со статусом от AgentStatusPolicy) → навыки (с nextStatuses)`; агент из нескольких продуктов попадает в каждую ветку, а статус и навыки для него вычисляются один раз. Сортировка: продукты и агенты по `slug`, навыки по названию.
- Роадмап и карточку агента портал строит из того же ответа (группировка по статусу, выбор агента по `id`). Отдельных эндпоинтов нет. Чтобы навык агента из двух продуктов не появился в роадмапе дважды, `groupByStatus` убирает повторы по `id` навыка, а продукты для карточки и фильтра берёт из `agent.products`; у агента в ответе каталога есть полный список продуктов.
- `GET /portal/archive` (`developer`). `CatalogQuery.loadArchive()` возвращает архивных агентов (с продуктами и числом навыков без собственного архива, которые вернутся вместе с агентом) и навыки с `archived_at IS NOT NULL`. Навыки архивного агента, не архивированные отдельно, в ответ не входят.
- `GET /portal/skills` и `GET /portal/agents` дополняются условием видимости. Контракт ответа сохраняется, к навыку добавляется только `nextStatuses`.

### 6. Эндпоинты архивации

`POST /portal/skills/:id/archive`, `POST /portal/skills/:id/restore`, `POST /portal/agents/:id/archive`, `POST /portal/agents/:id/restore`. Все с `@Roles('developer')` и без тела. Отвечают 200 с актуальным представлением навыка или агента. Используется `POST`, а не `PATCH { archived }`, по образцу `POST skills/:id/status`: действие явное, без частичной правки ресурса.

### 7. Подпись `rework` и уведомления

В `SKILL_STATUS_LABELS` добавляется `rework: 'Доработка'`. Тип `Record<SkillStatus, string>` не даст забыть подпись. Правило `request.status-changed` срабатывает на любое событие смены статуса, поэтому переходы в `rework` и из него уведомляют авторов без правок модуля `notifications`. `RequestStatusCode` расширяется автоматически, потому что включает `SkillStatus`.

### 8. Портал: новые фичи `catalog` и `archive`, ключи кэша в `lib`

- `features/catalog`: запрос каталога, разбор ответа (Zod) и UI каталога, карточки агента и роадмапа, а также мутация «архивировать агента». Работает для всех ролей, действие разработчика показывается по роли из профиля.
- `features/archive`: запрос архива и мутации восстановления. Только для разработчика.
- `features/skills`: действия берутся из `nextStatuses` (решение 1). Добавляется «Архивировать навык». `useSkillStatus` выбирает актуальный статус по `statusChangedAt`, а не по порядку в цепочке.
- Фичи не импортируют друг друга. Архивация и восстановление инвалидируют кэш нескольких фич, поэтому ключи (`catalog`, `skills`, `agents`, `archive`) выносятся в `lib/query-keys.ts`. Цвета бейджа статуса навыка (включая `rework`) и бейджа статуса агента переезжают в `lib/status-labels.ts`, чтобы ими пользовались и `skills`, и `catalog`.
- Маршруты: `/catalog`, `/catalog/agents/:id`, `/roadmap` — внутри `RequireAuth`; `/archive` — внутри `RequireRole role="developer"`.

## Risks / Trade-offs

- [Каталог отдаётся целиком, без пагинации] → при текущем масштабе ответ — десятки килобайт. Если каталог вырастет, добавится фильтр по продукту на сервере, контракт дерева при этом не изменится.
- [Статус агента считается в коде, а не в SQL] → для этого грузятся навыки всех видимых агентов. Это укладывается в тот же единственный запрос каталога.
- [Портал может держать в кэше устаревшие `nextStatuses`] → сервер всё равно проверяет переход и отвечает 409, а портал на 409 перезапрашивает навык (поведение из Э0 сохраняется).
- [Архивация агента скрывает навыки с привязанными заявками] → заявки продолжают показывать автору последний статус (спека `featurer-requests`). Привязку к навыку архивация не трогает.
- [Удаление `portal_agents.product_id` ломает старый бэкенд при откате выкатки] → миграция и бэкенд выкатываются вместе; откат приложения требует отката миграции (описан ниже).
- [Встроенный `CHECK` на статус имеет имя, которое сгенерировал Postgres] → миграция удаляет ограничение по фактическому имени `portal_skills_status_check`. Тест миграции на чистой базе проверяет, что имя совпадает.

## Migration Plan

Миграция `034_portal_catalog_archive.sql`:
0. `CREATE TABLE portal_agent_products (...)`, `INSERT INTO portal_agent_products SELECT id, product_id FROM portal_agents`, `DROP INDEX portal_agents_product_idx`, `ALTER TABLE portal_agents DROP COLUMN product_id`.
1. `ALTER TABLE portal_skills DROP CONSTRAINT portal_skills_status_check`, затем `ADD CONSTRAINT portal_skills_status_check CHECK (status IN ('planned','in_dev','testing','launched','rework'))`.
2. `ALTER TABLE portal_skills ADD COLUMN launched_at TIMESTAMPTZ, ADD COLUMN archived_at TIMESTAMPTZ`.
3. Заполнить существующие запущенные навыки: `UPDATE portal_skills SET launched_at = status_changed_at WHERE status = 'launched'`.
4. `ADD CONSTRAINT portal_skills_launched_has_time CHECK (status <> 'launched' OR launched_at IS NOT NULL)`.
5. `ALTER TABLE portal_agents ADD COLUMN archived_at TIMESTAMPTZ`.

Выкатка: сначала миграция, потом бэкенд, потом портал. Старый портал с новым бэкендом работает: новые поля он игнорирует. Навык в `rework` старый портал не распознает, но до выкатки нового портала такой навык не может появиться.

Откат (комментарий в миграции): вернуть `portal_agents.product_id`, заполнив его любым одним продуктом агента (`min(product_id)`), удалить `portal_agent_products`; `UPDATE portal_skills SET status = 'testing' WHERE status = 'rework'`, удалить новые ограничения и колонки, вернуть прежний `CHECK`. Флаг архива при откате теряется, и архивные записи снова становятся видны.
