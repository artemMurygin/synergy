## Context

Мотивация и скоуп — в `proposal.md`, требования — в `specs/`. Здесь только то, как это встраивается в существующий код.

Что уже есть и ограничивает решение (после Э0):

- **Модуль `auth`** (`backend/src/modules/auth`) по слоям `domain / application / infrastructure / interface`. Агрегат `User` хранит логин, хэш пароля, `mustChangePassword`, `isActive`; `UserRepository.save` делает полный upsert всей строки `auth_users`, включая `password_hash`. Роли — таблица `auth_user_roles` (`CHECK role IN ('developer')`), доменный `Role` — закрытое множество `['developer']`, `UserRepository.assignRoles` идемпотентно добавляет, снимать роль нечем.
- **Токен и права.** Роли записываются в access-токен при входе и обновлении, `RolesGuard` берёт их из claims, `@Roles('developer')` вешается на эндпоинты. Вход и обновление сессии проверяют `user.canSignIn()` (`isActive`), поэтому отключённый пользователь не может ни войти, ни обновить токены. `AuthSessionRepository.revokeAllForUser` уже есть.
- **Сидер.** `SeedUsersUseCase` читает список из `AUTH_SEED_USERS` (JSON в переменной окружения, разбирается в `env.schema.ts` и в `seed-users.cli.ts`), создаёт пользователя с временным паролем и **добавляет роли и существующим** пользователям. Запускается как `npm run seed:users` через отдельный `AuthSeedModule`.
- **Профиль** `GET /auth/me` (`GetCurrentUserUseCase`) возвращает `id`, `login`, `mustChangePassword`, `roles`. Список `GET /users` возвращает активных пользователей только с `id` и `login` для выбора ответственного в задачах.
- **Модуль `portal`** (Э0) читает автора заявки соединением с `auth_users` и отдаёт `authorId` и `authorLogin`.
- **Портал `portal/`**: SPA на React 19, TanStack Query, zustand, `react-router`. Каркас — `features/{auth,requests,decision,skills,shell}`, страницы в `pages/`, роль скрывает раздел через `RequireRole`, меню — `features/shell/NavMenu.tsx`. Тип `Role` и схема профиля — в `lib/schemas`.
- **Клиенты** `control-center` и `manager-helper` разбирают ответ профиля обычными zod-схемами без `.strict()`, лишние поля они отбрасывают.

## Goals / Non-Goals

**Goals:**
- Данные о людях и их доступах живут в одном месте (`auth`) и изменяются только через целевые операции, а не полным перезаписыванием пользователя.
- Один путь создания сотрудника для начальной загрузки и админки, чтобы правила (логин, пароль, профиль, роли) не расходились.
- Инвариант «всегда есть активный администратор» выдерживается и при одновременных запросах двух администраторов.

**Non-Goals:**
- Выделение оргструктуры в отдельный модуль (решение: всё остаётся в `auth`).
- Журнал изменений административных операций, сброс пароля администратором, импорт и синхронизация с внешними системами.
- Мгновенный отзыв ролей и права, зависящие от отдела или руководителя.

## Decisions

### 1. Профиль в отдельной таблице `auth_user_profiles`, а не колонками `auth_users`
`auth_user_profiles (user_id PK → auth_users ON DELETE CASCADE, last_name, first_name, middle_name, department_id → auth_departments, position, email, scrm_employee_id)`. Строки профиля нет у пользователей, заведённых до Э1: отсутствие строки равно пустому профилю (спека `employee-directory`, «Пользователь, заведённый до появления профиля»).

Главная причина — потерянное обновление. `UserRepository.save` перезаписывает всю строку `auth_users`, включая `password_hash`. Если профиль лежит в той же строке, правка ФИО администратором, прочитавшим пользователя до того, как тот сменил пароль, откатит пароль к старому хэшу. Отдельная таблица делает правку профиля независимой от пароля, а правку пароля — независимой от профиля.

Вторая причина — таблица `auth_users` участвует в каждом входе и обновлении токена и не должна пухнуть от справочных полей.

*Альтернатива:* колонки в `auth_users` — проще на один JOIN, но требует переписать `save` на точечные обновления; всё равно пришлось бы вводить отдельные методы. Отвергнуто.

Индексы и ограничения: `UNIQUE (lower(email)) WHERE email IS NOT NULL`, при этом пустая строка в email приводится к `NULL` на входе; `CHECK` на непустые `last_name` и `first_name` не вводится, потому что при создании их обязательность проверяет доменная проверка, а у старых пользователей строки профиля нет вообще. Индекс по `department_id` для фильтра и подсчёта сотрудников отдела.

### 2. Отделы: `auth_departments`, идентификатор — текст
`auth_departments (id TEXT PK, name TEXT NOT NULL, head_user_id UUID NULL → auth_users ON DELETE SET NULL)`, `UNIQUE (lower(name))`. Внешний ключ профилей на отдел — `ON DELETE RESTRICT`.

Идентификатор — `TEXT`, а не `UUID`, потому что файл начальной загрузки содержит собственные идентификаторы отделов (`"id": "d1"`), и именно по ним загрузка определяет «уже существует». Отделы, созданные в админке, получают `randomUUID()`, записанный как текст. Смешанные форматы допустимы: идентификатор непрозрачен для клиентов.

*Альтернатива:* `UUID` PK плюс отдельная колонка `external_key` для загрузки. Отвергнуто: лишняя колонка, живущая только ради одноразовой загрузки.

Удаление пустого отдела — в транзакции: проверка «нет сотрудников» плюс удаление; внешний ключ `RESTRICT` — страховка, при его срабатывании ошибка отображается как 409 того же вида.

### 3. Роли: расширение `CHECK`, замена набора, точечные операции
Миграция заменяет `CHECK` на `role IN ('developer', 'admin')`: `ALTER TABLE ... DROP CONSTRAINT IF EXISTS auth_user_roles_role_check; ADD CONSTRAINT ... CHECK (...)`. Доменный `Role` расширяется значением `admin`.

В `UserRepository` добавляются точечные методы вместо расширения `save`:
- `replaceRoles(userId, roles)` — `DELETE` и `INSERT` в одной транзакции, заменяет набор целиком (спека `user-administration`, «Управление ролями»);
- `setActive(userId, active)` — `UPDATE auth_users SET is_active = ...`, не трогая остальные колонки.

`assignRoles` остаётся для создания нового пользователя. Сидер больше не вызывает его для существующих.

Токен не меняется: claim `rol` уже есть, `RolesGuard` проверяет `admin` так же, как `developer`. Задержка отзыва до `AUTH_ACCESS_TTL` принята осознанно для обеих ролей (в том числе `admin`), немедленной проверки по БД нет.

### 4. Инвариант «есть активный администратор» — блокировка внутри транзакции
Две одновременные операции двух администраторов («A снимает роль у B» и «B снимает роль у A») при проверке «остаётся ли другой активный администратор» обе увидят другого и обе пройдут, оставив систему без администратора. Поэтому операции, уменьшающие число активных администраторов (`replaceRoles` без `admin`, `setActive(false)`), выполняются в одной транзакции, которая сначала берёт `pg_advisory_xact_lock` на фиксированный ключ, затем считает активных администраторов после изменения и откатывает транзакцию с `LAST_ADMIN`, если их не осталось.

Блокировка глобальная, но операции редкие (административные), а удерживается она до конца короткой транзакции.

*Альтернативы:* `SELECT … FOR UPDATE` по строкам администраторов — не защищает от вставки нового администратора и сложнее; уровень `SERIALIZABLE` — требует повторов на уровне приложения. Advisory-блокировка — самое простое и однозначное.

### 5. Увольнение: `setActive(false)` плюс отзыв сессий в одной транзакции
`DismissEmployeeUseCase`: блокировка из п. 4, проверка `LAST_ADMIN`, `setActive(false)`, `AuthSessionRepository.revokeAllForUser(userId)` — всё в одной транзакции, чтобы не получить «уволен, но сессии живы». Вход и обновление уже проверяют `canSignIn()`, так что дополнительных проверок не нужно; access-токен действует до истечения (спека). Возврат — `setActive(true)`; операции идемпотентны, повторная — успех без изменений.

### 6. Единый путь создания сотрудника
Один `ProvisionEmployee` (доменно-прикладной сервис) создаёт пользователя с временным паролем, строку профиля и роли; им пользуются `CreateEmployeeUseCase` (админка) и загрузка из файла. Пароль генерируется существующим `PasswordGenerator` и хэшируется `PasswordHasher`; `mustChangePassword = true` ставит существующая фабрика `User.createWithTemporaryPassword`. Правила логина — прежний `Login.of`, фамилия и имя обязательны.

Хэширование (argon2) дорогое, поэтому при загрузке сотен записей оно выполняется **до** открытия транзакции, а внутри транзакции остаются только записи в БД. Это не даёт долго держать соединение и блокировки.

### 7. Начальная загрузка: файл, предварительная проверка, одна транзакция
Формат файла — объект `{ "departments": [...], "users": [...] }`. Поля отдела: `id`, `name`, `head` (логин). Поля сотрудника: `login`, `lastName`, `firstName`, `middleName?`, `departmentId?`, `position?`, `email?`, `scrmEmployeeId?`, `password?`, `roles?`. Прежний формат (массив `{login, password?, roles?}` из `AUTH_SEED_USERS`) остаётся допустимым и разбирается как «только сотрудники без профиля и отделов».

Порядок:
1. **Разбор и проверка всего файла** до любой записи (zod): допустимые роли, существование отделов и руководителей (в файле или уже в БД), дубли логинов и email внутри файла, конфликт email с существующим сотрудником. Любая ошибка — выход с сообщением и без записи (спека `employee-directory`).
2. **Подготовка**: хэши паролей для новых сотрудников (п. 6).
3. **Одна транзакция** в таком порядке: отделы без руководителей → сотрудники с профилями и ролями → назначение руководителей. Такой порядок снимает циклическую зависимость «отдел ссылается на руководителя, сотрудник на отдел».
4. **Режим «только новые»**: отдел определяется по `id`, сотрудник по `login`; существующие пропускаются целиком, включая роли. Руководитель назначается только отделу, созданному в этом запуске.

Источник данных: путь к файлу — переменная `AUTH_SEED_FILE` или аргумент `--file`; если заданы и файл, и `AUTH_SEED_USERS`, команда завершается ошибкой, чтобы не гадать, что главное. Реальный файл исключается через `.gitignore`, в репозитории лежит `users.example.json`. Команда `npm run seed:users` и `AuthSeedModule` остаются, меняется только их содержимое.

*Альтернатива:* обновлять существующих («файл главнее») — отвергнуто решением владельца продукта: после первой загрузки все данные ведёт админка, повторный запуск не должен затирать её правки.

### 8. Полное имя — одна функция в `shared`
Правило «фамилия, имя, отчество через пробел без пустых частей, иначе логин» нужно и в `auth` (профиль, список сотрудников), и в `portal` (автор в очереди). Чтобы не дублировать правило в SQL и коде, оно выносится в чистую функцию `formatFullName({lastName, firstName, middleName}, login)` в `backend/src/shared/people/` и используется обоими модулями. `portal` по-прежнему не импортирует внутренности `auth`; он получает через JOIN три части ФИО и логин и сам вызывает общую функцию.

*Альтернативы:* собирать имя в SQL (`concat_ws`) — правило в двух местах; хранить колонку `full_name` — нарушает спеку и может расходиться с частями.

### 9. HTTP API администратора
Контроллеры в модуле `auth`, префикс `/admin`, на классе `@Roles('admin')`; общий `JwtAuthGuard` и `PasswordChangeGuard` уже применяются глобально. Существующий `GET /users` (выбор ответственного в задачах) не меняется.

| Метод и путь | Назначение |
|---|---|
| `GET /admin/employees` | список с поиском, фильтрами по отделу и увольнению, пагинацией |
| `GET /admin/employees/:id` | карточка |
| `POST /admin/employees` | создание, ответ содержит временный пароль один раз |
| `PATCH /admin/employees/:id` | правка профиля, логин не меняется |
| `PUT /admin/employees/:id/roles` | замена набора ролей |
| `POST /admin/employees/:id/dismiss` | уволить |
| `POST /admin/employees/:id/restore` | вернуть |
| `GET`, `POST /admin/departments` | список, создание |
| `PATCH`, `DELETE /admin/departments/:id` | переименование и смена руководителя, удаление пустого |

Ошибки домена отображаются в `auth-error-status.ts` в статусы и коды: `LAST_ADMIN` (409), `EMAIL_TAKEN` (409), `LOGIN_TAKEN` (409), `DEPARTMENT_NAME_TAKEN` (409), `DEPARTMENT_NOT_EMPTY` (409), `EMPLOYEE_NOT_FOUND` и `DEPARTMENT_NOT_FOUND` (404). Тело создания и правки валидируется схемами zod рядом с контроллером (`admin.schemas.ts`), как в остальном модуле. Правка использует семантику «не переданное остаётся, пустое очищает» (спека).

Поиск по ФИО, логину и email — `ILIKE` с экранированием, по образцу существующего `UserSearch.likePattern`; сортировка `lower(last_name), lower(first_name), lower(login)`.

### 10. Профиль и автор в очереди читают профиль соединением
`GetCurrentUserUseCase` дополнительно читает профиль и отдел и возвращает названные поля; роли по-прежнему из токена. Данные профиля читаются из БД при каждом запросе, поэтому правка администратора видна без повторного входа (спека `user-auth`).

В `portal` запрос заявок для очереди и карточки добавляет `LEFT JOIN auth_user_profiles`, а `RequestView` получает `authorFullName`; `authorLogin` остаётся для обратной совместимости с «Моими заявками». Для автора без профиля (старый пользователь) функция из п. 8 возвращает логин.

### 11. Фронтенд портала
- **Роли и профиль.** `Role` в `lib/schemas` расширяется значением `admin`, схема профиля получает `fullName`, части ФИО, `position`, `department`. `NavMenu` добавляет группу `ADMIN` («Сотрудники», «Отделы») для `admin`, не вытесняя группу разработчика: роли независимы.
- **Маршруты** под `RequireRole role="admin"`: `/admin/employees`, `/admin/employees/new`, `/admin/employees/:id`, `/admin/departments`. Для пользователя без роли `RequireRole` уже ведёт на «Мои заявки» и не монтирует раздел.
- **Новые features:** `features/employees` (список, форма, карточка, роли, увольнение) и `features/departments` (список, форма, выбор руководителя). Структура `model/` (api, queries) и `ui/` по образцу `features/skills`.
- **Временный пароль** живёт только в локальном состоянии компонента и в результате мутации; он не попадает в кэш запросов, не пишется в хранилище и не сохраняется в адресе, а после закрытия окна уничтожается (спека `featurer-admin-ui`). Мутация создания вызывается с `gcTime: 0`.
- **Шапка** (`layouts/AppLayout`) показывает полное имя из профиля вместо логина.

*Альтернатива:* общая библиотека UI между `portal/` и `control-center` — отвергнуто ещё в Э0 (второго потребителя нет).

### 12. Ограничения длины
Фамилия, имя, отчество, должность и название отдела — до 200 символов; идентификатор в SCRM — до 64; email — до 254; логин — прежние 64; строка поиска — до 100. Проверка в VO и в zod-схемах (400), значения дублируются в `maxLength` полей портала. В БД — `CHECK (char_length(...) <= N)`, чтобы ограничение не обходилось прямой записью.

### 13. Конфигурация и развёртывание
Портал и API на одном домене, поэтому `SameSite=Strict` остаётся; Э1 добавляет только origin портала в `AUTH_ALLOWED_ORIGINS` (как предусмотрено в Э0). Новая переменная — `AUTH_SEED_FILE`, необязательная.

## Risks / Trade-offs

- **[Загрузка из файла перестала менять существующих]** → осознанно (решение владельца): правки только через админку. Сидер Э0, выдававший роли существующим, меняется; тесты Э0 на это поведение переписываются, в отчёте загрузки существующие записи помечаются `skipped`.
- **[Глобальная advisory-блокировка на административные операции]** → операции редкие и короткие; блокировка снимается автоматически с транзакцией. Риск взаимной блокировки отсутствует, потому что берётся один ключ.
- **[Сортировка по `lower(last_name)` зависит от collation БД]** → при коллации `C` буква «ё» окажется после «я»; для внутреннего справочника допустимо, при необходимости позже добавляется явная коллация.
- **[Отозванная роль `admin` действует до `AUTH_ACCESS_TTL`]** → принято решением владельца; интерфейс прямо сообщает о задержке (спека `featurer-admin-ui`).
- **[Временный пароль виден в ответе API один раз]** → ответ не кэшируется, не пишется в журналы запросов; на фронте не сохраняется. Потерянный пароль восстановить нельзя, сброса в Э1 нет (см. Open Questions).
- **[Руководитель отдела может быть уволен]** → допустимо: связь остаётся, в списке показывается его имя, уволенный отображается как уволенный; вынуждать замену не нужно, так как права не завязаны на руководителя.
- **[Два формата входа сидера]** → прежний формат поддерживается как подмножество нового, при одновременном указании обоих источников команда падает, а не угадывает.

## Migration Plan

1. Миграции `031+` аддитивные: расширение `CHECK` ролей, таблицы `auth_departments` и `auth_user_profiles` с индексами. Существующие пользователи остаются без профиля и работают как раньше. Откат: `DROP TABLE auth_user_profiles; DROP TABLE auth_departments;` и возврат прежнего `CHECK` (безопасно, пока никому не выдана роль `admin`; иначе сначала `DELETE FROM auth_user_roles WHERE role = 'admin'`).
2. Выкат бэкенда. Затем разовая загрузка: положить реальный файл на сервер вне репозитория, указать `AUTH_SEED_FILE`, запустить `npm run seed:users`, передать временные пароли.
3. Первый администратор: либо запись в файле с ролью `admin` (для нового пользователя), либо разовый `INSERT INTO auth_user_roles (user_id, role) VALUES (<id>, 'admin')` для уже существующего (загрузка существующим роли не выдаёт). Роль `admin` и `developer` у одного человека — нормальный случай, роли независимы.
4. Выкат портала (в `AUTH_ALLOWED_ORIGINS` origin портала добавлен ещё в Э0).
