## MODIFIED Requirements

### Requirement: Профиль текущего пользователя
Система SHALL возвращать авторизованному клиенту данные текущего пользователя: идентификатор, логин, `mustChangePassword`, полное имя, фамилию, имя, отчество, должность и отдел (идентификатор и название). Незаполненные поля профиля MUST возвращаться пустыми, а полное имя для пользователя без ФИО MUST совпадать с логином. Роли возвращаются по правилам `user-roles`. Email, идентификатор в SCRM и другие служебные поля в профиль MUST NOT включаться.

#### Scenario: Получение профиля
- **WHEN** клиент с валидным access-токеном запрашивает профиль
- **THEN** система возвращает идентификатор, логин, `mustChangePassword`, полное имя, части ФИО, должность и отдел, но не пароль и не его хэш

#### Scenario: Профиль без ФИО
- **WHEN** запрашивает профиль пользователь, у которого фамилия, имя и отчество не заполнены
- **THEN** полное имя в ответе равно логину, части ФИО пусты

#### Scenario: Профиль без отдела
- **WHEN** запрашивает профиль пользователь без отдела
- **THEN** отдел в ответе пуст

#### Scenario: Данные изменили после входа
- **WHEN** администратор изменил отдел или ФИО пользователя
- **THEN** при следующем запросе профиль возвращает новые значения без повторного входа

### Requirement: Сидирование пользователей
Система SHALL создавать пользователей начальной загрузкой из файла при первом развёртывании (подробности формата и правил — `employee-directory`). Каждому новому пользователю загрузка MUST назначать временный пароль и устанавливать `mustChangePassword = true`. Повторный запуск MUST не перезаписывать и не менять существующих пользователей, их пароли, профили и роли. Загрузка из прежнего источника (список пользователей в переменной окружения) MUST продолжать работать для записей без отделов. Публичной регистрации MUST не быть.

#### Scenario: Первый запуск сидера
- **WHEN** сидер запускается на пустой базе с заданным списком пользователей
- **THEN** создаются пользователи с хэшами временных паролей и `mustChangePassword = true`

#### Scenario: Повторный запуск сидера
- **WHEN** сидер запускается, когда пользователь с таким логином уже существует
- **THEN** существующий пользователь, его пароль, профиль и роли остаются без изменений

#### Scenario: Прежний источник
- **WHEN** сидер запускается со списком в переменной окружения и без файла
- **THEN** пользователи создаются, как раньше, без профиля и отдела
