## Purpose

Поддержка в портале Featurer: сотрудник сообщает о проблеме в работе агента конкретного продукта, разработчик ведёт баг по статусам, а автор всегда видит, что с его обращением.

## ADDED Requirements

### Requirement: Подача бага
Система SHALL позволять любому вошедшему сотруднику сообщить о баге. Запрос MUST содержать название, описание, продукт и агента. Название MUST быть непустым после удаления пробелов по краям и не длиннее 200 символов. Описание MUST быть непустым после удаления пробелов по краям и не длиннее 4000 символов, переносы строк внутри MUST сохраняться. Продукт и агент MUST существовать, агент MUST входить в выбранный продукт и MUST NOT быть в архиве. Новый баг MUST получать статус `open`, автором MUST становиться пользователь из access-токена, а не из данных запроса. Успешная подача MUST отвечать 201 и созданным багом.

Ошибки:
- недопустимые название или описание — 400;
- неизвестный продукт или агент, в том числе некорректный идентификатор, — 404;
- агент не входит в выбранный продукт — 400;
- агент в архиве — 409;
- запрос без access-токена — 401.

Во всех случаях ошибки баг MUST NOT создаваться.

#### Scenario: Сотрудник сообщает о баге
- **WHEN** сотрудник без ролей отправляет баг «Сводка не приходит» по агенту Ассистент продукта Telegram-бот
- **THEN** система отвечает 201, баг создан в статусе `open`, автор — этот сотрудник

#### Scenario: Агент не из этого продукта
- **WHEN** сотрудник выбирает продукт веб и агента, который входит только в control-center
- **THEN** система отвечает 400, баг не создаётся

#### Scenario: Архивный агент
- **WHEN** сотрудник отправляет баг по агенту, который в архиве
- **THEN** система отвечает 409, баг не создаётся

#### Scenario: Пустое описание
- **WHEN** описание состоит из одних пробелов
- **THEN** система отвечает 400, баг не создаётся

#### Scenario: Неизвестный агент
- **WHEN** в запросе идентификатор агента, которого нет
- **THEN** система отвечает 404

### Requirement: Поля бага
Система SHALL возвращать баг в одном формате во всех ответах: идентификатор, название, описание, продукт (идентификатор и название), агент (идентификатор и название), автор (идентификатор, логин и полное имя, без ФИО — логин), статус, время создания, время последней смены статуса, разработчик, который последним сменил статус (идентификатор, логин и полное имя, пусто, пока статус не менялся), причина для `wont_fix` (пусто в остальных статусах) и список статусов, в которые баг можно перевести сейчас. Список следующих статусов MUST быть пустым для пользователя без роли `developer`. Название продукта и агента MUST возвращаться текущее, даже если агент позже перенесён в архив. Система MUST NOT хранить историю статусов бага: только текущий статус и время его смены.

#### Scenario: Баг глазами автора
- **WHEN** автор без ролей открывает свой баг в статусе `open`
- **THEN** ответ содержит все поля бага, разработчик пуст, список следующих статусов пуст

#### Scenario: Баг глазами разработчика
- **WHEN** разработчик открывает баг в статусе `open`
- **THEN** список следующих статусов — `in_progress` и `wont_fix`

#### Scenario: Агент в архиве после подачи
- **WHEN** после подачи бага агент перенесён в архив
- **THEN** баг по-прежнему открывается и показывает название агента

### Requirement: Доступ к багу
Система SHALL показывать баг только его автору и пользователям с ролью `developer`. Для остальных вошедших пользователей баг MUST быть неотличим от несуществующего: запрос MUST отвечаться 404. Неизвестный или некорректный идентификатор MUST отвечаться 404. Запрос без access-токена MUST отвечаться 401.

#### Scenario: Автор открывает свой баг
- **WHEN** автор запрашивает свой баг
- **THEN** система отвечает 200 и возвращает баг

#### Scenario: Разработчик открывает чужой баг
- **WHEN** разработчик запрашивает баг другого сотрудника
- **THEN** система отвечает 200

#### Scenario: Посторонний сотрудник
- **WHEN** сотрудник без роли `developer` запрашивает чужой баг
- **THEN** система отвечает 404

#### Scenario: Некорректный идентификатор
- **WHEN** пользователь запрашивает баг с идентификатором неверного формата
- **THEN** система отвечает 404

### Requirement: Мои обращения
Система SHALL возвращать вошедшему пользователю список его багов от новых к старым, постранично, с общим числом записей. Каждая запись MUST содержать идентификатор, название, продукт, агента, статус, время создания и время последней смены статуса. Чужие баги MUST NOT попадать в список, в том числе у разработчика.

#### Scenario: Список своих багов
- **WHEN** сотрудник, подавший три бага, запрашивает «Мои обращения»
- **THEN** система возвращает три бага, самый новый первым, и общее число 3

#### Scenario: Разработчик видит только свои
- **WHEN** разработчик без собственных багов запрашивает «Мои обращения»
- **THEN** список пуст

### Requirement: Очередь багов разработчика
Система SHALL возвращать пользователю с ролью `developer` очередь всех багов постранично, с общим числом записей и необязательным фильтром по статусу. Без фильтра в очереди MUST быть только незакрытые баги (`open` и `in_progress`). Порядок MUST быть: сначала `open`, затем `in_progress`, внутри статуса — от старых к новым по времени создания. С фильтром по статусу MUST возвращаться баги только этого статуса; для `resolved` и `wont_fix` — от новых к старым по времени смены статуса. Каждая запись MUST содержать поля записи «Моих обращений» и автора (полное имя, без ФИО — логин). Пользователю без роли `developer` MUST отвечаться 403. Недопустимое значение фильтра MUST отвечаться 400.

#### Scenario: Очередь по умолчанию
- **WHEN** в системе баги в статусах `open`, `in_progress` и `resolved`, и разработчик запрашивает очередь без фильтра
- **THEN** в ответе баги `open` и `in_progress`, сначала `open`, решённого нет

#### Scenario: Фильтр по статусу
- **WHEN** разработчик запрашивает очередь с фильтром `resolved`
- **THEN** в ответе только решённые баги, недавно решённые первыми

#### Scenario: Сотрудник без роли
- **WHEN** сотрудник без роли `developer` запрашивает очередь багов
- **THEN** система отвечает 403

### Requirement: Жизненный цикл бага
Система SHALL поддерживать статусы бага `open` («Открыт»), `in_progress` («В работе»), `resolved` («Исправлен») и `wont_fix` («Не будет исправлен») и разрешать только переходы:
- `open → in_progress`, `open → wont_fix`;
- `in_progress → resolved`, `in_progress → wont_fix`, `in_progress → open`;
- `resolved → in_progress`, `wont_fix → in_progress` (переоткрытие).

Менять статус MUST только пользователь с ролью `developer`, иначе 403. Переход в `wont_fix` MUST требовать причину: непустую после удаления пробелов по краям и не длиннее 2000 символов, иначе 400. Причина при других переходах MUST игнорироваться, а при уходе из `wont_fix` MUST очищаться. Недопустимый переход MUST отвечаться 409 без изменений. Если статус бага изменился между чтением и запросом и переход из текущего статуса недопустим, MUST отвечаться 409. Успешная смена MUST записывать время смены и разработчика, отвечать 200 и багом в новом статусе. Неизвестный баг MUST отвечаться 404.

#### Scenario: Взять баг в работу
- **WHEN** разработчик переводит баг из `open` в `in_progress`
- **THEN** система отвечает 200, статус `in_progress`, разработчик и время смены записаны

#### Scenario: Закрыть как повтор
- **WHEN** разработчик переводит баг из `open` в `wont_fix` с причиной «Повтор бага 3f2a…, уже исправляется»
- **THEN** статус `wont_fix`, причина сохранена и видна автору

#### Scenario: Отказ без причины
- **WHEN** разработчик переводит баг в `wont_fix` без причины
- **THEN** система отвечает 400, статус не меняется

#### Scenario: Недопустимый переход
- **WHEN** разработчик переводит баг из `open` сразу в `resolved`
- **THEN** система отвечает 409, статус не меняется

#### Scenario: Переоткрытие
- **WHEN** автор написал, что проблема осталась, и разработчик переводит баг из `resolved` в `in_progress`
- **THEN** статус `in_progress`, причина пуста

#### Scenario: Гонка двух разработчиков
- **WHEN** два разработчика одновременно переводят один баг из `in_progress`: первый в `resolved`, второй в `open`
- **THEN** один запрос выполняется, второй отвечает 409, если его переход из нового статуса недопустим

#### Scenario: Сотрудник без роли
- **WHEN** автор бага без роли `developer` пытается сменить его статус
- **THEN** система отвечает 403

### Requirement: События по багам в outbox
Система SHALL в той же транзакции, что и изменение, записывать в outbox:
- при подаче бага — событие о новом баге с идентификатором бага, автором, названием бага, названиями продукта и агента;
- при смене статуса — событие о смене статуса с идентификатором бага, автором бага, разработчиком, названием бага, прежним и новым статусом и причиной для `wont_fix`.

Если событие записать не удалось, изменение MUST NOT сохраняться.

#### Scenario: Подача и событие атомарны
- **WHEN** сотрудник подаёт баг
- **THEN** баг и событие о нём сохраняются вместе

#### Scenario: Событие смены статуса
- **WHEN** разработчик закрывает баг как `wont_fix` с причиной
- **THEN** в outbox появляется событие с прежним статусом, `wont_fix` и причиной
