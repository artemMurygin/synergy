## Why

Сотрудник узнаёт о назначенной ему задаче, только если сам откроет список задач: система никак не сообщает о событиях, которые его касаются. Нужен единый механизм уведомлений, который доставляет событие в реальном времени во все открытые интерфейсы пользователя (control-center и manager-helper) и который можно расширять новыми каналами доставки (следующим будет Telegram) и новыми типами событий без переделки ядра.

## What Changes

- Backend: новый модуль `notifications`:
  - хранение уведомлений в Postgres: получатель, тип, заголовок, текст, ссылка на объект (например, на задачу), время создания, время прочтения;
  - REST API для получателя: список своих уведомлений с пагинацией, число непрочитанных, отметка одного и всех уведомлений прочитанными;
  - расширяемая доставка: ядро создаёт уведомление и передаёт его всем зарегистрированным каналам. В этом change реализуется канал «в приложении» (сохранение и отправка по WebSocket). Новый канал (Telegram) добавляется отдельным адаптером без изменения ядра и триггеров;
  - расширяемые триггеры: уведомления создаются реакцией на доменные события других модулей, а модуль-источник ничего не знает о каналах и получателях.
- Backend: WebSocket-шлюз для доставки в реальном времени:
  - подключение только с валидным access-токеном;
  - у одного пользователя может быть несколько одновременных соединений (несколько устройств, вкладок, приложений), и уведомление приходит в каждое;
  - после переподключения клиент дочитывает пропущенное через REST, так что уведомления не теряются.
- Backend: реализуется публикация доменных событий через transactional outbox. Событие пишется в БД в той же транзакции, что и изменение, а фоновый relay доставляет его подписчикам с ретраями. Это гарантирует, что событие не теряется при падении процесса. Каналы доставки тоже получают уведомления через outbox, так что будущий Telegram-канал сразу получит ретраи.
- Backend: `TransactionRunner` выносится из модуля `auth` в общую инфраструктуру. Модуль задач переходит на транзакции.
- Базовый сценарий: при создании задачи с ответственным система уведомляет ответственного. Если ответственный и есть создатель, уведомление не создаётся.
- control-center: колокольчик с числом непрочитанных, список уведомлений, всплывающее уведомление при получении нового, переход к задаче по клику, отметка прочитанными.
- manager-helper: фоновый процесс (service worker) держит одно WebSocket-соединение, пока браузер открыт и пользователь залогинен, даже если side panel закрыт.
  - Когда панель закрыта, он показывает системное уведомление браузера, а число непрочитанных выводит бейджем на иконке расширения.
  - Клик по уведомлению открывает панель на задаче.
  - Уведомления, пропущенные, пока браузер был закрыт, показываются после запуска; если их много, одним сводным.
  - В открытой панели — компактный список, счётчик, всплывающее уведомление и переход к задаче; события панель получает от фонового процесса.

## Capabilities

### New Capabilities
- `domain-event-outbox`: надёжная публикация доменных событий: атомарная запись вместе с изменением, доставка каждому подписчику «хотя бы один раз», ретраи с backoff, перевод в `failed` после лимита попыток, порядок в пределах агрегата, очистка обработанных событий.
- `notifications`: модель уведомления, хранение, REST API получателя (список, непрочитанные, отметка прочитанными), расширяемые каналы доставки и правила, по которым доменные события превращаются в уведомления.
- `notifications-realtime`: WebSocket-доставка: аутентификация соединения, несколько соединений на пользователя, формат событий, поведение при разрыве и переподключении.
- `notifications-desktop-ui`: уведомления в control-center: колокольчик и счётчик, список, всплывающие уведомления, переход к объекту, отметка прочитанными, состояние соединения.
- `notifications-extension-ui`: уведомления в manager-helper. Фоновое соединение в service worker, системные уведомления браузера при закрытой панели, бейдж с непрочитанными, показ пропущенного после запуска браузера, переход к задаче по клику. В side panel — счётчик, список и всплывающие уведомления.

### Modified Capabilities
- `task-management`: при создании задачи с ответственным система публикует событие о назначении, и ответственный (если это не создатель) получает уведомление.

## Impact

- `backend/src/modules/notifications/*`: новый модуль (domain, application, infrastructure, interface): сущность уведомления, порт канала доставки, канал «в приложении», WebSocket-шлюз, REST-контроллер.
- `backend/src/shared/ddd` и `backend/src/database/postgres`: порт `DomainEventPublisherPort` (переименование), outbox-публикатор, реестр событий, relay с ретраями, общий `TransactionRunner`. Модуль `auth` переключается на общий runner без изменения поведения.
- `backend/src/modules/tasks`: `Task` порождает `TaskCreatedEvent`. Use-case создания сохраняет задачу и событие в одной транзакции. Репозитории задач пишут через транзакционный executor.
- `backend/db/migrations`: таблицы `outbox_events`, `outbox_deliveries`, `notifications` и их индексы.
- Новые настройки окружения: интервал опроса outbox, лимит попыток, срок хранения обработанных событий.
- Зависимости: пакет NestJS для WebSocket (`@nestjs/websockets` с адаптером). Если бэкенд работает в нескольких экземплярах, нужна рассылка между ними; Redis в проекте уже есть. Выбор фиксируется в design.
- `control-center`: WebSocket-соединение из renderer или из main через существующий механизм авторизации (зависит от `add-electron-auth`), UI-компоненты уведомлений, интеграция с разделом задач из `add-tasks-clients`.
- `manager-helper`:
  - `src/background`: соединение, системные уведомления, бейдж, сторож на `chrome.alarms`;
  - `shared/auth/session-channel`: новое сообщение `session-started`;
  - side panel: UI уведомлений и порт к фоновому процессу;
  - манифест: разрешения `notifications`, `alarms` и `minimum_chrome_version: "116"`.
- Переход к задаче по клику зависит от экранов задач из `add-tasks-clients`.
- Вне рамок: канал Telegram, пользовательские настройки уведомлений, системные уведомления ОС в control-center, уведомления о других событиях задач (смена ответственного, статуса, дедлайна).
