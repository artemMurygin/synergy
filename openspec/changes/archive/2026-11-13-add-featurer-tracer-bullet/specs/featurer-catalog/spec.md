## Purpose

Минимальный каталог портала Featurer: продукты, их агенты и навыки агентов с жизненным циклом статуса. Навык — единица, к которой привязываются заявки и от статуса которой зависит видимый автору статус заявки.

## ADDED Requirements

### Requirement: Продукты и агенты из seed
Система SHALL содержать продукты и их агентов, заведённые сидером при развёртывании. Начальный набор продуктов: control-center, manager-helper, Telegram-бот, веб. Повторный запуск сидера MUST NOT создавать дубликаты и MUST NOT перезаписывать существующие записи. Создание и редактирование продуктов и агентов через API MUST NOT предоставляться.

#### Scenario: Первый запуск сидера
- **WHEN** сидер запускается на пустой базе
- **THEN** создаются продукты начального набора и их агенты

#### Scenario: Повторный запуск сидера
- **WHEN** сидер запускается, когда продукты и агенты уже существуют
- **THEN** количество продуктов и агентов не меняется

### Requirement: Список агентов
Система SHALL возвращать вошедшему сотруднику список агентов с названием, продуктом, к которому агент относится, и идентификатором, чтобы разработчик мог выбрать агента для нового навыка.

#### Scenario: Получение списка
- **WHEN** вошедший пользователь запрашивает список агентов
- **THEN** система отвечает 200 и возвращает агентов вместе с их продуктами

#### Scenario: Запрос без токена
- **WHEN** клиент запрашивает список агентов без access-токена
- **THEN** система отвечает 401

### Requirement: Поля навыка
Система SHALL хранить для навыка: идентификатор, агента, которому он принадлежит, название, описание, статус, время создания и время последней смены статуса. Навык MUST принадлежать ровно одному агенту. Название MUST быть непустым после удаления пробелов по краям и не длиннее установленного предела; описание MAY быть пустым.

#### Scenario: Навык с полными полями
- **WHEN** разработчик создаёт навык «Сводка встречи» у агента Ассистент с описанием
- **THEN** навык сохраняется с названием, описанием, агентом, статусом `planned` и временем создания

#### Scenario: Пустое название
- **WHEN** разработчик создаёт навык, у которого название состоит из пробелов
- **THEN** система отвечает 400 и навык не создаётся

#### Scenario: Несуществующий агент
- **WHEN** разработчик создаёт навык для несуществующего агента
- **THEN** система отвечает 404 и навык не создаётся

### Requirement: Жизненный цикл статуса навыка
Система SHALL поддерживать для навыка статусы `planned`, `in_dev`, `testing`, `launched`. Новый навык MUST создаваться в статусе `planned`. Система MUST разрешать переход только на соседний статус вперёд по порядку `planned → in_dev → testing → launched`. Переход назад, пропуск статуса, повтор текущего статуса и любой переход из `launched` MUST отклоняться ответом 409 без изменения навыка. Неизвестное значение статуса MUST отвечаться 400.

#### Scenario: Переход вперёд
- **WHEN** разработчик меняет статус навыка с `planned` на `in_dev`
- **THEN** система отвечает 200, статус навыка становится `in_dev`, время смены статуса обновляется

#### Scenario: Пропуск статуса
- **WHEN** разработчик пытается перевести навык из `planned` сразу в `testing`
- **THEN** система отвечает 409, статус остаётся `planned`

#### Scenario: Переход назад
- **WHEN** разработчик пытается вернуть навык из `testing` в `in_dev`
- **THEN** система отвечает 409, статус остаётся `testing`

#### Scenario: Запущенный навык
- **WHEN** разработчик пытается изменить статус навыка в `launched`
- **THEN** система отвечает 409, статус остаётся `launched`

#### Scenario: Неизвестный статус
- **WHEN** разработчик передаёт значение статуса, которого нет в списке
- **THEN** система отвечает 400

### Requirement: Создание и смена статуса навыка только разработчиком
Система SHALL разрешать создавать навык и менять его статус только пользователю с ролью `developer`. Остальным вошедшим пользователям система MUST отвечать 403, неавторизованным — 401.

#### Scenario: Сотрудник без роли создаёт навык
- **WHEN** пользователь без роли `developer` пытается создать навык или сменить его статус
- **THEN** система отвечает 403, данные не меняются

### Requirement: Список навыков
Система SHALL возвращать пользователю с ролью `developer` список навыков с названием, агентом, продуктом, статусом, временем последней смены статуса и числом привязанных заявок, с фильтром по статусу. Сотруднику без роли список навыков в целом MUST NOT возвращаться; сотрудник видит только навык, к которому привязана его собственная заявка (см. `featurer-requests`).

#### Scenario: Список для разработчика
- **WHEN** разработчик запрашивает список навыков
- **THEN** система отвечает 200 и возвращает навыки с числом привязанных заявок

#### Scenario: Фильтр по статусу
- **WHEN** разработчик запрашивает список навыков со статусом `in_dev`
- **THEN** в ответе только навыки в этом статусе

#### Scenario: Список для сотрудника без роли
- **WHEN** пользователь без роли `developer` запрашивает список навыков
- **THEN** система отвечает 403

### Requirement: Событие смены статуса навыка
Система SHALL при каждой успешной смене статуса навыка записывать в outbox событие в той же транзакции, что и смена статуса. Событие MUST содержать идентификатор навыка, прежний и новый статус и пользователя, сменившего статус. Отклонённая смена статуса MUST NOT записывать событие.

#### Scenario: Успешная смена
- **WHEN** статус навыка успешно сменился с `in_dev` на `testing`
- **THEN** в outbox есть одно событие с этим навыком, прежним статусом `in_dev` и новым `testing`

#### Scenario: Отклонённая смена
- **WHEN** смена статуса отклонена ответом 409
- **THEN** новое событие в outbox не записывается
