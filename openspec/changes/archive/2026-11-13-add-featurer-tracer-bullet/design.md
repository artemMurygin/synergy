## Context

Мотивация и скоуп — в `proposal.md`, требования — в `specs/`. Здесь только то, как это встраивается в существующий код.

Что уже есть и ограничивает решение:

- **Бэкенд** — NestJS, модули в `backend/src/modules/*` по слоям `domain / application / infrastructure / interface`, SQL-миграции `backend/db/migrations/NNN_name.sql` (последняя — `026`), транзакции через `TransactionRunner`, события через outbox (`shared/outbox`) с подписчиками `EventSubscriber` и событиями в `<module>/contracts`, как у `tasks`.
- **Auth.** Refresh-cookie `mh_refresh`: `SameSite=Strict`, `path=/auth`, `Secure` только на HTTPS (`refresh-cookie.service.ts`). Cookie-эндпоинты защищает `OriginGuard` по `AUTH_ALLOWED_ORIGINS`. Тот же список управляет CORS с `credentials: true` (`configure-http.ts`). Роли в `auth_users` не хранятся.
- **Notifications.** Типы объекта ограничены в коде (`NOTIFICATION_TARGET_TYPES = ['task', 'chat']`), в БД `target_type` — свободный текст. Уникальный индекс `notifications (source_event_id, recipient_id, type)` обеспечивает идемпотентность повторной обработки события. Telegram-канал тип объекта не использует.
- **Клиенты** — `control-center` (Electron) и `manager-helper` (расширение) читают `GET /notifications` и сами решают, как показать объект уведомления.

## Goals / Non-Goals

**Goals:**
- Один сквозной срез «идея → решение → навык → статус → уведомление», который следующие этапы наращивают без переписывания: модель заявки и навыка, вывод статуса, события, роль.
- Не менять поведение существующих модулей, кроме явно перечисленных точек (профиль в `auth`, тип `request` и два подписчика в `notifications`).

**Non-Goals:**
- Общая библиотека UI между `portal/` и `control-center`. Токены дизайн-кита копируются в тему портала; выделение пакета — когда появится второй потребитель.
- Кэширование ролей, права на уровне отдельных объектов, аудит решений сверх `decided_by` и `decided_at`.
- Рассылка уведомлений разработчикам о новых заявках: очередь смотрят сами.

## Decisions

### 1. Новый модуль `portal` в бэкенде, роли живут в `auth`
Каталог, навыки и заявки — один модуль `portal` (один bounded context: навык и заявка связаны транзакционно при принятии). Роли — часть идентичности пользователя, поэтому таблица `auth_user_roles`, чтение и `RolesGuard` — в модуле `auth`, `portal` лишь навешивает guard на эндпоинты.

*Альтернативы:* отдельные модули `catalog` и `requests` — отвергнуто: принятие заявки с созданием навыка пришлось бы делать через два модуля и распределённую транзакцию. Роли внутри `portal` — отвергнуто: Э1 расширит роли за пределы Featurer.

### 2. Роли: таблица `auth_user_roles`, роли в access-токене
`auth_user_roles(user_id, role)`, PK `(user_id, role)`, `CHECK (role IN ('developer'))`. Роли читаются из БД при входе и при обновлении сессии и записываются в access-токен (новое поле claims `rol`). `RolesGuard` и профиль берут роли из токена, без запроса в БД. Токен живёт `AUTH_ACCESS_TTL` (по умолчанию 15 минут), поэтому выдача и отзыв роли вступают в силу не позднее чем через это время; именно это закреплено в спеке `user-roles`.

Назначение — расширение существующего `seed:users`: необязательное поле `roles` в JSON-списке. Неизвестная роль — ошибка запуска сидера, повторный запуск идемпотентен (`ON CONFLICT DO NOTHING`). Отдельного механизма не заводим.

*Альтернатива:* читать роль из БД на каждый запрос — даёт мгновенный отзыв, но добавляет запрос на каждое обращение разработчика. Отвергнуто осознанно: для внутреннего портала задержка до 15 минут допустима. Новое поле `rol` в claims добавляется как необязательное; что клиенты (расширение, десктоп) не разбирают claims сами, предположение — проверяется отдельной задачей.

### 3. Модель данных
Миграции начинаются с `027`:

| Таблица | Поля и ограничения |
|---|---|
| `portal_products` | `id`, `slug` UNIQUE, `name` |
| `portal_agents` | `id`, `product_id` → продукт, `slug` UNIQUE, `name` |
| `portal_skills` | `id`, `agent_id`, `name`, `description`, `status` CHECK из четырёх значений, `created_at`, `status_changed_at` |
| `portal_requests` | `id`, `author_id` → `auth_users`, поля анкеты, `decision` (`pending`/`accepted`/`rejected`), `skill_id` NULL, `reject_reason` NULL, `decided_by`, `decided_at`, `created_at` |

Инварианты — в БД `CHECK`: `accepted ⇔ skill_id IS NOT NULL`, `rejected ⇔ reject_reason` непустая; числа анкеты `> 0`. Статуса «для автора» в таблице **нет**.

### 4. Статус заявки выводится, а не хранится
Статус для автора вычисляется при чтении: `pending` → «На рассмотрении», `rejected` → «Отклонена», `accepted` → статус навыка через JOIN. Это единственное место, где живёт правило, и рассинхронизация исключена по построению.

*Альтернатива:* хранить статус заявки и обновлять его по событию смены статуса навыка. Отвергнуто: две копии истины, окно рассинхронизации при сбое обработчика, лишний подписчик. Цена выбранного варианта — JOIN в «Моих заявках»; индекс по `portal_requests (author_id, created_at DESC)` и PK навыка это покрывают.

### 5. Конкурентность: условные обновления и блокировка навыка
- Решение по заявке: `UPDATE … WHERE id = $1 AND decision = 'pending'`; 0 строк → 409.
- Смена статуса навыка: `UPDATE … WHERE id = $1 AND status = <ожидаемый предыдущий>`; 0 строк → 409 («одновременная правка» из сценария портала).
- Принятие заявки в навык и смена статуса навыка берут строку навыка `SELECT … FOR UPDATE`. Благодаря этому набор привязанных заявок, попадающий в событие смены статуса, согласован с привязками.
- Принятие с созданием навыка — одна транзакция: навык, привязка и событие либо все есть, либо нет.

### 6. События: снимок привязанных заявок внутри события
Outbox-события в `portal/contracts` (по образцу `tasks/contracts`):
- `RequestAccepted` — заявка, автор, разработчик, навык (id, название, статус).
- `RequestRejected` — заявка, автор, разработчик, причина.
- `SkillStatusChanged` — навык, прежний и новый статус, инициатор и **снимок** `[{requestId, authorId, title}]` привязанных заявок на момент смены, прочитанный в той же транзакции (см. п. 5).

*Альтернатива:* событие только с `skillId`, подписчик сам ищет заявки при обработке. Отвергнуто: заявка, привязанная между сменой статуса и обработкой события, получила бы уведомление о смене, которой для неё не было, а повторная обработка давала бы разный результат. Снимок детерминирован. Размер события не проблема на масштабе Э0; если навык соберёт сотни заявок, это станет вопросом Э3+.

### 7. Уведомления: два подписчика и правка уникального индекса
В модуле `notifications` по образцу `TaskCreatedSubscriber`: правила в `domain/*.rule.ts`, подписчики вызывают `CreateNotificationsUseCase.execute(event.id, drafts)` одним вызовом. `'request'` добавляется в `NOTIFICATION_TARGET_TYPES`, в БД менять тип не нужно.

**Конфликт с существующим индексом.** `(source_event_id, recipient_id, type)` оставит автору с двумя заявками на один навык одно уведомление на смену статуса, а спека требует по одному на заявку. Решение — миграция, расширяющая индекс до `(source_event_id, recipient_id, type, target_id)`. Это ослабляет ограничение (все существующие строки остаются валидными), идемпотентность повторной обработки сохраняется, потому что `target_id` детерминирован событием.

*Альтернатива:* отдельное outbox-событие на каждую заявку. Отвергнуто: размножает события и ломает атомарность «смена статуса — одно событие».

Тексты уведомлений собираются на сервере и замораживаются (требование `notifications`). Названия статусов навыка на русском — один словарь в `portal/contracts`, общий для API заявок и текстов уведомлений.

### 8. HTTP API
Все под `/portal`, схемы zod и пагинация — как в остальных модулях (`pagination.schema.ts`).

| Метод и путь | Доступ |
|---|---|
| `POST /portal/requests` | любой вошедший |
| `GET /portal/requests/my`, `GET /portal/requests/:id` | автор; разработчик может открыть любую; чужая для обычного пользователя — 404 |
| `GET /portal/queue` | `developer` |
| `POST /portal/requests/:id/accept`, `…/reject` | `developer` |
| `GET /portal/agents` | любой вошедший |
| `GET`, `POST /portal/skills`, `POST /portal/skills/:id/status` | `developer` |

Тело `accept` — либо `{skillId}`, либо `{agentId, name, description}`; валидация исключает смешение вариантов.

### 9. Seed продуктов и агентов
Отдельный идемпотентный CLI `seed:portal` (по образцу `seed-users.cli.ts`): фиксированные `slug`, `INSERT … ON CONFLICT (slug) DO NOTHING`, существующие записи не перезаписываются. Данные заданы константами в коде модуля, не env-JSON: они меняются редко и должны жить в ревью.

Начальный состав взят из реальных возможностей бэкенда (`AgentCapability` в `assistant`, профили `app` и `telegram`):

| Продукт | Агенты |
|---|---|
| `control-center` | Ассистент (оркестратор профиля `app`), Задачи (`tasks`), Встречи (`meetings`), Цены (`sheets_qa`) |
| `manager-helper` | Аудит сделок (`audit-agent`) |
| `telegram-bot` | Агент задач (профиль `telegram`) |
| `web` | пока без агентов (сам портал; агенты появятся в Э2) |

Агент принадлежит одному продукту, поэтому одна и та же возможность бэкенда не дублируется по продуктам. Названия на русском, `slug` — латиницей.

### 10. Портал: куда его хостить и как не сломать cookie
Cookie `SameSite=Strict` отправляется только при **same-site** запросах, то есть портал и API должны быть на одном зарегистрируемом домене (поддомены допустимы, порты не учитываются). Менять cookie не нужно.

Решение: портал и API на одном зарегистрированном домене, по HTTPS (иначе `Secure` не выставляется, а браузер для `SameSite=Strict` кросс-сайт всё равно не отправит). Origin портала добавляется в `AUTH_ALLOWED_ORIGINS`, и это одновременно открывает `OriginGuard` и CORS с credentials. Для локальной разработки `localhost:<vite-порт>` и `localhost:<порт API>` — один site, поэтому ничего дополнительного не нужно.

*Альтернативы:* `SameSite=Lax`/`None` — отвергнуто: ослабляет CSRF-защиту, на которую опирается весь `OriginGuard` и которая общая с расширением. Reverse proxy на один origin — рабочий вариант, но не обязателен: поддомена достаточно, а прокси добавляет компонент инфраструктуры.

Конкретный домен — вопрос развёртывания, не дизайна (см. Open Questions).

### 11. Фронтенд `portal/`
Отдельное SPA на Vite (не Electron): React 19, TanStack Query, zustand, Tailwind 4. Access-токен в памяти (zustand), восстановление по cookie при открытии, один общий refresh при 401 — те же правила, что у клиентов `auth-session`. Токены дизайн-кита копируются в тему Tailwind. Роли из профиля скрывают разделы; сервер остаётся источником истины.

### 12. Переход из уведомлений в портал
Клиенты (`control-center`, `manager-helper`) сегодня знают только типы объекта `task` и `chat`; схемы принимают любую строку, поэтому список не ломается, но на `request` ничего не происходит. Добавляется обработка `request`: открыть в браузере `<адрес портала>/requests/<id>`.

- **Адрес портала** — в конфигурации каждого клиента, рядом с адресом бэкенда. Сервер адрес не отдаёт: уведомление остаётся «тип и id», как для `task` и `chat`, и контракт `notifications` не растёт.
- **`control-center`:** открытие во внешнем браузере (в приложении уже есть путь «открыть внешний адрес», ограниченный проверкой безопасного URL); портал открывается вне окна приложения.
- **`manager-helper`:** новая вкладка (`chrome.tabs.create`), которая не требует новых разрешений в манифесте. Для системного уведомления при закрытой панели клик обрабатывается в фоне, без обязательного открытия панели.
- **Портал:** маршрут `/requests/:id`, возврат на заявку после входа, сообщение «Заявка не найдена» вместо технической ошибки.

*Альтернатива:* сервер кладёт готовую ссылку в уведомление. Отвергнуто: ссылка «заморозилась» бы при смене домена портала, а в базе уже лежат неизменяемые уведомления.

## Risks / Trade-offs

- **[Расширение индекса `notifications` затрагивает чужой модуль]** → ослабляющая миграция, существующие тесты `notifications` запускаются в регрессии; добавляются сценарий с двумя заявками одного автора и повторной обработкой.
- **[Клиенты открывают портал по настроенному адресу]** → клиент открывает только адрес настроенного портала, идентификатор кодируется; если адрес не задан, уведомление прочитано, пользователь видит сообщение (требование в спеках клиентов). Проверка вручную: уведомление `request` в обоих клиентах.
- **[Роли в токене: отзыв не мгновенный]** → отозванная роль действует до истечения access-токена (до 15 минут по умолчанию); для критичных действий позже можно добавить проверку по БД на конкретных эндпоинтах.
- **[Снимок заявок в событии растёт с числом заявок на навык]** → на Э0 пренебрежимо; пересмотр в Э3 вместе с дубликатами.
- **[Разработчик может остаться без роли после ошибки seed]** → сидер идемпотентен, роль можно выдать SQL (по proposal).
- **[Навык нельзя вернуть назад]** → осознанное решение спеки; ошибочный статус в Э0 исправляется SQL. Пересмотр — в Э2 вместе с управлением каталогом.

## Migration Plan

1. Миграции `027+` (роли, каталог, заявки) и миграция индекса `notifications` — аддитивные, откат — удаление новых таблиц и возврат прежнего индекса (безопасен, пока нет дублей по `(source_event_id, recipient_id, type)`).
2. Добавить origin портала в `AUTH_ALLOWED_ORIGINS` до выката портала, иначе cookie-эндпоинты ответят 403.
3. Выкат бэкенда, затем `seed:users` с ролью `developer` и `seed:portal`.
4. Выкат портала на поддомен того же домена.

Откат бэкенда безопасен: новые таблицы изолированы, добавленные подписчики уведомлений просто перестают работать.

## Open Questions

- Адреса портала и API на стенде. Нужно только одно: оба должны быть на одном домене, например `featurer.example.ru` и `api.example.ru`, по HTTPS (причина — п. 10). Какие именно адреса, решают при развёртывании; это значение конфигурации `AUTH_ALLOWED_ORIGINS`, а не изменение подхода.
- Привязка «Аудита сделок» к продукту `manager-helper` взята по смыслу (CRM-сделки в расширении), в коде это не проверено. Если окажется иначе, правится одна константа в seed.
