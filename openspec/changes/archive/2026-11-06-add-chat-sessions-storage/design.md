## Context

Мотивация — см. `proposal.md`. Текущее состояние:

- `backend/src/modules/sheets-qa`: `POST /sheets-qa/ask` принимает `{question, sessionId}` и вызывает `DeepAgentsSheetsAssistant`, который держит `MemorySaver` (checkpointer LangGraph) внутри процесса; `thread_id = sessionId`. Агент создаётся на каждый вопрос.
- Postgres уже подключён: `PostgresModule` (`PG_POOL` на slonik), миграции `backend/db/migrations/NNN_*.sql` применяются при старте. Следующий номер — `012`.
- `manager-helper` (расширение, React + Vite): история в `useState` в `use-chat.ts`, `sessionId` генерируется на клиенте, адрес бэкенда берётся из настроек (`getBackendUrl`).
- Авторизации в расширении нет; бэкенд один, пользователь один.

## Goals / Non-Goals

**Goals:**
- Две независимые части памяти чата: история для показа в UI и контекст агента для продолжения диалога; обе переживают перезапуск.
- Минимум нового: переиспользовать пул Postgres и существующий механизм миграций.
- Не менять поведение самого агента (промпт, инструменты, подагенты).

**Non-Goals:**
- Мультипользовательность, права доступа, шаринг чатов.
- Стриминг ответов, пагинация истории и списка (на текущих объёмах не нужны).
- Перенос старых in-memory диалогов — их не существует после перезапуска.

## Decisions

### 1. Две таблицы предметной области + таблицы checkpointer'а

`chat_session(id uuid pk, title, title_is_custom bool, created_at, last_activity_at)` и `chat_message(id bigserial pk, session_id fk on delete cascade, role, text, tool_calls jsonb, duration_ms, created_at)`; индексы по `last_activity_at desc` и `(session_id, id)`.

Контекст агента хранится отдельно в таблицах checkpointer'а LangGraph, ключ — `thread_id = chat_session.id`.

*Почему отдельно:* checkpoint — внутренний формат графа (сообщения LangChain, состояние подагентов, todo), он нестабилен и не годится как источник для UI. История для UI — наш контракт.
*Альтернатива:* восстанавливать контекст агента из `chat_message` на каждый запрос. Отвергнуто: теряются tool-сообщения и состояние deepagents, приходится самим сериализовать/десериализовать формат LangChain.

### 2. Постоянный checkpointer — `PostgresSaver`

Заменяем `MemorySaver` на `PostgresSaver` (`@langchain/langgraph-checkpoint-postgres`) на том же `POSTGRES_URL`; `setup()` вызывается один раз при инициализации модуля. При удалении чата вызываем `deleteThread(sessionId)`.

*Альтернатива:* оставить `MemorySaver`. Отвергнуто: требование «после перезапуска всё сохраняется».
*Риск:* checkpointer создаёт собственные таблицы вне наших миграций — см. «Риски».

### 3. Источник идентификатора — сервер

Клиент вызывает `POST /chat-sessions`, получает `id` и дальше передаёт его в `ask`. `ask` для неизвестного `id` отвечает 404. Это устраняет возможность «случайно создать» контекст в checkpointer'е из-за опечатки.

*Альтернатива:* создавать сессию лениво на первом `ask` с клиентским uuid. Отвергнуто: размывает контракт и усложняет удаление/ошибки.

### 4. Размещение API: отдельная подсистема сессий внутри модуля `sheets-qa`

Новые эндпоинты: `POST/GET /chat-sessions`, `GET /chat-sessions/:id/messages`, `PATCH /chat-sessions/:id`, `DELETE /chat-sessions/:id`. `POST /sheets-qa/ask` остаётся по пути, но проверяет сессию и пишет историю. Слои — по правилам проекта (domain / application / infrastructure / interface), порт репозитория и порт ассистента, реализации на slonik.

*Альтернатива:* отдельный модуль `chat-sessions`. Решение зафиксировано в `architecture.md`; логика привязана только к `sheets-qa`, второго потребителя пока нет, поэтому отдельный модуль преждевременен.

### 5. Порядок записи при вопросе

1. Проверить, что сессия существует (404 иначе).
2. Сохранить сообщение пользователя.
3. Вызвать агента.
4. В одной транзакции сохранить ответ агента, обновить `last_activity_at` и при необходимости автоназвание.

Если агент упал — сообщение пользователя остаётся, ответ не пишется (соответствует спеке). Параллельные вопросы в одну сессию клиент блокирует; на сервере лёгкая защита не вводится (один пользователь), но порядок сообщений обеспечивается `bigserial`.

### 6. Автоназвание — усечение первого вопроса

Название по умолчанию — «Новый чат», флаг `title_is_custom=false`. После первого вопроса название = первые ~60 символов вопроса. Явное переименование ставит `title_is_custom=true`. *Альтернатива:* вызов LLM для названия — лишняя стоимость и задержка; можно добавить позже без изменения контракта.

### 7. Клиент: состояние и API

`use-chat.ts` разделяется на хук списка чатов (`use-chat-sessions`) и хук активного чата (`use-chat` принимает `sessionId`). Идентификатор активного чата хранится в `chrome.storage.local` — восстановление при открытии панели; сами данные всегда берутся с сервера. Ответ, пришедший после переключения, привязывается к чату, из которого он был отправлен, а не к текущему активному (у каждого запроса свой `AbortController` и целевой `sessionId`).

*Альтернатива:* кэшировать историю в `chrome.storage`. Отвергнуто: два источника правды.

## Risks / Trade-offs

- [Таблицы checkpointer'а создаются библиотекой, а не нашими миграциями] → вызывать `setup()` при старте в `PostgresModule`-совместимом месте и описать в README; в тестах миграций проверять только наши таблицы.
- [Рост checkpoint-таблиц: хранится каждое состояние графа] → удаление чата чистит thread; при необходимости позже добавить политику очистки старых checkpoint'ов.
- [Рассинхрон: сообщение пользователя записано, ответ нет (падение между шагами)] → допустимо по спеке; UI показывает такой вопрос без ответа, пользователь может повторить.
- [BREAKING для `ask` с произвольным `sessionId`] → единственный потребитель — `manager-helper`, обновляется в этом же change.
- [Ответ приходит после переключения чата] → цель записи определяется `sessionId` запроса; интерфейс не пишет ответ в активный чат автоматически.
- [Расхождение версий `@langchain/langgraph` и пакета checkpointer'а] → зафиксировать совместимую версию при установке.

## Migration Plan

1. Добавить миграцию `012_chat_sessions.sql` (таблицы и индексы); применяется автоматически при старте.
2. Установить `@langchain/langgraph-checkpoint-postgres`, подключить `PostgresSaver`, вызвать `setup()`.
3. Выкатить бэкенд, затем обновлённое расширение (старое расширение с клиентским `sessionId` получит 404 — ожидаемо).
4. Откат: вернуть предыдущую версию бэкенда и расширения; новые таблицы безвредны и могут остаться. Данные старых диалогов не мигрируются — они хранились только в памяти.
