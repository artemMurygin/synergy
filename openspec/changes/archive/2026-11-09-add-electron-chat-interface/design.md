## Context

Мотивация и объём — в `proposal.md`. Здесь только техническое состояние и ограничения.

**`control-center`** — Electron + electron-vite, React 19, Tailwind 4, shadcn-компоненты, `zustand`, `@tanstack/react-query`, `zod`. Окно создаётся с `sandbox: true`, `contextIsolation: true`. Preload экспортирует только `platform`. В renderer одна демо-таблица с mock-данными. CSP в `index.html`: `default-src 'self'`, то есть любые сетевые запросы из renderer сейчас запрещены.

**Backend `sheets-qa`** (NestJS) отдаёт:
- `/threads` — список, создание, `GET :id/messages`, `PATCH :id`, `DELETE :id`, `POST :id/run/cancel`;
- `/agent` — запуск агента, SSE-поток событий AG-UI. Ответ 409, если в чате уже идёт запуск.

CORS на backend не включён (`main.ts` без `enableCors`). Авторизации нет; её добавит отдельный change.

**`manager-helper`** — готовый референс: `@ag-ui/client` (`HttpAgent`), `@assistant-ui/react` и `@assistant-ui/react-ag-ui`, клиент `threads-api.ts`, хуки списка чатов и статуса запуска. Работает из расширения Chrome, где CORS обходится через `host_permissions`, поэтому в Electron этот приём не переносится.

Контракт API зафиксирован в спеках `chat-sessions` и `agent-streaming-protocol`; поведение UI — в `chat-thread-ui` и `chat-session-switcher`. Новый клиент реализует то же поведение, API не меняется.

## Goals / Non-Goals

**Goals:**
- Рабочий чат и список чатов в `control-center` на существующем API без правок backend.
- Транспортный слой, к которому в следующем заходе добавится авторизация (JWT) без переписывания UI.
- Структура feature-модулей, на которую лягут следующие экраны приложения.

**Non-Goals:**
- Общий пакет с `manager-helper` (выносить код в shared-библиотеку сейчас рано, он разный по среде и стилю; дублирование ограничиваем копированием контракта, а не логики).
- Экран настроек для адреса backend, офлайн-режим, кэш истории на диске.
- Отображение вызовов инструментов агента (`ToolCallGroup`), быстрый подбор (`QuickSearchForm`) — остаются только в расширении.

## Decisions

### 1. Доступ к backend через кастомный протокол `cc-api://`, проксируемый main-процессом

Main-процесс регистрирует схему `cc-api` (`protocol.registerSchemesAsPrivileged` с `supportFetchAPI`, `stream`, `corsEnabled`) и обрабатывает её через `protocol.handle`, пересылая запрос в backend с помощью `net.fetch`. Renderer ходит на `cc-api://backend/threads` обычным `fetch`, а `HttpAgent` получает `url: 'cc-api://backend/agent'`. Адрес backend читается в main из переменной окружения `CC_BACKEND_URL` (по умолчанию `http://localhost:3000`) и в renderer не попадает.

Почему так:
- CORS не возникает ни в dev (`http://localhost:5173`), ни в production (`file://` с `Origin: null`), backend не трогаем.
- SSE-поток проходит как обычный `Response.body`, поэтому `HttpAgent` и `assistant-ui` работают без адаптеров.
- Точка для авторизации: в следующем заходе main добавит заголовок `Authorization`, токен не будет доступен в renderer (важно для безопасности с `sandbox: true`).
- Сужается CSP: `connect-src cc-api:` вместо произвольных адресов.

Альтернативы:
- *`app.enableCors()` на backend.* Проще, но меняет backend, требует allowlist origin'ов и не решает случай `file://` без хаков; токены оставались бы в renderer.
- *IPC (`ipcMain.handle`) вместо протокола.* Потоковую передачу SSE пришлось бы реализовывать вручную через события, и `HttpAgent` пришлось бы заменять собственным агентом.
- *Подмена заголовков через `session.webRequest.onHeadersReceived`.* Обходит CORS, но не даёт точки для авторизации и держит backend-адрес в renderer.
- *Отключить `webSecurity`.* Небезопасно, отвергнуто.

### 2. Клиент чата: те же библиотеки, что в `manager-helper`

Используем `@ag-ui/client` (`HttpAgent`), `@assistant-ui/react` и `@assistant-ui/react-ag-ui` с теми же версиями, что в `manager-helper` (1.0.4 / 0.15.32 / 0.1.1). Они уже решают потоковое отображение, остановку и восстановление истории, а поведение уже описано в спеках.

Альтернатива — собственный хук поверх SSE: больше кода и риск расхождения с протоколом AG-UI; выигрыша по размеру нет, потому что UI-примитивы всё равно нужны. Отвергнуто.

Версии фиксируем без `^`, как в `manager-helper`, потому что пара `assistant-ui` / `react-ag-ui` чувствительна к совместимости.

### 3. Состояние: серверное — в TanStack Query, UI — в zustand

- Список чатов, создание, переименование, удаление: `useQuery` / `useMutation` с инвалидацией ключа `['threads']`. Загрузка, ошибка и «Повторить» берутся из состояния запроса.
- Активный чат (`activeThreadId`) — в zustand-сторе `chat.store`. Последний активный чат запоминается в `localStorage` и восстанавливается при запуске, если он ещё есть в списке; иначе открывается пустое состояние.
- История и стрим ответа ведёт runtime `assistant-ui`, а не Query: история загружается один раз при открытии чата.

Альтернатива — держать всё в zustand: пришлось бы вручную писать кэш, статусы загрузки и ретраи, которые Query даёт готовыми.

### 4. Контракт с backend описываем zod-схемами в renderer

Ответы `/threads` разбираются через `zod` на границе клиента (по аналогии с `features/items/schema.ts`). Ошибки сети, 404 и 409 приводятся к типизированным ошибкам клиента (`ThreadNotFoundError`, `RunConflictError`), чтобы UI показывал понятные сообщения, а не сырые коды.

Альтернатива — переносить `parseThread` из `manager-helper` как есть: он написан вручную без `zod` и расходится с принятым в `control-center` подходом.

### 5. Структура и раскладка экрана

Двухколоночный экран: слева список чатов (фиксированная ширина, прокрутка), справа выбранный чат. Код делится на feature-модули `features/chat` (runtime, thread, composer) и `features/chat-list` (запросы, список, элемент, диалог удаления) и общий `lib/backend` (клиент `/threads` и `/agent`). Детальная раскладка по слоям — в `architecture.md`, визуальные решения — в `ui-design.md`.

### 6. Переименование и удаление

- Переименование — инлайн в элементе списка: Enter сохраняет, Esc отменяет; пустое название и название длиннее 120 символов блокируются на клиенте (так же проверяет backend).
- Удаление — подтверждение встроено в строку списка (как в `manager-helper`, см. `ui-design.md`), без модального окна. Если удаляется активный чат, интерфейс переключается на следующий в списке или на пустое состояние. Если в чате идёт ответ, текст подтверждения предупреждает об этом; поведение сервера в этом случае определено спекой `chat-sessions` («Удаление во время ответа»), клиент ему следует.

### 7. Адрес backend

Единственный источник — `CC_BACKEND_URL` в main-процессе. Экрана настроек нет (Non-Goal); в dev значение задаётся через `.env`, для сборки — переменной окружения при запуске.

## Risks / Trade-offs

- **[`net.fetch` в `protocol.handle` не пробрасывает тело POST или рвёт стрим]** → первой задачей делаем спайк «POST `/agent` через `cc-api://` отдаёт SSE по частям»; для тела запроса используем `duplex: 'half'`. Если стрим буферизуется, запасной вариант — IPC-транспорт (решение 1, альтернатива).
- **[Кастомная схема меняет CSP и поведение dev-режима]** → явно добавить `connect-src cc-api:` в CSP и проверить в `electron-vite dev` и в сборке.
- **[Расхождение версий `@ag-ui/*` и `@assistant-ui/*` с backend и `manager-helper`]** → фиксированные версии без `^`; при обновлении менять синхронно в обоих клиентах.
- **[Дублирование клиента `threads-api` между расширением и десктопом]** → осознанно: общий пакет добавит инфраструктуру ради двух потребителей; пересмотреть, когда появится третий.
- **[Backend недоступен на старте]** → список показывает ошибку с «Повторить», чат не блокирует остальное приложение; адрес из `CC_BACKEND_URL` указывается в тексте ошибки.
- **[Отсутствие авторизации]** → backend сейчас открыт, но приложение — внутреннее; авторизация идёт вторым заходом, точка расширения заложена в решении 1.
- **Spike result (группа 2):** проверено в реальном Electron 45 (скрытый `BrowserWindow`, страница `file://`) на локальном mock-сервере (реальный backend `sheets-qa` не поднимался: требует Postgres/MSSQL/Redis и LLM). `protocol.handle('cc-api')` + `net.fetch(..., { duplex: 'half', bypassCustomProtocolHandlers: true })` при схеме с `standard/secure/supportFetchAPI/stream/corsEnabled`: тело POST доходит (echo с `content-type`), `GET /threads` отдаёт JSON, SSE приходит по частям (первый чанк ~3 мс, далее каждые ~400 мс, не одним куском в конце). Решение 1 подтверждено, запасной IPC-транспорт не нужен. Не проверено: реальный backend и dev-сервер с CSP.

## Migration Plan

Миграции данных нет: backend не меняется, клиент новый. Откат — удалить feature-модули и схему `cc-api`; демо-таблица остаётся доступной до замены экраном чата в рамках этого change.
