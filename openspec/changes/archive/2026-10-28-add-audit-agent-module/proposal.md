## Why

Менеджеры по продажам высшего образования заполняют сделки в CRM неполно: нет телефона, программы, формы обучения, источника. Из-за этого страдают воронка и отчётность. Сейчас проверки нет. Нужен автоматический аудит, который находит такие сделки и сообщает ответственному сотруднику, пока лид не потерян.

## What Changes

- Новый модуль `audit-agent` в `audit-agent/src/modules/audit-agent/`, построенный по целевой архитектуре проекта (domain / application / infrastructure / interface).
- **BullMQ Job Scheduler** (`upsertJobScheduler`) периодически ставит в очередь повторяющуюся задачу синхронизации. Ретраи, backoff и распределение между инстансами обеспечивает BullMQ, отдельный cron не нужен. Обработчик синхронизации запрашивает у CRM сделки, обновлённые с прошлого запуска, и ставит в очередь `audit` по одной задаче на сделку (в задаче только `dealId`). Курсор «обновлено с» хранится в Redis (отдельный ключ) и сдвигается только после успешной постановки всех задач, так что ретрай повторяет окно без потерь.
- **Обработчик очереди** `audit` (с настроенными ретраями и backoff) получает полную карточку сделки из CRM и передаёт её AI-агенту для проверки заполненности обязательных полей.
- **Обязательные поля:** ФИО клиента, телефон, образовательная программа, форма обучения, источник лида, этап воронки.
- **AI-агент** работает как tool-calling агент: проверяет поля и возвращает структурированный результат (список незаполненных или некорректных полей с пояснением).
- **Очередь `notification` и tool агента.** Модель получает инструмент `notify_responsible(username, message)`, который просто добавляет задание в очередь уведомлений. Отправку в Telegram выполняет отдельный обработчик очереди `notification` со своими ретраями. Юзернейм ответственного модель получает вторым инструментом `getUserTelegramAccountById(id)`, который по `responsibleId` из сделки CRM находит Telegram username сотрудника в таблице Postgres.
- **Postgres:** новая таблица сотрудников (`responsibleId` из CRM, ФИО, Telegram username и chat id) и таблица результатов аудита (сделка, вердикт, найденные нарушения, время). Миграции входят в change.
- **Мок CRM** за портом `CrmGatewayPort`: возвращает правдоподобные сделки вуза, часть из них с намеренно пропущенными полями. Доступа к реальной CRM нет. Реальный адаптер можно подставить позже без изменения домена.
- Метрики и логирование идут по существующим соглашениям проекта (PinoLogger, метрики BullMQ).

## Capabilities

### New Capabilities
- `deal-sync`: периодическое получение обновлённых сделок из CRM через BullMQ Job Scheduler и постановка задач аудита в очередь, включая курсор «обновлено с» в Redis, идемпотентность (jobId = dealId) и ретраи средствами BullMQ.
- `deal-audit`: получение полной сделки, проверка обязательных полей AI-агентом и сохранение результата аудита.
- `employee-notification`: очередь уведомлений, определение ответственного по `responsibleId` и доставка ему уведомления об ошибках в Telegram с ретраями, включая случай «сотрудник не найден».
- `crm-gateway`: контракт доступа к CRM (список обновлённых сделок, сделка по id) и его мок-реализация.

## Impact

- **Код:** новый модуль `audit-agent/src/modules/audit-agent/`, подключение в `app.module.ts`. Старые удалённые файлы модуля не восстанавливаются.
- **БД:** две новые таблицы и миграции в слое `database`.
- **Инфраструктура:** BullMQ (Redis, три очереди: `deal-sync`, `audit`, `notification`), Job Schedulers BullMQ вместо cron (`@nestjs/schedule` не используется), LangChain v1 (`createAgent`; добавляется пакет `langchain`) с `@langchain/openai`, Telegram Bot API.
- **Конфигурация:** новые переменные в `.env.example`: интервал и политика ретраев планировщика BullMQ, токен Telegram-бота, ключ LLM.
- **Внешние системы:** реальная CRM не затрагивается, используется мок.
- **Вне объёма:** UI, реальный адаптер CRM, эскалация и повторные напоминания.
