## Context

Мотивацию и объём см. в `proposal.md`, требования в `specs/`.

Текущее состояние `audit-agent` (NestJS 12, BullMQ 6, Prisma 7, в зависимостях `@langchain/core`, `@langchain/langgraph`, `@langchain/openai`, `zod` 4; пакета `langchain` пока нет):
- `src/modules/` пуст: прежняя реализация модуля удалена, пишем с нуля.
- Есть `src/shared` (config, logger, metrics, errors, ddd, context, health, http) и `src/database/postgres` (`migrator.ts`, `postgres.module.ts`). Миграции Postgres лежат как SQL в `db/migrations/`.
- Redis, OpenAI и метрики BullMQ уже сконфигурированы в `.env.example` и shared-слоях.
- Реальной CRM нет, Telegram-бота в проекте пока нет.

## Goals / Non-Goals

**Goals:**
- Модуль `audit-agent` разделён на domain / application / infrastructure / interface; домен не зависит от NestJS, BullMQ, LangChain, pg и Telegram.
- Внешние системы (CRM, LLM, Telegram, хранилище курсора) спрятаны за портами, адаптеры заменяемы.
- Все периодические запуски и ретраи делегированы BullMQ.

**Non-Goals:**
- Реальный адаптер CRM, UI, админка справочника сотрудников (наполнение таблицы вручную или SQL).
- Эскалации, напоминания, дашборд нарушений.
- Эскалация недоставленных уведомлений другому каналу.

## Decisions

### 1. Три очереди BullMQ: `deal-sync`, `audit`, `notification`
Синхронизация, аудит (LLM) и доставка (Telegram) имеют разные профили нагрузки и политики ретраев. Отдельные очереди дают независимые concurrency, backoff и метрики.
*Альтернатива:* одна очередь с разными именами задач. Отвергнута: общий лимит concurrency и смешанные метрики.

### 2. Планировщик через `Queue.upsertJobScheduler`
Планировщик регистрируется при старте приложения идемпотентно (`upsert`), поэтому повторный старт или несколько инстансов не плодят расписания. Интервал задаётся env-переменной (`every`), у шаблона задачи свои `attempts` и экспоненциальный `backoff`.
*Альтернатива:* `@nestjs/schedule` cron. Отвергнута по требованию: BullMQ уже даёт распределённость и ретраи.

### 3. Курсор синхронизации в Redis
Отдельный ключ (например `audit-agent:deal-sync:cursor`) на том же подключении ioredis, за портом `SyncCursorRepositoryPort`. Читается в начале запуска, записывается после успешной постановки всех задач. Окно по умолчанию, если ключа нет, задаётся env (`DEAL_SYNC_DEFAULT_WINDOW_MINUTES`). В качестве нового значения берётся время начала запуска, а не конца, чтобы не потерять сделки, обновлённые во время синхронизации.
*Альтернатива:* таблица в Postgres. Отвергнута по решению пользователя; цена: при сбросе Redis берётся окно по умолчанию.

### 4. Идемпотентность через `jobId = dealId`
Задача аудита ставится с `jobId = audit:<dealId>`: пока задача ожидает или выполняется, дубликат игнорируется BullMQ. Для защиты от повторной проверки уже завершённых сделок `removeOnComplete` задаётся с коротким возрастом хранения. Повторный аудит после реального обновления допустим.
*Риск см. ниже.*

### 5. Уведомление: два tool агента и очередь `notification`
Агент (`createAgent` из пакета `langchain` v1, замена устаревшего `createReactAgent` из `@langchain/langgraph/prebuilts`) получает два инструмента, объявленных через `tool()` из `langchain` со zod-схемами:
- **`getUserTelegramAccountById({ id })`** — принимает `responsibleId` из сделки, через порт `EmployeeRepositoryPort` ищет активного сотрудника в таблице `employee` и возвращает его `telegram_username`; если не найден — текст «сотрудник не найден».
- **`notify_responsible({ username, message })`** — просто добавляет в очередь `notification` задание `{ username, message }` и возвращает `queued`.
Системный промпт задаёт порядок: при нарушениях сначала `getUserTelegramAccountById`, затем `notify_responsible`; если сотрудник не найден — уведомление не создавать. Никакой дополнительной защиты и дедупликации нет — по решению пользователя логика держится простой.
`NotificationProcessor` берёт задание, находит активного сотрудника по `telegram_username` (Bot API не умеет писать пользователю по username, нужен chat id) и отправляет `message` через порт `NotifierPort`. Ретраи Telegram живут на очереди `notification`, LLM-аудит из-за них не перезапускается.
*Альтернатива:* подставлять username в промпт до запуска агента. Отвергнута по решению пользователя: поиск выполняется инструментом.
*Альтернатива:* отправка внутри tool или в use case после агента. Отвергнута: сбой Telegram не должен ломать вызов LLM.

### 6. Различие временных и постоянных ошибок
Временные (CRM недоступна, таймаут LLM, 5xx Telegram) пробрасываются из обработчика, и BullMQ повторяет задачу; Telegram вызывается только из `NotificationProcessor`, поэтому его ошибки повторяются на очереди `notification`, а не в аудите. Постоянные (сделка не найдена в аудите; username не найден, чат Telegram недоступен в доставке) логируются и завершаются `UnrecoverableError`, без трат ретраев. Классификация ошибок живёт в портах и адаптерах.

### 7. AI-агент
Агент создаётся через `createAgent` (пакет `langchain` v1) на модели `ChatOpenAI` из `OPENAI_MODEL`. У него два инструмента из решения 5 и системный промпт с правилами проверки.
- **Что делает.** Вся проверка выполняется только моделью, без отдельной проверки кодом: она смотрит на поля сделки и решает, какие пустые или заполнены бессмысленно (например, «телефон» без цифр).
- **Что возвращает.** Структурированный ответ `verdict` + `issues[] { field, reason }`. Формат задан через `responseFormat: toolStrategy(...)`, результат берём из `result.structuredResponse`.
- **Ошибки инструментов** не глотаем: если упала БД или Redis, задача аудита повторится средствами BullMQ.
- **Данные сделки** передаём в промпт как данные, а не как инструкции.
*Отвергнуто:* `createReactAgent` (устарел), свой `StateGraph` (избыточно), предпроверка пустых полей кодом (не нужна по решению пользователя), любые дополнительные инструменты сверх двух из решения 5.

### 8. Данные Postgres
Две таблицы в `db/migrations/` (SQL, как существующий `001_audit_run.sql`), доступ через существующий `postgres.module`:
- `employee(id, crm_responsible_id UNIQUE, full_name, telegram_username UNIQUE, telegram_chat_id, is_active, created_at)`
- `deal_audit(id, deal_id, deal_updated_at, verdict, issues JSONB, audited_at)`, индекс по `deal_id`, уникальность по `(deal_id, deal_updated_at)`.

Уникальность по `(deal_id, deal_updated_at)` делает повтор той же версии сделки идемпотентным на уровне БД: если результат для версии уже есть, повторная проверка и уведомление не выполняются.

### 9. Telegram через Bot API по HTTP
Тонкий адаптер порта `NotifierPort` (его вызывает `NotificationProcessor`) над `fetch`/HTTP-клиентом проекта, без тяжёлых библиотек. Токен из env. Ответы Telegram классифицируются по решению 6.

### 10. Мок CRM
`MockCrmGateway` — адаптер порта `CrmGatewayPort` с in-memory набором сделок (~10 штук: полные и с разными пропусками, несколько `responsibleId`, включая отсутствующего в справочнике). Выбор мока/реального адаптера по env `CRM_DRIVER=mock`. Для демонстрации сидируется несколько сотрудников в справочник.

### 11. Структура модуля
```
modules/audit-agent/
  domain/          Deal, AuditResult, Employee, порты (CrmGatewayPort, DealAuditorPort,
                   NotifierPort, EmployeeRepositoryPort, DealAuditRepositoryPort,
                   SyncCursorRepositoryPort, AuditQueuePort, NotificationQueuePort)
  application/     SyncDealsUseCase, AuditDealUseCase, DeliverNotificationUseCase
  infrastructure/  crm/ (mock), agent/ (langchain), persistence/ (postgres),
                   telegram/, redis/ (cursor), queue/ (bullmq: scheduler, очереди)
  interface/       queue processors: DealSync, Audit, Notification (входные адаптеры)
```
Детали по слоям и зависимостям вынесены в `architecture.md`.

## Risks / Trade-offs

- [Сброс Redis теряет курсор] → окно по умолчанию с запасом; идемпотентность `(deal_id, deal_updated_at)` в БД не даёт задублировать результат и уведомление.
- [`jobId` дедуплицирует только пока задача в Redis] → дубль аудита после `removeOnComplete` отсекается уникальностью в БД до вызова LLM: перед проверкой агентом смотрим, есть ли результат для этой версии сделки.
- [Стоимость и латентность LLM] → ограниченная concurrency очереди, таймаут вызова. Модель проверяет все поля сама, поэтому возможны пропуски; принимаем осознанно.
- [Новая зависимость `langchain` v1 и совместимость версий с `@langchain/core` 1.x] → добавить `langchain` с версией, согласованной с `@langchain/core`, и проверить сборку и типы на первом шаге задач; API сверен с актуальной документацией LangChain v1.
- [Нестабильный вывод LLM] → структурированная схема, повтор при невалидном ответе, ограниченный лимит попыток.
- [Telegram недоступен долго] → задание ретраится очередью `notification`; после исчерпания попыток сбой в логах и метриках, аудит не затронут.
- [Модель может не вызвать инструмент или указать неверный username] → принимаем осознанно ради простоты; неверный username отсекается обработчиком (сотрудник не найден, предупреждение в логах).
- [Мок расходится с реальной CRM] → контракт зафиксирован в spec `crm-gateway`, реальный адаптер подставляется без изменений домена.

## Migration Plan

1. Применить SQL-миграции (`employee`, `deal_audit`) существующим мигратором.
2. Добавить зависимость `langchain` (v1) в `package.json`; `@langchain/langgraph` остаётся как транзитивная.
3. Добавить переменные в `.env.example` (интервал планировщика, окно по умолчанию, `CRM_DRIVER`, `TELEGRAM_BOT_TOKEN`).
4. Наполнить `employee` (сид для мока).
5. Развернуть приложение. Планировщик регистрируется сам при старте.

Откат: убрать модуль из `app.module.ts`; планировщик удалить через `removeJobScheduler`, ключ курсора и таблицы можно оставить без вреда.
