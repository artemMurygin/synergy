## MODIFIED Requirements

### Requirement: Подача идеи
Система SHALL позволять любому вошедшему сотруднику подать заявку со следующими полями:
- название (обязательное, непустое после удаления пробелов по краям, не длиннее установленного предела);
- описание процесса (обязательное, непустое);
- частота: целое число раз больше нуля и период `day`, `week` или `month`;
- минут за один раз: целое число больше нуля;
- сколько человек так делают: целое число больше нуля.

Заявка MUST создаваться в статусе `new`, без взявшего разработчика и без оценки, и принадлежать подавшему её пользователю. Автор MUST определяться по access-токену, а не по данным запроса. Недопустимые значения MUST отвечаться 400 без создания заявки.

#### Scenario: Успешная подача
- **WHEN** сотрудник подаёт заявку «Сверка актов» с описанием, частотой 5 раз в неделю, 20 минут за раз, 3 человека
- **THEN** система отвечает 201, заявка создана в статусе `new` и принадлежит сотруднику

#### Scenario: Пустое название
- **WHEN** сотрудник подаёт заявку, у которой название состоит из пробелов
- **THEN** система отвечает 400 и заявка не создаётся

#### Scenario: Недопустимые числа
- **WHEN** сотрудник передаёт нулевое или отрицательное значение частоты, минут или числа людей, либо дробное число, либо неизвестный период
- **THEN** система отвечает 400 и заявка не создаётся

#### Scenario: Запрос без токена
- **WHEN** клиент подаёт заявку без access-токена
- **THEN** система отвечает 401

### Requirement: Мои заявки
Система SHALL возвращать по запросу сотрудника список его собственных заявок, новые первыми, с пагинацией (`limit`, `page`, как в остальных списках API) и общим числом записей. Каждая заявка MUST содержать поля анкеты, статус для автора, время создания, взявшего разработчика (идентификатор, логин и полное имя по правилам `employee-directory`, пусто для заявки в статусе `new`) и время взятия, а для принятой заявки — оценку трудозатрат в часах. Заявки других пользователей MUST NOT попадать в ответ. Запрос чужой заявки по идентификатору MUST отвечаться 404.

#### Scenario: Список своих заявок
- **WHEN** у сотрудника 3 заявки, у другого сотрудника 2, и первый запрашивает список
- **THEN** ответ содержит только его 3 заявки, новые первыми, и общее число 3

#### Scenario: Чужая заявка по идентификатору
- **WHEN** сотрудник запрашивает заявку другого сотрудника
- **THEN** система отвечает 404

#### Scenario: Недопустимые параметры
- **WHEN** клиент передаёт `limit` больше максимального или нечисловую страницу
- **THEN** система отвечает 400

#### Scenario: Заявка в работе
- **WHEN** разработчик «Петров Пётр» взял заявку сотрудника в работу
- **THEN** в списке у заявки статус «На рассмотрении», взявший — «Петров Пётр» и время взятия

#### Scenario: Оценка у принятой заявки
- **WHEN** заявку приняли с оценкой 16 часов
- **THEN** автор видит у заявки оценку 16 часов

### Requirement: Статус заявки для автора
Система SHALL определять статус заявки для автора так:
- заявка в статусе `new` — «Новая»;
- заявка в статусе `under_review` — «На рассмотрении»;
- отклонённая заявка — «Отклонена»;
- принятая заявка берёт статус привязанного навыка: `planned` — «Запланировано», `in_dev` — «В разработке», `testing` — «Тестируется», `launched` — «Запущено», `rework` — «Доработка».

Статус принятой заявки MUST выводиться из текущего статуса навыка в момент чтения и MUST NOT храниться отдельной копией. Для отклонённой заявки автору MUST быть видна причина отказа. Для принятой заявки автору MUST быть видны название и описание привязанного навыка. Если привязанный навык или его агент в архиве, автор MUST продолжать видеть последний статус навыка, его название и описание.

#### Scenario: Новая заявка
- **WHEN** сотрудник открывает только что поданную заявку
- **THEN** статус «Новая»

#### Scenario: Заявка взята в работу
- **WHEN** разработчик взял заявку в работу
- **THEN** автор видит статус «На рассмотрении»

#### Scenario: Отклонённая заявка
- **WHEN** разработчик отклонил заявку с причиной «Уже есть в поставке»
- **THEN** автор видит статус «Отклонена» и причину

#### Scenario: Статус следует за навыком
- **WHEN** принятая заявка привязана к навыку, и разработчик переводит навык из `planned` в `in_dev`
- **THEN** автор без каких-либо действий над заявкой видит статус «В разработке»

#### Scenario: Доработка
- **WHEN** навык принятой заявки переходит из `launched` в `rework`
- **THEN** автор видит статус «Доработка»

#### Scenario: Навык в архиве
- **WHEN** навык принятой заявки в статусе `in_dev` архивирован
- **THEN** автор видит статус «В разработке», название и описание навыка

#### Scenario: Несколько заявок на один навык
- **WHEN** к одному навыку привязаны заявки двух авторов, и навык переходит в `launched`
- **THEN** обе заявки показывают «Запущено»

### Requirement: Очередь заявок разработчика
Система SHALL возвращать пользователю с ролью `developer` очередь заявок в статусах `new` и `under_review`, старые первыми, с пагинацией и общим числом записей. Каждая заявка в очереди MUST содержать поля анкеты, статус, автора (идентификатор, логин и полное имя по правилам `employee-directory`), время подачи, а для `under_review` — взявшего разработчика в том же виде и время взятия. Пользователю без роли `developer` система MUST отвечать 403, неавторизованному — 401. Разработчик MUST иметь возможность открыть любую заявку по идентификатору; в ней автор и взявший MUST возвращаться в том же виде.

#### Scenario: Очередь для разработчика
- **WHEN** есть 3 заявки `new`, 1 `under_review` и 2 с решением, и разработчик запрашивает очередь
- **THEN** ответ содержит 4 заявки, самая старая первой, у каждой её статус

#### Scenario: Взявший в очереди
- **WHEN** заявку взял в работу разработчик «Петров Пётр»
- **THEN** в очереди у неё статус `under_review` и взявший «Петров Пётр»

#### Scenario: Очередь для сотрудника без роли
- **WHEN** пользователь без роли `developer` запрашивает очередь
- **THEN** система отвечает 403

#### Scenario: Заявка после решения
- **WHEN** по заявке принято решение
- **THEN** она пропадает из очереди

#### Scenario: Автор с заполненным именем
- **WHEN** автор заявки — «Иванов Иван Иванович», логин `ivan`
- **THEN** в очереди автор возвращается с идентификатором, логином `ivan` и полным именем «Иванов Иван Иванович»

#### Scenario: Автор без ФИО
- **WHEN** у автора заявки не заполнены фамилия, имя и отчество
- **THEN** полное имя автора в очереди равно его логину

#### Scenario: Автор уволен
- **WHEN** автор заявки уволен
- **THEN** заявка остаётся в очереди, а автор возвращается с тем же полным именем

### Requirement: Решение «принять в навык»
Система SHALL позволять разработчику принять заявку в статусе `under_review` с обязательной оценкой трудозатрат, привязав её к навыку одним из трёх способов:
- выбрать существующий навык;
- создать новый навык (название, описание) у выбранного существующего агента;
- создать новый навык у нового агента (см. требование «Принятие с созданием агента»).

Оценка MUST быть целым числом часов больше нуля и не больше установленного предела, иначе система MUST отвечать 400 без изменений. Решение MAY вынести любой разработчик, а не только взявший заявку. Создание навыка (и агента, и продукта) и привязка заявки MUST выполняться атомарно. Привязка к несуществующему навыку или создание навыка у несуществующего агента MUST отвечаться 404. Привязка к архивному навыку, к навыку архивного агента или создание навыка у архивного агента MUST отвечаться 409, заявка остаётся в `under_review`. Принять заявку в статусе `new` MUST отвечаться 409 без изменений. Принять заявку, по которой решение уже принято, MUST отвечаться 409 без изменений. К одному навыку система MUST разрешать привязывать несколько заявок, у каждой своя оценка. После принятия оценка MUST NOT меняться.

#### Scenario: Привязка к существующему навыку
- **WHEN** разработчик принимает заявку на рассмотрении с оценкой 8 часов, выбрав существующий навык «Сводка встречи»
- **THEN** система отвечает 200, заявка привязана к этому навыку с оценкой 8 часов, а её статус для автора равен статусу навыка

#### Scenario: Создание нового навыка
- **WHEN** разработчик принимает заявку, создавая навык «Сверка актов» у агента Ассистент
- **THEN** навык создаётся в статусе `planned`, заявка привязывается к нему, автор видит «Запланировано»

#### Scenario: Решение не взявшего разработчика
- **WHEN** заявку взял в работу один разработчик, а принимает другой
- **THEN** система отвечает 200, решение записано на принявшего, взявший не меняется

#### Scenario: Без оценки
- **WHEN** разработчик принимает заявку без оценки, с нулевой, отрицательной или дробной оценкой
- **THEN** система отвечает 400, заявка остаётся на рассмотрении, навык не создаётся

#### Scenario: Заявка не взята в работу
- **WHEN** разработчик принимает заявку в статусе `new`
- **THEN** система отвечает 409, заявка и каталог не меняются

#### Scenario: Ошибка при создании навыка
- **WHEN** принятие с созданием навыка завершается ошибкой, например нет такого агента
- **THEN** ни навык, ни привязка не создаются, заявка остаётся на рассмотрении

#### Scenario: Архивный навык
- **WHEN** разработчик принимает заявку в навык, который в архиве или чей агент в архиве
- **THEN** система отвечает 409, заявка остаётся на рассмотрении

#### Scenario: Новый навык у архивного агента
- **WHEN** разработчик принимает заявку, создавая навык у агента, который в архиве
- **THEN** система отвечает 409, навык не создаётся, заявка остаётся на рассмотрении

#### Scenario: Повторное решение
- **WHEN** разработчик пытается принять заявку, по которой решение уже принято
- **THEN** система отвечает 409, заявка и навык не меняются

#### Scenario: Решение без роли
- **WHEN** пользователь без роли `developer` пытается принять заявку
- **THEN** система отвечает 403 и заявка не меняется

### Requirement: Решение «отклонить с причиной»
Система SHALL позволять разработчику отклонить заявку в статусе `under_review`, при этом причина MUST быть обязательной и непустой после удаления пробелов по краям. Оценка трудозатрат при отклонении MUST NOT требоваться и MUST NOT сохраняться. Решение MAY вынести любой разработчик, а не только взявший заявку. Отклонение без причины MUST отвечаться 400 без изменений. Отклонить заявку в статусе `new` MUST отвечаться 409 без изменений. Отклонить заявку, по которой решение уже принято, MUST отвечаться 409.

#### Scenario: Отклонение с причиной
- **WHEN** разработчик отклоняет заявку на рассмотрении, указав причину
- **THEN** система отвечает 200, заявка получает статус «Отклонена» с этой причиной

#### Scenario: Отклонение без причины
- **WHEN** разработчик отклоняет заявку с пустой причиной или причиной из пробелов
- **THEN** система отвечает 400, заявка остаётся на рассмотрении

#### Scenario: Отклонение новой заявки
- **WHEN** разработчик пытается отклонить заявку в статусе `new`
- **THEN** система отвечает 409, заявка остаётся в статусе `new`

#### Scenario: Отклонение принятой заявки
- **WHEN** разработчик пытается отклонить уже принятую заявку
- **THEN** система отвечает 409, заявка не меняется

### Requirement: События по заявкам в outbox
Система SHALL записывать в outbox в той же транзакции, что и изменение, событие о взятии заявки в работу, событие о принятии заявки в навык и событие об отклонении заявки. Событие MUST содержать идентификатор и название заявки, автора и разработчика, выполнившего действие. Для взятия в работу этот разработчик — взявший. Для принятия событие дополнительно MUST содержать идентификатор, название и статус навыка и оценку трудозатрат, для отклонения — причину. Принятие с созданием агента или продукта MUST записывать одно событие принятия, без отдельных событий о создании агента и продукта. При смене статуса навыка система MUST обеспечивать, чтобы по событию смены статуса навыка (см. `featurer-catalog`) можно было определить все привязанные к навыку заявки и их авторов. Отклонённое действие MUST NOT записывать события.

#### Scenario: Событие взятия в работу
- **WHEN** разработчик берёт заявку в работу
- **THEN** в outbox появляется одно событие взятия с заявкой, автором и взявшим

#### Scenario: Событие принятия
- **WHEN** разработчик принимает заявку в навык с оценкой 8 часов
- **THEN** в outbox появляется одно событие принятия с заявкой, автором, навыком и оценкой 8 часов

#### Scenario: Событие отклонения
- **WHEN** разработчик отклоняет заявку с причиной
- **THEN** в outbox появляется одно событие отклонения с причиной

#### Scenario: Принятие с новым агентом
- **WHEN** разработчик принимает заявку с созданием нового продукта, агента и навыка
- **THEN** в outbox появляется одно событие принятия и никаких других событий

#### Scenario: Отклонённое действие
- **WHEN** действие отклонено ответом 409 или 400
- **THEN** новое событие в outbox не записывается

#### Scenario: Привязанные заявки при смене статуса навыка
- **WHEN** у навыка две привязанные заявки двух авторов и его статус меняется
- **THEN** по событию смены статуса можно определить обе заявки и обоих авторов

## ADDED Requirements

### Requirement: Взятие заявки в работу
Система SHALL позволять разработчику взять заявку в статусе `new` в работу. При этом заявка переходит в `under_review`, взявшим становится этот разработчик, а время взятия — текущее время. Открытие и чтение заявки MUST NOT менять её статус. Взять заявку, которая уже в `under_review` (в том числе тем же разработчиком) или по которой решение принято, MUST отвечаться 409 без изменений. Если два разработчика одновременно берут одну заявку, успешно MUST завершаться ровно одно действие, второе получает 409. Несуществующая заявка MUST отвечаться 404, пользователь без роли `developer` — 403. Возврат заявки из `under_review` в `new` и смена взявшего MUST NOT предоставляться.

#### Scenario: Взять новую заявку
- **WHEN** разработчик берёт в работу заявку в статусе `new`
- **THEN** система отвечает 200, заявка в статусе `under_review`, взявший — этот разработчик, время взятия заполнено

#### Scenario: Открытие не меняет статус
- **WHEN** разработчик открывает заявку в статусе `new`, не беря её в работу
- **THEN** заявка остаётся в статусе `new`

#### Scenario: Заявка уже в работе
- **WHEN** разработчик берёт заявку, которую уже взял другой разработчик
- **THEN** система отвечает 409, взявший и время взятия не меняются

#### Scenario: Одновременное взятие
- **WHEN** два разработчика одновременно берут одну заявку
- **THEN** одному система отвечает 200, другому 409, взявшим записан первый

#### Scenario: Заявка с решением
- **WHEN** разработчик берёт в работу отклонённую или принятую заявку
- **THEN** система отвечает 409, заявка не меняется

#### Scenario: Без роли
- **WHEN** пользователь без роли `developer` берёт заявку в работу
- **THEN** система отвечает 403, заявка не меняется

### Requirement: Принятие с созданием агента
Система SHALL позволять разработчику при принятии заявки создать новый навык у нового агента. Для нового агента задаются название и продукты: список существующих продуктов и, при необходимости, один новый продукт с названием. Агент MUST входить хотя бы в один продукт: если не передан ни один существующий продукт и нет нового продукта, система MUST отвечать 400. Названия агента и продукта MUST быть непустыми после удаления пробелов по краям и не длиннее установленного предела. Новый продукт, новый агент со связями с продуктами, новый навык и привязка заявки MUST создаваться одной транзакцией: при любой ошибке не создаётся ничего и заявка остаётся в `under_review`. Несуществующий продукт из списка MUST отвечаться 404. Правила `slug` и уникальности названий агента и продукта — по `featurer-catalog`.

#### Scenario: Новый агент в существующем продукте
- **WHEN** разработчик принимает заявку, создавая агента «Сверщик» в продукте control-center и навык «Сверка актов»
- **THEN** создаются агент, связанный с control-center, и навык в статусе `planned`, заявка привязана к навыку

#### Scenario: Новый агент в новом продукте
- **WHEN** разработчик принимает заявку, создавая продукт «Портал бухгалтерии», агента «Сверщик» в нём и навык
- **THEN** создаются продукт, агент, связанный с ним, и навык, заявка привязана к навыку

#### Scenario: Новый агент в существующем и новом продукте
- **WHEN** разработчик выбирает продукт веб и указывает новый продукт «Портал бухгалтерии»
- **THEN** новый агент связан с обоими продуктами

#### Scenario: Агент без продуктов
- **WHEN** разработчик создаёт нового агента без существующих продуктов и без нового продукта
- **THEN** система отвечает 400, ничего не создаётся

#### Scenario: Несуществующий продукт
- **WHEN** в списке продуктов нового агента есть несуществующий идентификатор
- **THEN** система отвечает 404, ничего не создаётся

#### Scenario: Название агента занято
- **WHEN** разработчик создаёт агента «ассистент», а агент «Ассистент» уже есть
- **THEN** система отвечает 409, ничего не создаётся, заявка остаётся на рассмотрении

#### Scenario: Откат при ошибке
- **WHEN** новый продукт создан, но создание агента завершается ошибкой
- **THEN** продукт тоже не сохраняется, заявка остаётся на рассмотрении
