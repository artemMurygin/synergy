## Context

Мотивация и состав изменения: см. `proposal.md`. Требования: `specs/*/spec.md`.

Текущее состояние, которое определяет подход:

- Миграции лежат в `backend/db/migrations/` как `NNN_name.sql`, последняя — `003_deal_audit.sql`. Мигратор (`src/database/postgres/migrator.ts`) применяет файлы по порядку, каждый в транзакции, один раз, под advisory lock. Отката («down») нет.
- Существующие миграции используют `UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `TEXT` с `CHECK (... IN (...))` вместо `ENUM`, `TIMESTAMPTZ DEFAULT now()`, `JSONB` для произвольных структур.
- Postgres 17, но образ `postgres:17-alpine` не содержит pgvector.
- В `package.json` уже есть `@langchain/openai`, то есть эмбеддинги можно считать моделью OpenAI.
- Объём данных небольшой: сотни программ, тысячи предложений и цен, порядка тысяч текстовых фрагментов. Это определяет выбор индексов.
- Ограничения целостности нужны на уровне БД: данные пишет ETL, а читает агент, и ни один из них не должен полагаться на то, что другой «не ошибётся».

## Goals / Non-Goals

**Goals:**
- Набор SQL-миграций, создающих все таблицы из спеков с ограничениями, индексами и каскадами.
- Инварианты (допустимые значения, уникальность естественных ключей, неотрицательные цены, согласованность метаданных чанка) гарантируются самой БД, а не кодом.
- Схема допускает идемпотентный upsert по естественному ключу и безопасное удаление отсутствующих записей.
- Один запрос может сочетать фильтры по каталогу с векторным или полнотекстовым поиском.

**Non-Goals:**
- Репозитории, DTO и NestJS-код: это работа следующих change.
- Выбор способа парсинга листов, расписание синхронизации и вычисление эмбеддингов (`add-programs-etl-pipeline`).
- Алгоритм объединения результатов трёх видов поиска (`add-programs-selection-agent`).
- Данные: миграции создают только структуру, справочники не наполняются.
- Откат миграций: проект работает вперёд, см. Migration Plan.

## Decisions

### D1. Допустимые значения: `TEXT` + `CHECK`, а не `ENUM`
Уровни программ, формы обучения, базы, виды цен, типы разделов и валюта задаются `CHECK (col IN (...))`.

- **Почему:** так сделано в существующих миграциях. Добавить значение в `CHECK` — это обычная миграция, а `ALTER TYPE ... ADD VALUE` имеет ограничения внутри транзакции, в которой работает мигратор. Значения читаются в схеме без обращения к каталогу типов.
- **Альтернативы:** `ENUM` (отвергнут из-за ограничений транзакции и расхождения с проектом); справочные таблицы с внешним ключом (избыточно: значения фиксированы и известны коду).

Коды значений:
- уровень: `spo`, `bachelor`, `specialist`, `master`, `postgrad`, `dpo_pp`, `dpo_pk`, `short_course`, `kids`, `camp`;
- форма: `full_time` (очная), `mixed` (очно-заочная), `extramural` (заочная), `distance`, `distance_tutor`, `online`;
- база: `grade9`, `grade11`, `spo`, `vo`, `any`;
- вид цены: `first_year`, `next_year`, `total`, `installment`, `lump_sum`, `site_price`, `discounted`;
- валюта: `RUB`, `USD`, `EUR`.

### D2. Естественный ключ программы: два частичных уникальных индекса
Спек требует разный ключ для программ с кодом направления и без него. Один составной `UNIQUE` не подходит: `NULL` в колонках считается разным значением, а включение `title` в ключ для кодированных программ приведёт к дублям при изменении написания названия.

- Программы с кодом: уникальный индекс `(organization_id, level, direction_code, profile, qualification) NULLS NOT DISTINCT` с условием `direction_code IS NOT NULL`.
- Программы без кода: уникальный индекс `(organization_id, level, title)` с условием `direction_code IS NULL`.

- **Почему:** `NULLS NOT DISTINCT` (Postgres 15+) корректно трактует пустые профиль и квалификацию как одинаковые значения. Частичные индексы описывают оба правила точно.
- **Последствие для ETL:** `INSERT ... ON CONFLICT` должен указывать условие индекса (index predicate); это нужно отразить в задачах следующего change.
- **Альтернативы:** вычисляемая текстовая колонка `natural_key` (проще для `ON CONFLICT`, но ключ становится строкой с разделителями и скрывает логику); суррогатный ключ из ETL (теряет гарантию на уровне БД).

### D3. Уникальность предложений и цен: `NULLS NOT DISTINCT`
- Предложение: `(program_id, location_id, study_form, base_education, tariff) NULLS NOT DISTINCT`, так как площадка и тариф необязательны.
- Цена: `(offer_id, kind, condition) NULLS NOT DISTINCT`.
- Для вида `discounted` условие (категория: «новый клиент», «выпускники МТИ» и т. д.) обязательно: `CHECK (kind <> 'discounted' OR condition IS NOT NULL)`.

Скидочные категории МТИ хранятся как цены вида `discounted` с категорией в `condition`, а не отдельными видами цен: набор категорий меняется чаще, чем набор видов, и не требует миграции.

### D4. Метаданные чанка денормализованы, но защищены составным внешним ключом
`content_chunk` хранит `organization_id` и `level` дублями программы, чтобы фильтр по ним работал без соединения. Дубли не могут разойтись: оба поля входят в естественный ключ программы и не меняются у существующей программы (смена уровня означает другую программу).

Согласованность обеспечивает составной внешний ключ `(program_id, organization_id, level) → program(id, organization_id, level)`. Для него нужен `UNIQUE (id, organization_id, level)` на `program` (тривиально выполняется, так как `id` уникален). Каскад `ON DELETE CASCADE` сохраняется.

- **Альтернативы:** соединение с `program` при каждом поиске (корректно, но усложняет запросы и план при гибридном поиске); денормализация без ограничения (риск тихого расхождения).

### D5. Векторы: `vector(1536)`, косинусное расстояние, индекс HNSW
- Размерность 1536 соответствует модели `text-embedding-3-small`, которая уже доступна через `@langchain/openai`. Колонка допускает `NULL` (вектор ещё не рассчитан); индекс и запросы поиска игнорируют такие строки.
- Индекс: HNSW по `vector_cosine_ops`. Для нескольких тысяч фрагментов даже полный перебор быстр, но HNSW не требует обучения на данных, в отличие от IVFFlat, и не деградирует при полной перезагрузке таблицы.
- Фильтры применяются после выбора кандидатов индексом, поэтому узкий фильтр может вернуть меньше записей, чем запрошено. На текущем объёме это решается включением итеративного сканирования HNSW на стороне запроса (задача следующего change); сама схема от этого не зависит.
- **Смена модели или размерности** потребует новой миграции (изменить тип колонки, пересоздать индекс) и полного пересчёта эмбеддингов. Это сознательно принятая цена за простоту.
- **Альтернативы:** `halfvec` (экономит место, не нужно на этом объёме); модель с большей размерностью (дороже, выигрыш для русскоязычных коротких описаний не доказан); отдельная векторная БД (лишний сервис, нет транзакций с каталогом).

### D6. Хэш и сброс вектора: вычисляемая колонка + триггер
- `content_hash` объявлен как `GENERATED ALWAYS AS (md5(text)) STORED`: хэш не может расходиться с текстом.
- Триггер `BEFORE UPDATE OF text` обнуляет `embedding`, когда меняется `text`, а вектор в том же `UPDATE` не передан. Если ETL одним запросом пишет и новый текст, и новый вектор, вектор сохраняется.
- **Почему:** спек требует инвариант «изменился текст ⇒ вектор сброшен». Если оставить это ETL, любая ручная правка или другой писатель его нарушит, и в поиске окажутся векторы, не соответствующие тексту.
- **Альтернативы:** сброс в коде ETL (инвариант зависит от дисциплины писателя); сравнение хэшей в ETL без триггера (то же).

### D7. Полнотекстовый поиск: сохраняемый `tsvector` и два словаря
- На `program` и `content_chunk` добавляются сохраняемые колонки `tsvector` с GIN-индексами.
- Русский текст (название, профиль, квалификация, текст чанка) разбирается словарём `russian`, что даёт поиск по словоформам («фельдшеры» → «фельдшер»).
- Код направления (`44.02.02`) добавляется в вектор через словарь `simple`, чтобы он не разбирался как число или версия русским словарём. Одновременно на `direction_code` создаётся обычный индекс B-tree для точного совпадения и поиска по префиксу.
- Корректность токенизации кодов проверяется тестами миграции (см. задачи): это единственное место, где поведение словаря неочевидно.
- **Альтернативы:** `pg_trgm` (нечёткий поиск по опечаткам, не решает морфологию); внешний поисковый движок (лишний сервис).

### D8. Реестр источников: таблицы без внешних ключей на «сырое» наружу
- `source_sheet`: уникальность `(spreadsheet_id, sheet_id)`, поля `title`, `content_hash`, `synced_at`, `is_enabled`.
- `raw_row`: `source_sheet_id` с `ON DELETE CASCADE`, номер строки, `data JSONB`, `row_hash`; уникальность `(source_sheet_id, row_no)`.
- Ссылки `source_row_id` в `program`, `offer` и `content_chunk` ведут на `raw_row` с `ON DELETE SET NULL`, чтобы очистка сырых строк не удаляла бизнес-данные (спек `programs-source-tracking`).
- Хранение исключённых секретных колонок в `raw_row` схемой не запрещается, так как это неотслеживаемое БД свойство данных. Требование выполняет ETL (фильтрация колонок до записи); схема лишь не предоставляет для секретов специальных колонок.

### D9. Каскады и защита организаций
- Всё, что принадлежит программе (предложения, цены через предложение, вступительные требования, привязки к людям, материалы, бонусные курсы, чанки), удаляется `ON DELETE CASCADE`.
- Организация защищена `ON DELETE RESTRICT` от удаления при наличии программ.
- Бонусный курс удаляется каскадом при удалении любой из двух программ связи; запрет «подарок самому себе» — `CHECK (program_id <> bonus_program_id)`.
- Записи людей при удалении программы остаются: на них могут ссылаться другие программы.

### D10. Разбиение на миграции
Файлы подряд после `003`; зависимости между ними учтены порядком:

1. `004_programs_source_tracking.sql`: `source_sheet`, `raw_row` (нужны остальным как цель ссылок).
2. `005_programs_catalog.sql`: организации, площадки, факультеты, программы, предложения, цены, вступительные требования.
3. `006_programs_reference_data.sql`: скидки, региональные ставки, способы оплаты, группы продуктов, люди, привязки, материалы, бонусные курсы.
4. `007_programs_content_index.sql`: расширение `vector`, `content_chunk`, индексы, триггер сброса вектора.

Расширение создаётся именно в последней миграции, чтобы все остальные можно было применить и на базе без pgvector, если расширение окажется недоступно.

## Risks / Trade-offs

- **[Образ Postgres без pgvector]** `CREATE EXTENSION vector` упадёт на текущем образе → заменить образ в `docker-compose.yml` на образ с pgvector (например, `pgvector/pgvector:pg17`) и отметить требование для прода в задачах; миграция `007` проверяется на этом образе.
- **[Смена модели эмбеддингов]** размерность зашита в тип колонки → считать смену редкой операцией: новая миграция плюс полный пересчёт; зафиксировано в D5.
- **[Фильтр после HNSW]** узкие фильтры могут вернуть меньше результатов → итеративное сканирование в запросе (следующий change) и, при необходимости, обычный перебор: на текущем объёме он быстр.
- **[Токенизация кодов направления]** словарь может неожиданно разобрать `44.02.02` → отдельный словарь `simple` для кода и тесты на реальных кодах из таблиц.
- **[Жёсткие `CHECK`]** новое значение формы или вида цены в таблице потребует миграции → это желаемое поведение: неизвестное значение должно останавливать загрузку, а не молча попадать в базу.
- **[Секреты в `raw_row`]** схема не может проверить содержимое `JSONB` → ответственность ETL (фильтрация колонок), проверяется тестом ETL; зафиксировано в D8.
- **[Нет отката]** мигратор идёт только вперёд → см. Migration Plan.

## Migration Plan

1. Заменить образ Postgres на образ с pgvector в локальном окружении и убедиться, что существующие миграции `001`–`003` применяются без изменений.
2. Добавить миграции `004`–`007` в `backend/db/migrations/`. Мигратор применит их при старте приложения под advisory lock, каждую в транзакции.
3. Для прода предварительно убедиться, что расширение `vector` доступно и у пользователя миграции есть право его создать.
4. Новые таблицы не связаны с таблицами аудит-агента, поэтому существующий функционал не затрагивается и зависимостей порядка запуска нет.

**Откат:** мигратор не поддерживает «down». Так как все таблицы новые и ни на что не влияют, откат выполняется новой миграцией, удаляющей созданные объекты (`DROP TABLE ... CASCADE`, `DROP EXTENSION` при необходимости). Автоматический откат в рамках этого change не добавляется.
