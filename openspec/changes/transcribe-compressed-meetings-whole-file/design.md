## Context

См. `proposal.md` и дельту `specs/meeting-transcription/spec.md`. Сейчас `MeetingTranscriberPort` реализован `ChunkedMeetingTranscriber`: файл из S3 сохраняется во временную папку, `ffprobe` проверяет длительность, `ffmpeg` делает десятиминутные OGG-фрагменты, OpenRouter передаёт каждый в `elevenlabs/scribe-v2`, а `SpeakerRegistry` и `TranscriptMerger` склеивают ответы. Максимум записи — 4 часа и 1 ГБ; OpenRouter ограничивает размер одного загружаемого аудиофайла. Прямой Speech-to-Text API ElevenLabs принимает целый файл существенно большего размера и возвращает слова с таймкодами и `speaker_id`.

## Goals / Non-Goals

**Goals:** один вызов STT на одну попытку обработки записи; ограниченная память при загрузке и отправке; сохранение существующих сегментов, статусов и правил владения; отсутствие фрагментов записи и текста ответа в логах.

**Non-Goals:** изменение голосовых сообщений Telegram, извлечения задач из уже готового текста, HTTP API или интерфейса; автоматическая повторная расшифровка уже завершённых записей; исправление возможных ошибок самой диаризации Scribe.

## Decisions

### 1. Отдельные этапы подготовки аудио и распознавания

Сохранить внешний `MeetingTranscriberPort`, заменив его реализацию на последовательность «поток S3 → временный исходный файл → `ffprobe` → один сжатый OGG → STT → сегменты». Внутри инфраструктуры выделить порт/адаптер подготовки аудио и порт/адаптер распознавания целого файла. Так проверка формата и длительности остаётся до вызова провайдера, а прикладной `TranscribeMeetingUseCase` не узнаёт о формате multipart.

`ffmpeg` запускается один раз для всей дорожки с `-vn -ac 1 -ar 16000 -c:a libopus -b:a 32k`. Запись не режется по времени, независимо от исходного формата. После кодирования проверяются размер и корректность результата. Временная папка удаляется в `finally` при успехе, ошибке и отмене; папки упавшего процесса по-прежнему очищаются при старте.

**Альтернатива:** оставить `ChunkedMeetingTranscriber` и увеличить длину куска. Это сохраняет стыки и повторное определение спикеров, поэтому не решает проблему качества.

### 2. Прямое обращение к ElevenLabs для целого файла

Новый адаптер отправляет сжатый OGG как один multipart `file` на `POST /v1/speech-to-text` с `model_id=scribe_v2`, `diarize=true`, `timestamps_granularity=word`; ключ берётся из отдельной секретной настройки. Используется потоковая передача файла, без base64 всей записи в памяти. Синхронный ответ укладывается в существующую модель BullMQ job; таймаут HTTP и общий дедлайн job задаются отдельно и рассчитаны на максимальную запись. Ограничение размера проверяется **до** отправки; при его превышении обработка завершается, а не переключается на куски.

**Альтернативы:** OpenRouter одним запросом успешно обработал проверочную запись (53 минуты, 12,1 МБ), но его лимит размера не покрывает гарантированно 4 часа. Передача через публичный URL усложняет доступ к приватной записи. Webhook ElevenLabs потребовал бы отдельного входящего маршрута и изменения жизненного цикла job; он остаётся вариантом, если измерения максимальных записей покажут, что синхронный ответ не укладывается в дедлайн.

### 3. Преобразование ответа в существующий домен

Из ответа ElevenLabs берутся только элементы типа `word` с валидными `start`, `end`, `text` и `speaker_id`; остальные элементы не становятся речевыми сегментами. Последовательные слова одного спикера группируются в `TranscriptSegment`, а номера спикеров назначаются по первому появлению. Времена остаются относительно начала целой записи — `SpeakerRegistry`, образцы голоса и `TranscriptMerger` больше не нужны. Пустой список речевых слов даёт `no_speech`. Ошибка или невалидный ответ не превращаются в пустую успешную расшифровку.

Прямой API может не возвращать стоимость запроса. Учёт использования меняется так, чтобы известная длительность сохранялась, а неизвестная стоимость оставалась `null`, не отображалась как нулевая и не попадала в текстовые логи. Провайдерские сообщения и содержимое расшифровки не логируются.

**Альтернатива:** хранить сырой ответ ElevenLabs в БД. Это дублирует уже существующие сегменты и увеличивает объём персональных данных.

### 4. Сбои и развёртывание

Неподдерживаемый источник или сбой кодирования → `unsupported-media`; превышение длительности или предела размера целого файла → `too-long`; временные сетевые ошибки/429/5xx → существующие повторы job, затем `provider-unavailable`; общий дедлайн → `timeout`. 401/403 указывают на конфигурацию ключа в структурированном логе без его значения. Повторная попытка заново подготавливает файл из сохранённой записи; финализация расшифровки остаётся идемпотентной и атомарной с сегментами и событием.

## Risks / Trade-offs

- **Длительный синхронный запрос** → измерить время на 1–4 часах, настроить отдельный таймаут и дедлайн; если синхронный режим не выдерживает максимум, до внедрения перейти на webhook с сохранением той же семантики одного файла.
- **Повтор после сетевого обрыва может оплатить запись дважды** → не повторять постоянные ошибки, логировать попытки и длительность без текста, оценить поддержку идемпотентности API перед внедрением.
- **Дисковое место и число параллельных job** → ограничить concurrency и заранее учитывать место для исходного файла до 1 ГБ и сжатой копии на каждую job; очищать временные файлы.
- **Смена маршрута провайдера** → проверить контракт и качество прямого API на обезличенном коротком образце и на разрешённой длинной записи; мигрировать только модуль встреч.

## Migration Plan

1. Добавить конфигурацию прямого ElevenLabs API и секрет в окружение без публикации значения; подготовить таймауты и ресурсы воркера.
2. Ввести новый адаптер за `MeetingTranscriberPort`, проверить короткую, длинную, видео- и ошибочные записи. Активные job завершаются старой версией до переключения воркера.
3. Развернуть новый воркер; новые и повторно поставленные записи идут через целый сжатый файл. Готовые расшифровки и API не мигрируются.
4. При откате вернуть прежний адаптер и настройки; уже сохранённые сегменты остаются совместимыми.
