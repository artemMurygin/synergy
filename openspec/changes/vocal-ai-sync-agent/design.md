## Context

VocalAI (app.vocal-ai.ru) не имеет публичного API — только внутренний REST, используемый его фронтендом (структура эндпоинтов зафиксирована в `vocal-ai-api-research.md`). Подтверждённые в ходе исследования факты, значимые для дизайна:

- Авторизация двухшаговая: SSO Синергии (Keycloak) → обмен на короткоживущий (`expires_in` ≈ 1800 сек) JWT VocalAI.
- Найден `POST /api/auth/token/refresh` — обновление access-токена по refresh-токену без повторного логина через SSO.
- Список звонков (`POST /api/calls/project/{id}`) поддерживает два независимых диапазона дат, применяемых одновременно как AND: `startDate/endDate` (дата звонка) и `scoreStartDate/scoreEndDate` (дата оценки, дублируется как `dateFromScore/dateToScore`). Отдельного фильтра по дате переоценки в UI не обнаружено — риск описан ниже.
- Полная транскрипция доступна только через `GET /api/call/{id}?project_id=`, список — без неё.
- У внешнего API наблюдались заголовки `x-ratelimit-limit`/`x-ratelimit-remaining` (на S3-домене аудио, но не исключено и на API-домене) — нужно избегать агрессивного поллинга.

Мотивация и состав capability — см. `proposal.md`. Требования к поведению — см. `specs/vocal-ai-call-sync/spec.md` и `specs/vocal-ai-agent-tools/spec.md`.

Проект следует DDD/hexagonal-структуре `backend/src/modules/<module>/{domain,application,infrastructure,interface}` (см. `backend/CLAUDE.md`). Аналогичный по форме существующий кейс — `deal-sync` (синхронизация сделок CRM), который живёт внутри модуля `audit-agent`, а не как отдельный NestJS-модуль: `CrmGatewayPort` + `SyncCursorRepositoryPort` + `SyncDealsUseCase`, запускаемый по расписению через `queue.upsertJobScheduler`.

## Goals / Non-Goals

**Goals:**
- Воркер синхронизации, не теряющий и не дублирующий звонки при инкрементальных циклах (см. требования дедупликации в specs).
- Инструменты агента, полностью изолированные от прямых вызовов внешнего API (кроме ленивой подгрузки транскрипта).
- Схема БД, допускающая независимую фильтрацию по менеджеру/периоду/оценке/тегу/метрике без похода во внешний API.

**Non-Goals:**
- Управление списком синхронизируемых проектов через UI/БД — на старте список проектов задаётся конфигурацией (env), без admin-экрана.
- Поддержка загрузки новых звонков в VocalAI, экспорт в xlsx, CRUD метрик/тегов/вебхуков — вне этого change (см. proposal.md → Impact).
- Отдельный механизм (фильтр или периодическая сверка) для гарантированного покрытия переоценённых (`rescoredAt`) звонков — риск принят пользователем, см. Risks.

## Decisions

### Один модуль `vocal-ai`, а не два по числу capability
Capability `vocal-ai-call-sync` и `vocal-ai-agent-tools` тесно связаны (тулы читают то, что пишет синк, через общие порты и сущности) и реализуются одним NestJS-модулем `src/modules/vocal-ai/` с разделением по слоям (`infrastructure/queue` — синхронизация, `interface/agent` — тулы), а не по capability. Это соответствует существующему прецеденту: `deal-sync` и `deal-audit` — разные capability, но один модуль `audit-agent`. Альтернатива (два отдельных NestJS-модуля) добавила бы повторный DI-wiring портов без выигрыша в изоляции, так как общий код (gateway, репозитории) всё равно пришлось бы шарить через shared-библиотеку.

### Порты домена
- `VocalAiGatewayPort` — абстракция внешнего API: `login()`, `refreshToken()`, `listCalls(projectId, window)`, `getCall(callId, projectId)`. Единая точка, где учитывается single-flight refresh токена (см. ниже) и retry/backoff на 5xx/сетевые ошибки.
- `CallRepositoryPort` — persistence звонков, метрик, тегов, саммари (upsert, выборка с фильтрами, выборка для агрегатов).
- `CallTranscriptRepositoryPort` — отдельный порт для строк транскрипции (чтение/проверка наличия/запись), так как у него другой жизненный цикл (ленивая, разовая, неизменяемая запись) и другой объём данных.
- `SyncCursorRepositoryPort` — переиспользует паттерн `deal-sync`, но с курсором на уровне проекта (`projectId → lastSyncedAt`), а не глобальным.

Токены VocalAI (access/refresh) **не сохраняются в БД**: держатся в памяти процесса синхронизации (singleton-адаптер gateway), с single-flight promise на обновление, чтобы параллельные запросы, упавшие в 401 одновременно, не вызывали гонку логинов. При перезапуске процесса — чистый логин через SSO. Альтернатива (персистентный токен в таблице) отклонена: это лишний секрет в состоянии БД при том, что логин/рефреш дёшев и некритичен к редким перезапускам.

### Инкрементальная синхронизация = 2 запроса + дедупликация в use case
`SyncProjectCallsUseCase` выполняет `gateway.listCalls(projectId, {startDate, endDate})` и `gateway.listCalls(projectId, {scoreStartDate, scoreEndDate})` с одним и тем же окном (`[lastSyncedAt, now)`), объединяет результаты в `Map<callId, CallDto>` и передаёт единый набор в `CallRepositoryPort.upsertMany()` одной операцией. Это прямое соответствие подтверждённым возможностям API (см. Context) и ранее согласованному с пользователем подходу.

### Без отдельной сверки (reconciliation) для `rescoredAt`
Отдельный фильтр по дате переоценки не подтверждён (см. Context), и reconciliation-проход в этот change не включается — пользователь явно принимает риск того, что переоценка звонка (апелляция) может не попасть в инкрементальные окна по дате звонка и по дате оценки. Если это станет проблемой на практике, механизм сверки можно добавить отдельным change.

### Ленивая транскрипция — синхронный путь, не через очередь
Инструмент получения транскрипта вызывает use case напрямую (не через BullMQ): дожидается ответа внешнего API синхронно в рамках вызова тула, так как агенту нужен результат немедленно. Перед запросом use case проверяет наличие строк транскрипции в БД (`CallTranscriptRepositoryPort.exists(callId)`); при отсутствии — вызывает `gateway.getCall()`, сохраняет строки одной транзакцией. Повторный конкурентный вызов для того же звонка просто повторит запрос к внешнему API (строки транскрипции идемпотентно перезатираются, а не дублируются) — отдельная блокировка не вводится, так как цена дублирующего запроса ниже цены инфраструктуры для редкого edge-case.

### Список проектов — через конфигурацию, не БД
`VOCAL_AI_PROJECT_IDS` (список numeric id через запятую) в `env.schema.ts`. Планировщик на старте читает список и для каждого `projectId` регистрирует независимый повторяющийся job через `queue.upsertJobScheduler` (по аналогии с `DealSyncScheduler`), чтобы сбой синхронизации одного проекта не блокировал остальных (см. требование устойчивости в specs) — изоляция на уровне отдельных job, а не try/catch внутри одного цикла по всем проектам.

### Инструменты агента повторяют паттерн `task-tools.ts`
`createVocalAiTools(deps, ctx)` — функция, возвращающая объект тулов, построенных через `tool()` из `langchain` с zod-схемами аргументов, по образцу `backend/src/modules/tasks/interface/agent/task-tools.ts`. Зависимости (`deps`) — только use cases, читающие из `CallRepositoryPort`/`CallTranscriptRepositoryPort`; `VocalAiGatewayPort` в `deps` тулов фильтрации/агрегации не передаётся вообще (обеспечивает архитектурно требование изоляции из specs, а не только по соглашению).

## Risks / Trade-offs

- [Risk] Переоценка (`rescoredAt`) звонка может не попасть ни в окно по дате звонка, ни в окно по дате оценки → Mitigation: осознанно принято пользователем, механизм сверки (reconciliation) не реализуется в этом change; при необходимости добавляется отдельным change.
- [Risk] Гонка параллельного обновления токена при нескольких одновременных 401 → Mitigation: single-flight promise в `VocalAiGatewayPort`-адаптере, все параллельные вызовы ждут один и тот же in-flight refresh.
- [Risk] Внешний API ограничивает частоту запросов (наблюдались `x-ratelimit-*` заголовки) → Mitigation: пагинация с разумным `limit` (100), не увеличивать частоту синка агрессивно, backoff на 429/5xx на уровне gateway-адаптера.
- [Risk] Стартовая полная выгрузка истории большого проекта — потенциально много страниц/времени → Mitigation: это одноразовый фоновый job без требований к latency, выполняется постранично; при сбое на полпути — зафиксированный курсор позволяет доинкрементить оставшееся через обычный инкрементальный цикл, а не начинать выгрузку с нуля.
- [Risk] Персональные данные (ФИО, транскрипты, email) накапливаются в локальной БД → Mitigation: те же меры доступа к БД, что и для остальных модулей проекта (например, `meeting-transcription`); отдельных новых требований к хранению в рамках этого change не вводится, явно зафиксировано как решение, а не упущение.

## Migration Plan

1. Миграция `db/migrations/040_vocal_ai_calls.sql`: таблицы `vocal_ai_projects`, `vocal_ai_calls`, `vocal_ai_call_metric_scores`, `vocal_ai_call_tags`, `vocal_ai_call_summaries`, `vocal_ai_call_transcript_lines`. Откат — `DROP TABLE` в обратном порядке зависимостей.
2. Новые переменные окружения в `env.schema.ts` и `.env.example`: учётные данные SSO (секрет), `VOCAL_AI_PROJECT_IDS`, интервал синхронизации, параметры retry/backoff — без значений по умолчанию для секретов (обязательны к явной настройке).
3. Безопасный раскат: при пустом `VOCAL_AI_PROJECT_IDS` планировщик не регистрирует ни одного job — модуль задеплоен, но неактивен, пока проекты не сконфигурированы явно.
4. Откат функциональности без откат миграции: очистить `VOCAL_AI_PROJECT_IDS` — синхронизация останавливается, данные в таблицах остаются нетронутыми для последующего анализа/дебага.
