## Purpose

Клиентская часть авторизации в Electron-приложении control-center: вход, безопасное хранение токенов, автоматическое обновление, восстановление сессии при запуске, обязательная смена временного пароля и выход. Поведение повторяет расширение manager-helper (`auth-session`), но refresh-токен хранится приложением, а не cookie.

## ADDED Requirements

### Requirement: Экран входа
Приложение SHALL показывать экран входа с полями логина и пароля, если нет действующей сессии. Чаты и остальной интерфейс MUST быть недоступны до входа.

#### Scenario: Первый запуск
- **WHEN** пользователь запускает приложение без сохранённой сессии
- **THEN** показывается экран входа, список чатов и окно диалога недоступны

#### Scenario: Ошибка входа
- **WHEN** пользователь вводит неверные данные
- **THEN** приложение показывает сообщение об ошибке и остаётся на экране входа

#### Scenario: Превышен лимит попыток
- **WHEN** сервер отвечает 429
- **THEN** приложение показывает, через сколько можно повторить попытку, и блокирует отправку формы на это время

### Requirement: Вход как desktop-клиент
Приложение SHALL выполнять запросы `login`, `refresh`, `logout` и `change-password` с заявленным типом клиента `desktop`, получать refresh-токен из тела ответа и передавать его в теле запроса. Приложение MUST не использовать cookie для авторизации.

#### Scenario: Успешный вход
- **WHEN** пользователь вводит верные логин и пароль
- **THEN** приложение получает пару токенов, открывает рабочий интерфейс, и ни один запрос не зависит от cookie

### Requirement: Хранение токенов
Приложение SHALL хранить access-токен только в памяти и MUST не записывать его на диск. Refresh-токен SHALL сохраняться на диске только в зашифрованном средствами операционной системы виде. Если шифрование ОС недоступно, приложение MUST не сохранять refresh-токен на диск и сообщать пользователю, что вход будет требоваться при каждом запуске. Интерфейсная часть приложения (renderer) MUST не иметь доступа ни к access-, ни к refresh-токену.

#### Scenario: Перезапуск приложения
- **WHEN** приложение закрывается и запускается снова
- **THEN** access-токена в памяти нет, а refresh-токен читается из защищённого хранилища

#### Scenario: Шифрование недоступно
- **WHEN** операционная система не предоставляет шифрование для хранилища
- **THEN** refresh-токен остаётся только в памяти, а после перезапуска показывается экран входа

#### Scenario: Доступ из renderer
- **WHEN** код интерфейса пытается получить токен или передать собственный заголовок `Authorization` или `Cookie`
- **THEN** токен ему не отдаётся, а переданные им заголовки авторизации отбрасываются

### Requirement: Авторизация запросов к бэкенду
Приложение SHALL добавлять заголовок `Authorization: Bearer <access>` ко всем запросам к защищённым эндпоинтам бэкенда (чаты и агент, включая потоковые ответы). Запросы к `login`, `refresh` и `logout` MUST отправляться без этого заголовка.

#### Scenario: Запрос с токеном
- **WHEN** интерфейс запрашивает список чатов, пока сессия действует
- **THEN** запрос уходит с заголовком `Authorization: Bearer <access>`

#### Scenario: Потоковый ответ агента
- **WHEN** пользователь задаёт вопрос агенту
- **THEN** запрос к агенту авторизован, а ответ приходит потоком без буферизации

### Requirement: Автоматическое обновление токена
Приложение SHALL при ответе 401 «токен истёк» один раз обновить сессию и повторить исходный запрос. Параллельные запросы, получившие 401, MUST дожидаться одного общего обновления. Если сервер отвечает 409 `REFRESH_RACE`, приложение SHALL повторить обновление не более одного раза. Повтор запроса, в том числе запроса к агенту, MUST не приводить к двойному выполнению действия: повторяется только запрос, отклонённый сервером по авторизации.

#### Scenario: Обновление при 401
- **WHEN** запрос получает 401 «токен истёк», а сессия действительна
- **THEN** приложение обновляет токены и повторяет запрос, пользователь не видит ошибки

#### Scenario: Несколько запросов одновременно
- **WHEN** три запроса одновременно получают 401 «токен истёк»
- **THEN** выполняется ровно один запрос обновления, и все три запроса повторяются с новым токеном

#### Scenario: Обновление невозможно
- **WHEN** сервер отвечает 401 на обновление
- **THEN** приложение стирает токены из памяти и хранилища и показывает экран входа

### Requirement: Восстановление сессии при запуске
Приложение SHALL при запуске пытаться восстановить сессию по сохранённому refresh-токену без ввода пароля и показывать экран входа только если токена нет или сервер отклонил его ответом 401. Если сервер недоступен, приложение MUST не показывать экран входа и не стирать сохранённый токен.

#### Scenario: Успешное восстановление
- **WHEN** пользователь запускает приложение, а сохранённый refresh-токен действителен
- **THEN** приложение открывается в рабочем состоянии без экрана входа

#### Scenario: Токен отозван
- **WHEN** при восстановлении сессии сервер отвечает 401
- **THEN** сохранённый токен стирается, показывается экран входа

#### Scenario: Сервер недоступен
- **WHEN** при восстановлении сессии нет связи с сервером
- **THEN** приложение показывает ошибку подключения с возможностью повторить, не показывая экран входа, а сохранённый токен остаётся

### Requirement: Обязательная смена временного пароля
Приложение SHALL после входа с `mustChangePassword = true`, а также при ответе 403 `PASSWORD_CHANGE_REQUIRED`, показывать окно смены пароля, которое нельзя закрыть без смены или выхода. В окне пользователь вводит текущий пароль, новый пароль и его подтверждение. Приложение MUST проверять совпадение подтверждения и отличие нового пароля от текущего до отправки.

#### Scenario: Первый вход
- **WHEN** пользователь входит с временным паролем
- **THEN** сразу открывается окно смены пароля, остальной интерфейс недоступен

#### Scenario: Успешная смена
- **WHEN** пользователь вводит верный текущий и допустимый новый пароль
- **THEN** окно закрывается, приложение сохраняет новую пару токенов и открывает рабочий интерфейс

#### Scenario: Подтверждение не совпадает
- **WHEN** новый пароль и подтверждение различаются
- **THEN** приложение показывает ошибку и не отправляет запрос

#### Scenario: Новый пароль равен текущему
- **WHEN** пользователь вводит новый пароль, равный временному
- **THEN** приложение показывает ошибку и не отправляет запрос

#### Scenario: Отказ от смены
- **WHEN** пользователь нажимает «Выйти» в окне смены пароля
- **THEN** сессия завершается, показывается экран входа

### Requirement: Выход
Приложение SHALL предоставлять действие выхода, которое отзывает сессию на сервере, стирает токены из памяти и из защищённого хранилища и показывает экран входа. Если сервер недоступен, токены MUST всё равно быть стёрты локально, а пользователю показано, что сессия на сервере могла остаться активной.

#### Scenario: Выход при доступном сервере
- **WHEN** пользователь нажимает «Выйти»
- **THEN** сервер отзывает сессию, токены стираются, показывается экран входа

#### Scenario: Выход без связи
- **WHEN** пользователь нажимает «Выйти», а сервер недоступен
- **THEN** токены всё равно стираются локально, показывается экран входа с предупреждением

### Requirement: Очистка данных пользователя при завершении сессии
Приложение SHALL при завершении сессии (выход или неудачное обновление) прекращать идущие потоковые ответы и убирать из интерфейса данные предыдущего пользователя (список чатов, историю, черновики), чтобы следующий вошедший пользователь их не увидел.

#### Scenario: Смена пользователя
- **WHEN** один пользователь выходит, а другой входит
- **THEN** новый пользователь видит только свои чаты, данных предыдущего нет

#### Scenario: Потеря сессии во время ответа
- **WHEN** сессия завершается, пока идёт потоковый ответ агента
- **THEN** ответ прерывается, показывается экран входа
