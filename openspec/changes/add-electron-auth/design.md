## Context

Мотивация описана в `proposal.md`, требования в `specs/desktop-auth-session/spec.md`.

Текущее состояние control-center:
- Renderer ходит на backend через кастомный протокол `cc-api://backend/...`. Обработчик в main (`cc-api-protocol.ts`) пересылает запрос через `net.fetch`, пропускает только `/threads` и `/agent`, вырезает `authorization` и `cookie`, ответ отдаёт потоком.
- Preload отдаёт в renderer только `platform`. Хранилища секретов нет.
- Backend (`/auth/*`) уже умеет `X-Client-Type: desktop`: refresh-токен приходит и принимается в теле, cookie не ставятся, `OriginGuard` такие запросы пропускает. Ошибки: 401 `TOKEN_EXPIRED`/`TOKEN_INVALID`, 409 `REFRESH_RACE`, 403 `PASSWORD_CHANGE_REQUIRED`, 429 `RATE_LIMITED` с `Retry-After`. Refresh-токен ротируется при каждом обновлении.
- В расширении manager-helper (`src/shared/auth`) есть готовая модель: хранилище access-токена, координатор обновления, `AuthGate`, `LoginForm`, `ChangePasswordDialog`. Отличие Electron: нет cookie и нет нескольких контекстов, зато есть доверенный процесс main.

## Goals / Non-Goals

**Goals:**
- Токены не попадают в renderer ни при каких сценариях (в том числе при XSS в интерфейсе).
- Одна точка авторизации и обновления токена для всех запросов, включая потоковый `/agent`.
- Переиспользовать UI-паттерны расширения без копирования его инфраструктуры cookie.

**Non-Goals:**
- Изменения backend и контракта `user-auth`.
- Общий пакет авторизации для расширения и Electron (разные среды хранения токенов; выносить рано).
- Несколько аккаунтов, SSO, «запомнить меня» как настройка (сессия сохраняется всегда, пока доступно шифрование ОС).
- Реакция на смену прав пользователя на лету (роли в приложении не используются).

## Decisions

### 1. Вся логика токенов живёт в main, renderer видит только состояние сессии
Main держит `AuthService`: access в памяти, refresh в защищённом хранилище, выполняет `login`/`refresh`/`logout`/`change-password` напрямую через `net.fetch`. Renderer управляет сессией IPC-командами (`login`, `logout`, `changePassword`, `retryRestore`, `getState`) и подписывается на события изменения состояния. Токены через IPC не передаются.

*Альтернатива:* пропускать `/auth/*` через `cc-api` и держать токены в renderer, как в расширении. Отвергнуто: refresh-токен оказывается в JS-контексте, что ломает требование о недоступности токена; в расширении это решала `httpOnly` cookie, в Electron её аналога для renderer нет.

### 2. Refresh-токен хранится через `safeStorage` в файле в `userData`
`safeStorage.encryptString` (Keychain на macOS, DPAPI на Windows, libsecret на Linux), результат пишется в файл в `app.getPath('userData')`. Если `safeStorage.isEncryptionAvailable()` ложно (или на Linux backend шифрования `basic_text`), токен на диск не пишется, сессия живёт до закрытия приложения, пользователь предупреждается.

*Альтернативы:* `keytar` (нативная зависимость, поддержка прекращена); хранение в открытом виде (отвергнуто по безопасности); `electron-store` с шифрованием ключом из кода (ключ лежит рядом, защиты нет).

### 3. Подстановка Bearer и повтор при 401 в `cc-api`-прокси
Обработчик протокола получает токен у `AuthService` (`getAccessToken()`), ставит `Authorization` и пересылает. При 401 с кодом `TOKEN_EXPIRED` вызывает `AuthService.refresh()` и повторяет запрос один раз. Для повтора тело запроса буферизуется (`arrayBuffer`): тела запросов к `/threads` и `/agent` небольшие JSON, а потоком идёт только ответ. Повтор безопасен, потому что backend отклоняет запрос по авторизации до начала работы. Перед отправкой токен проактивно обновляется, если до истечения (`exp` из JWT) меньше 30 секунд: это сокращает число повторов и защищает долгие стримы от протухания в начале.

Токен, истёкший посреди уже идущего стрима, не влияет на него: backend проверяет токен один раз при приёме запроса.

*Альтернатива:* повторять запросы на уровне renderer. Отвергнуто: renderer не должен знать о токенах, а логика дублировалась бы в каждом клиенте (`threads.api`, `agent`).

### 4. Единый refresh с очередью
`AuthService.refresh()` хранит один «полёт» (`Promise`), все ожидающие получают результат этого же вызова. Ротируемый refresh-токен нельзя предъявлять параллельно. 409 `REFRESH_RACE` обрабатывается одним повтором с актуальным токеном из хранилища. Новая пара сохраняется в хранилище до того, как access-токен становится доступен запросам, иначе падение между ротацией и записью потеряет сессию.

### 5. Машина состояний сессии
Состояния: `restoring` → (`authenticated` | `mustChangePassword` | `unauthenticated` | `connectionError`). Main публикует состояние в renderer событием, renderer рисует по нему `AuthGate` (аналог расширения). Сетевая ошибка при восстановлении не стирает токен и ведёт в `connectionError` с кнопкой «Повторить»; только 401/`TOKEN_INVALID` стирает токен.

### 6. Сброс пользовательских данных при потере сессии
При переходе в `unauthenticated` main прерывает активные запросы прокси (общий `AbortController` сессии), renderer очищает кэш запросов (TanStack Query) и Zustand-сторы чатов. Это закрывает утечку чатов предыдущего пользователя на экране входа и после входа под другим логином.

### 7. Узкий IPC и жёсткая фильтрация заголовков
Каналы IPC принимают только структурированные данные (логин/пароль, пароли для смены) и валидируются в main. Прокси продолжает отбрасывать `authorization`/`cookie`/`x-client-type` от renderer и сам выставляет нужные. Список разрешённых префиксов не расширяется: `/auth` через прокси недоступен.

## Risks / Trade-offs

- [`safeStorage` на Linux без keyring даёт слабое или никакое шифрование] → не сохранять токен при `basic_text`/недоступности, показывать предупреждение; вход при каждом запуске приемлем.
- [Падение приложения между ротацией refresh-токена на сервере и записью нового в хранилище → сессия потеряна] → писать новый токен синхронно сразу после ответа; худший случай - повторный вход.
- [Буферизация тела запроса при повторе] → ограничено небольшими JSON-телами; загрузку файлов через прокси не планируем, при появлении пересмотреть.
- [Повтор `/agent` после 401] → backend отклоняет до запуска агента; риск двойного выполнения нет. Проверить в тесте с mock-сервером.
- [Часы клиента расходятся с сервером, проактивное обновление срабатывает не вовремя] → проактивное обновление - оптимизация; корректность держится на реактивном повторе по 401.
- [Блокировка по 429 хранится только в UI] → при перезапуске счётчик сбросится, но сервер всё равно ответит 429; это допустимо.

## Migration Plan

Серверных и данных миграций нет. У существующих установок сохранённой сессии нет, при первом запуске после обновления показывается экран входа. Откат: вернуть прежнюю версию приложения; backend не менялся, поэтому остаётся совместимым.
