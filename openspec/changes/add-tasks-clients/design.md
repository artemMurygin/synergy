## Context

Мотивация и объём — в `proposal.md`, поведение — в `specs/`. Текущее состояние, влияющее на подход:

- Бэкенд задач готов (`openspec/specs/task-management`, `task-attachments`). Ответ задачи: `creator`, `assignee`, `watchers` как `{id, login|null}`, `deadline/createdAt/updatedAt/completedAt` в ISO, детали содержат `attachments`. Список: `GET /tasks?status&creatorId&assigneeId&watcherId&overdue&search&sort&order&limit&page`.
- Списка пользователей в API нет, есть только `GET /auth/me`.
- **control-center**: Electron + React 19, zustand (`ui.store`, `chat.store`), TanStack Query (`threads.queries.ts`), shadcn/Tailwind, zod. Запросы идут через кастомный протокол `cc-api://backend/...`; main-процесс пересылает только префиксы `/threads` и `/agent` и вырезает `Authorization`/`Cookie`. Роутера нет, раскладка `ChatLayout` — две колонки. Авторизация в этом приложении — отдельный change `add-electron-auth` (токен подставляет прокси в main).
- **manager-helper**: Chrome MV3, side panel на React без TanStack Query; запросы идут через `authFetch` (Bearer, один общий refresh) к `getBackendUrl()`. API-слой — ручные парсеры (`threads-api.ts`), без zod.
- Пакеты независимы, монорепозитория нет (решение: код не шарить).

## Goals / Non-Goals

**Goals:**
- Один контракт и один дизайн-язык в двух клиентах при независимой реализации.
- Серверное состояние (задачи, пользователи) живёт в кэше запросов, клиентское (фильтры, выбранная задача, раздел) — в zustand; дублирования между ними нет.
- Расширение `features/tasks` не требует правок чатовых фич, кроме точек входа (`App.tsx`, `ui.store`, шапка панели).

**Non-Goals:**
- Роутер и URL-адресация задач в control-center.
- Права и роли: все аутентифицированные видят все задачи (как в бэкенде).
- Комментарии, история изменений, уведомления, push/реалтайм-обновление списков, офлайн-режим.
- Загрузка и удаление вложений, а также редактирование наблюдателей в расширении.
- Общий npm-пакет между клиентами.
- Канбан-доска (кандидат на отдельный change; данные и фильтры устроены так, чтобы её можно добавить).

## Decisions

### D1. `GET /users` — в модуле `auth`, ответ только `{id, login}`
Эндпоинт принадлежит владельцу таблицы `auth_users`; tasks остаётся зависимым только от порта `UserDirectory`. Расширяем существующий порт каталога пользователей методом поиска, а не даём клиентам ходить в БД другим путём. Поиск `ILIKE` по логину с экранированием `%`/`_`, сортировка по логину, стандартная пагинация, `is_active = true`.
*Альтернативы:* вводить поле «имя» (нет в модели, отдельный change); отдавать всех без пагинации (рост списка, утечка лишнего).

### D2. Контракт клиента: zod-схемы + тонкий API-слой в каждом пакете
В control-center — `lib/backend/tasks.schema.ts`, `tasks.api.ts`, `users.api.ts` (zod уже в зависимостях). В manager-helper — `shared/tasks-api.ts` в стиле существующих парсеров, без добавления zod (иначе расширение растёт ради одного модуля). Имена типов и полей совпадают (`Task`, `TaskDetails`, `TaskStatus`, `TaskUser`, `TaskPage`), чтобы переносить логику и тесты.
Типизированные ошибки: `TaskNotFoundError` (404), `TaskUserNotFoundError` (422 `TASK_USER_NOT_FOUND`), `AttachmentTooLargeError` (413), `AttachmentLimitError` (422), `BackendError`.
*Альтернатива:* общий пакет (отвергнут пользователем: нужны workspaces и сборка).

### D3. control-center: раскладка и навигация
- `AppShell` = левый рейл (56 px, иконки «Чаты» и «Задачи» с подписью-tooltip, переключатель темы и пользователь внизу) + область раздела. Вместо `ChatLayout` в `App.tsx` рендерится `AppShell`, внутри которого активный раздел выбирается по `ui.store.section: 'chats' | 'tasks'`. Оба раздела остаются смонтированными (скрытие через `hidden`), чтобы не терять состояние чата и поток запроса при переключении; раздел задач монтируется лениво при первом открытии.
- Раздел «Задачи»: `TasksPage` = панель инструментов (поиск, быстрые представления, фильтр статуса, сортировка, «Новая задача») + `TaskList` + `TaskDrawer`.
- Drawer: не модальный, `role="complementary"`, ширина 480 px, список под ним остаётся кликабельным. Модальны только диалоги создания и подтверждения удаления.
*Альтернативы:* react-router hash (лишняя зависимость при одном переключателе); две колонки, как у чатов (теряется ширина списка с колонками).

### D4. control-center: состояние
- `tasks.store.ts` (zustand): `view`, `status`, `search`, `sort`, `order`, `page`, `selectedTaskId`. Только клиентские решения пользователя; значения не дублируют ответ сервера.
- `tasks.queries.ts` (TanStack Query): `tasksQuery(filters)` с `placeholderData: keepPreviousData` (без мигания при смене страницы), `taskQuery(id)`, `usersQuery(search)`, мутации `useCreateTask`, `useUpdateTask`, `useDeleteTask`, `useUploadAttachment`, `useDeleteAttachment`.
- Представления («Мои» и др.) переводятся в параметры запроса функцией `viewToFilter(view, currentUserId)`; текущий пользователь берётся из состояния сессии, добавляемого `add-electron-auth`.
- Смена статуса — оптимистичная: `onMutate` правит кэш списка и деталей, `onError` откатывает и показывает уведомление, `onSettled` инвалидирует. Остальные правки — не оптимистичные (ждут ответа).
- Поиск — debounce 300 мс на уровне хука.

### D5. control-center: прокси `cc-api` и вложения
Расширяем `ALLOWED_PREFIXES` на `/tasks` и `/users`. Загрузка: renderer отправляет `FormData` через `fetch('cc-api://…')`; тело пересылается потоком, `content-type` с boundary не должен вырезаться (он не в списке отбрасываемых — оставляем, добавляем тест). Прогресс загрузки у `fetch` недоступен, поэтому используем `XMLHttpRequest` для `cc-api` (поддерживается для стандартных протоколов с `supportFetchAPI`; проверяется спайком в первой задаче, запасной вариант — индикатор без процентов). Скачивание: ответ `blob` → сохранение через `<a download>` с именем из `Content-Disposition` (`filename*`), без нового IPC.
**Результат спайка (задача 2.5):** XHR к `cc-api://` в Electron работает (статус 201, multipart с boundary доходит до обработчика протокола, тело 3 МБ цело), но `upload.onprogress` не срабатывает ни разу, ни со страницы `data:`, ни с `http://localhost`. Поэтому UI вложений показывает индикатор загрузки без процентов с кнопкой «Отмена» (отмена через `AbortSignal`); полоса прогресса из макета `oOcIi` реализуется как неопределённая.
Лимиты (20 МБ, 10 файлов) клиент знает из констант с комментарием «значения по умолчанию бэкенда» и не считает их истиной: решающим остаются ответы 413/422.

### D6. Дизайн-система
Токены и компоненты берутся из `design/synergy-design-kit.pen` (шрифты Onest и Raleway уже подключены). Новые общие элементы, описанные в `ui-design.md`: `StatusBadge`, `DeadlineLabel`, `UserChip`/`AvatarStack`, `TaskRow`, `FilterTabs`, `UserPicker`, `AttachmentRow`. Статус кодируется иконкой и текстом, цвет — дополнительный сигнал. Реализация в control-center на shadcn (добавляются `dialog`, `sheet`-подобный drawer, `select`, `badge`, `popover`, `command`, `textarea`, `tooltip`, `sonner`-подобный тост на Radix). В расширении — те же названия, но на Tailwind без shadcn, чтобы не раздувать бандл.

### D7. manager-helper: экран и состояние
- В шапке `ChatHeader` — сегмент «Чат / Задачи»; `App.tsx` выбирает `ChatApp` или `TasksApp`. Чат остаётся смонтированным и скрытым, чтобы не прерывать стрим (`ChatRuntimeProvider` живёт выше переключателя). Выбранный раздел хранится в `chrome.storage.local` (по образцу `active-session.ts`).
- `features`-слой расширения: `sidepanel/tasks/` с `TasksApp`, `TaskList`, `TaskRow`, `QuickCreate`, `TaskDetails`, `use-tasks.ts`. Серверное состояние — собственный минимальный хук (`useAsync`-стиль с `reload`, `loadMore`, оптимистичная смена статуса); TanStack Query в расширение не добавляем (нет в зависимостях, лишние ~13 КБ ради одного модуля).
- Навигация экран-список/экран-детали — локальный стейт `selectedId`; прокрутка и фильтр сохраняются тем, что список не размонтируется (скрывается).
- «Мои задачи» по умолчанию: `assigneeId=<я>`, статусы `todo` и `in_progress` (бэкенд не умеет «не done», поэтому клиент делает два запроса `status=todo` и `status=in_progress` и сливает по дедлайну; пагинация — «ещё» по каждому потоку). Это ограничение отмечено в рисках; альтернативой считался новый фильтр `statusNot` в бэкенде (расширяет контракт `task-management`, отложено).

### D7a. manager-helper: версия для планшета (растянутая панель)
Side panel можно растянуть по ширине, поэтому у раздела задач две раскладки, как у чата: порог `WIDE_BREAKPOINT = 640` и `useViewportSize` берутся из `panel-layout.ts`, отдельный порог не вводится. В широком режиме `TasksApp` рендерит список и детали одновременно (список 340 px, детали занимают остальное); в узком показывает один из них по `selectedId`. Состояние (`selectedId`, фильтр, прокрутка) одно на оба режима, переключение ширины его не сбрасывает. Правка и смена статуса в широком режиме идут в правом столбце без смены экрана. Функция видимости столбцов выносится в чистую `tasks-layout.ts` по образцу `paneVisibility` и покрывается тестами.

### D8. Обработка ошибок и сессии
Все запросы идут через слой авторизации своего клиента (`authFetch` в расширении, прокси в control-center), потеря сессии обрабатывается там же и в фичах не дублируется. Фичи различают только доменные ошибки (404, 413, 422) и общую `BackendError` с сообщением. Диалоги и формы не закрываются при ошибке и сохраняют ввод.

### D9. Тестирование
Vitest + Testing Library, как в проектах. Слои: API-клиенты (мок `fetch`), `viewToFilter`/слияние потоков (чистые функции), хуки с мутациями (оптимистичный откат), компоненты (список, drawer, диалог, UserPicker, вложения) с проверкой доступности по ролям. Backend: unit на use-case и контроллер, интеграционный тест репозитория. Ручная проверка в приложении и в Chrome с фиксацией скриншотов.

## Risks / Trade-offs

- [Прогресс загрузки через `cc-api` может не работать в XHR] → спайк в первой задаче; fallback — неопределённый индикатор.
- [Два запроса в «Мои задачи» расширения усложняют пагинацию и сортировку] → ограничить первую версию страницей в 50 задач на поток с кнопкой «Ещё»; при росте объёма добавить `statusNot`/`open=true` в бэкенд отдельным change.
- [Список пользователей отдаёт логины всем аутентифицированным] → допустимо для внутреннего инструмента, соответствует тому, что логины и так видны в задачах; без хэшей и служебных полей.
- [Оба раздела смонтированы одновременно в control-center] → память и подписки растут незначительно; раздел задач монтируется лениво.
- [Зависимость от `add-electron-auth`] → разработку и тесты клиента ведём на моках API; интеграционная проверка против защищённого бэкенда — после слияния auth, пока допустимо тестировать с отключённой защитой окружения.
- [Дублирование контракта в двух пакетах] → схемы маленькие; общий набор фикстур JSON в описании контракта (`specs/`) и тесты в обоих пакетах ловят расхождение с бэкендом.
- [Оптимистичная смена статуса при конкурентной правке] → после `onSettled` всегда перечитываем данные, побеждает сервер.

## Migration Plan

1. Backend `GET /users` (обратно совместимое добавление, миграции БД не нужны).
2. control-center: прокси и раздел задач за переключателем рейла; чаты не затронуты.
3. manager-helper: раздел задач за сегментом в шапке.
Откат: обратное добавление эндпоинта безопасно; клиентские разделы удаляются вместе с точками входа, данные не затрагиваются.
