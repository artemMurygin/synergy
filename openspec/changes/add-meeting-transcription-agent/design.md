## Context

Мотивация и состав описаны в proposal.md, требования — в `specs/`. Ниже только то, что влияет на подход.

- **Расшифровка.** `transcription/meeting` расшифровывает записи в фоне (BullMQ) и сохраняет результат в `meeting_transcript`. Сегменты лежат там же, в поле `segments JSONB`, которое читается только целиком. Через outbox публикуются события `meeting-transcript.completed` и `meeting-transcript.failed`. Подписчиков у них пока нет.
- **Файлы.** `files` хранит файлы в MinIO, загрузка идёт через `POST /files` (multipart), скачивание — по подписанной ссылке. Готового способа сохранить файл, созданный на сервере (буфер), нет.
- **Чат.**
  - История лежит в двух местах: таблица `chat_message` (`role user|agent`, `text`, `tool_calls`, `duration_ms`) для клиента и checkpointer LangGraph (thread = id чата) для контекста агента.
  - Вход запуска — только текст (`RunInput.question`).
  - Поток — AG-UI (`@ag-ui/core` 1.0.4).
  - Активные запуски учитываются в памяти процесса (`ActiveRunRegistry`).
- **Агент.** Профиль «приложение» — оркестратор `deepagents` со специалистами (`AgentCapability`: `sheetsQa`, `tasks`). Специалист не может сам вызвать другого специалиста: делегирует только оркестратор. Подтверждение создания задачи сейчас обеспечивает только промпт (skill `task-creation`): на уровне данных защиты от повторного создания нет.
- **Задачи.** У задачи есть `creatorId`, его берут из токена. Событие `task.created` обрабатывают уведомления.
- **Ограничение.** Правила архитектуры из `openspec/config.yaml` (DDD, порты и адаптеры) важнее паттернов, которые встречаются в текущем коде.

## Goals / Non-Goals

**Goals:**
- Большая расшифровка (2–4 часа) никогда не попадает в контекст оркестратора целиком. С текстом работают инструменты, агенту возвращаются сводки.
- Повторное подтверждение не создаёт задачи дважды, и это гарантируют данные, а не промпт.
- Сообщение системы в чате попадает и в историю для клиента, и в контекст агента, без расхождений.
- Новые связи между модулями идут через контракты (события и порты), без прямых зависимостей на внутренности.

**Non-Goals:**
- Работа нескольких экземпляров бэкенда для активных запусков: сейчас реестр живёт в памяти процесса, и это изменение его не переделывает (см. риски).
- Общий механизм «агент пишет первым» для любых событий. Делаем ровно один источник: результат расшифровки. Контракт закладываем общим.
- Потоковая генерация документов и предпросмотр `.docx` в клиенте.

## Decisions

### 1. Сегменты и имена спикеров в отдельных таблицах
Миграция `022_meeting_transcript_segments.sql`:
- `meeting_transcript_segment (file_id, seq, speaker SMALLINT, start_sec, end_sec, text)`, PK `(file_id, seq)`, FK на `meeting_transcript`;
- `meeting_transcript_speaker (file_id, speaker, name, updated_at)`, PK `(file_id, speaker)`. Строка есть только у спикеров с именем: сброс имени = удаление строки.

Перенос данных: `jsonb_array_elements(segments) WITH ORDINALITY`, номер спикера берётся из метки `Спикер N`. После переноса колонка `segments` удаляется.

Агрегат `MeetingTranscript` получает отдельную сущность `SpeakerNames` с инвариантами: номер спикера ≤ `speaker_count`, имя 1–100 символов. Сегменты в агрегат не грузятся. Их читает отдельный порт `TranscriptSegmentReader`: целиком, по диапазону и выборкой примеров для каждого спикера.

*Альтернативы:*
- Оставить JSONB и хранить имена отдельно. Отвергнуто: пользователь явно просил отдельную таблицу, а выборки «примеры реплик спикера» и «диапазон времени» на JSONB неудобны.
- Переписывать метку спикера в сегментах. Отвергнуто: теряется исходная разметка, а одно имя у двух спикеров становится необратимым.

### 2. Вложения чата — таблица связей, источник сообщения — колонка
Миграция `023_chat_attachments.sql`:
- `chat_message_attachment (message_id, file_id, position)`, FK на `chat_message ON DELETE CASCADE` и на `stored_file`;
- `chat_message.source TEXT NOT NULL DEFAULT 'run' CHECK (source IN ('run','system'))`;
- `chat_message.dedup_key TEXT UNIQUE NULL` для идемпотентности сообщений системы.

Статус файла (`active`/`deleted`) в историю не копируется: история берёт его соединением со `stored_file`.

Проверку файлов при запуске (свой, `active`, не больше 5) делает `StartAgentRunUseCase` через контракт модуля `files` (`FindOwnedFiles`) до открытия потока. `RunInput` получает `attachments: readonly AttachmentRef[]`, а правило «текст или вложение» становится инвариантом `RunInput`.

Агент видит вложения как служебный блок в конце `HumanMessage`. Пример: `[Вложения]\n1. id=…; встреча.m4a; recording; 84 МБ`. Блок сохраняется в checkpointer, поэтому прошлые вложения остаются в контексте.

*Альтернативы:*
- JSONB-массив вложений в `chat_message`. Отвергнуто: не проверяется FK и нельзя дёшево найти «первый чат, где файл отправлен» (решение 4).
- Мультимодальный content part. Отвергнуто: провайдеры по-разному поддерживают части, отличные от текста, а содержимое агенту не нужно.

### 3. Файлы из ответа агента: сборщик в контексте запуска и событие AG-UI CUSTOM
`AgentRunContext` получает сборщик `RunAttachments`, созданный на один запуск. Инструмент, который создал документ, добавляет в него `fileId`.

`AgentRunner` при добавлении файла отправляет событие AG-UI `CUSTOM` с `name: "file-attached"` и `value: {id, name, mediaType, size, kind}`. При `run-finished` вложения сохраняются вместе с сообщением агента в одной транзакции. При ошибке или отмене сборщик отбрасывается, а файлы остаются в хранилище до истечения обычного срока.

`CUSTOM` выбран потому, что он есть в протоколе: клиенты, которые его не знают, просто игнорируют событие.

*Альтернатива:* ссылка на файл в тексте ответа (markdown). Отвергнуто: ссылка на скачивание живёт недолго, а модель может исказить идентификатор.

### 4. Чат записи определяется по первому вложению, без отдельной связи
«Чат, куда запись отправили впервые» — это `chat_message_attachment` с минимальным `message_id` для этого `file_id`, при условии что чат существует. Модуль `assistant` отдаёт контракт `FindFirstChatOfFile(fileId, ownerId)`.

Отдельной таблицы связи нет. Если чат удалён, каскад убирает и вложения, и запрос вернёт пусто. Это и есть требуемое «в удалённый чат не пишем».

*Альтернатива:* таблица `meeting_transcript_chat`, которую заполняет модуль транскрибации. Отвергнуто: дублирует данные чата, и ей нужен свой каскад при удалении чата.

### 5. Сообщение системы: подписчик → очередь → `PostSystemMessageUseCase`
1. Подписчик модуля встреч (решение 6) получает события `meeting-transcript.completed` и `meeting-transcript.failed`. Он находит чат (решение 4), формирует текст, для `completed` выпускает документ расшифровки и вызывает контракт `assistant` `PostSystemMessage({sessionId, ownerId, text, attachments, dedupKey: eventId})`.
2. `PostSystemMessageUseCase`:
   - если в чате идёт запуск (`ActiveRunRegistry`), бросает `RunInProgress`, и задача BullMQ повторяется с задержкой (5 с, до 10 минут);
   - иначе в одной операции записывает в `chat_message` строку `source='system'` с `dedup_key` (`ON CONFLICT DO NOTHING`, так повтор становится no-op) и добавляет `AIMessage` в thread через `graph.updateState` скомпилированного агента профиля «приложение». Порядок такой: сначала checkpointer, потом строка. Если упали между шагами, повтор найдёт `dedup_key` отсутствующим и запишет снова; в checkpointer тогда будет дубль сообщения агенту, что допустимо (см. риски);
   - обновляет `last_activity_at` и публикует событие `chat.system-message-posted`.
3. Уведомления подписываются на `chat.system-message-posted` и создают `meeting-transcript.ready` или `meeting-transcript.failed` со ссылкой `chat`. Тип и имя записи передаются в payload.

Новый вопрос пользователя в этот момент не блокируется. `tryStart` может опередить сообщение системы, и тогда оно просто подождёт следующего окна.

*Альтернативы:*
- Записывать только в `chat_message`, а агенту подмешивать при следующем запуске. Отвергнуто: две истории начнут расходиться, а логика подмешивания размазывается по запуску.
- Запускать агента, чтобы он «сам написал». Отвергнуто: это дорого, недетерминированно и занимает слот активного запуска.

### 6. Специалист по встречам живёт в модуле `transcription`, документы — там же
Возможность `meetings` (`AgentCapability`, режим `fork`: ей нужна история чата с вложениями и сообщениями системы) находится в `transcription/meeting/interface/agent/`, по образцу `tasks/interface/agent/`. Подключается в `AgentProfileFactory` третьим специалистом.

Инструменты (все работают от `ctx.userId`, чужая расшифровка → «не найдено»):

| Инструмент | Что делает | Что возвращает агенту |
|---|---|---|
| `get_meeting_transcript(fileId)` | статус, длительность, спикеры с именами и долей речи | сводку, без сегментов |
| `get_speaker_samples(fileId)` | по 2–3 характерные реплики каждого спикера (самые длинные из разных частей записи) | реплики с таймкодами |
| `rename_speakers(fileId, [{speaker, name}])` | атомарно назначает имена, выпускает документ, кладёт его в `RunAttachments` | имена и имя файла |
| `extract_meeting_tasks(fileId)` | извлекает задачи (решение 7), выпускает документ, кладёт его в `RunAttachments` | нумерованный список задач |
| `retry_transcription(fileId)` | существующий `RetryMeetingTranscriptionUseCase` | новый статус |

Документы: прикладной сервис `MeetingDocuments` строит модель документа (заголовок, абзацы, таблицы), а собирает `.docx` общий генератор `shared/documents` (порт `DocumentRendererPort`, адаптер на библиотеке `docx`). Генератор не знает ни о встречах, ни о задачах, поэтому модуль `tasks` пользуется им для своего документа без зависимости от `transcription` (решение 8). Сохранение идёт через новый контракт `files`: `StoreGeneratedFile({ownerId, name, mediaType, buffer})`. Вид файла `document`, срок хранения обычный, событие `file.uploaded` публикуется как для любого файла. Расшифровку оно не запускает, потому что это документ.

*Альтернатива:* отдельный модуль `meetings`. Пока отвергнуто: вся предметная область (расшифровка, спикеры, сегменты) уже в `transcription/meeting`, а новый модуль читал бы её чужие таблицы. Если сценарий разрастётся (протоколы, саммари), выделим.

### 7. Извлечение задач — структурированный вызов LLM внутри инструмента
`extract_meeting_tasks` сам читает сегменты и вызывает модель со structured output (zod-схема: `title`, `description`, `assigneeMention`, `dueText`, `evidence: {seq, quote}`). Агенту возвращается только результат.

На вход модели идут реплики в виде `[seq] [чч:мм:сс] Имя: текст`. Если расшифровка длиннее порога (по умолчанию ~60 тыс. токенов), она режется на окна по 30 минут с перекрытием 2 минуты, а результаты сливаются вторым вызовом: убираются дубли, объединяются формулировки.

Пост-проверка:
- задача без `evidence`, с несуществующим `seq` или с цитатой, которой нет в сегменте (нормализованное вхождение), отбрасывается;
- `dueText` превращается в дату по правилам относительных дат из `task-agent-tools` относительно даты загрузки записи, а не сегодняшней.

Результат никуда не сохраняется: в чат он попадает документом и списком в ответе.

*Альтернатива:* дать специалисту инструмент «прочитать диапазон сегментов» и извлекать задачи в его контексте. Отвергнуто: стоимость растёт с длиной записи, а на длинных встречах модель теряет середину.

### 8. Список задач передаёт оркестратор, специалист по задачам — через черновик
Последний ответ специалиста по встречам содержит нумерованный список задач (название, описание, упомянутый исполнитель, срок, основание). Оркестратор при согласии пользователя делегирует задачу специалисту по задачам. Тот работает в режиме `fork`, поэтому видит этот список в истории. Прямой зависимости `tasks` → `transcription` нет.

В `tasks` добавляются:
- миграция `024_task_initiator.sql`: `task.initiator_id UUID NULL`, заполнение значением `creator_id`, затем `NOT NULL`;
- миграция `025_task_batch_draft.sql`: `task_batch_draft (id, owner_id, thread_id, items JSONB, origin JSONB NULL, status draft|superseded|consumed, result JSONB NULL, created_at)`;
- инструмент `propose_tasks(items[])` сохраняет черновик, а прошлый черновик этого thread помечает `superseded`. Возвращает `draftId` и карточки. Пользователей проверяет сразу: неизвестный исполнитель или постановщик → ошибка до показа;
- инструмент `create_tasks(draftId)` выполняет `UPDATE … SET status='consumed' WHERE id=$1 AND status='draft' RETURNING items`. Если строк нет — «уже создано или устарело», ничего не делается. Иначе для каждой задачи вызывается `CreateTaskUseCase` в своей транзакции, ошибки собираются по номерам;
- `CreateTaskUseCase` принимает `actor` (инициатор, из контекста) и необязательный `creatorId`. HTTP-контроллер `creatorId` не передаёт никогда, так что правило «создатель из токена» сохраняется на уровне интерфейса. `TaskCreated` получает `initiatorId`;
- черновик хранит `origin: { kind: 'meeting', fileId, recordingName } | null`: специалист по задачам передаёт его в `propose_tasks`, когда список пришёл из встречи. Для такого черновика `create_tasks` после создания строит модель «Поставленные задачи» (`TasksReportDocument` в `tasks`), рендерит её через `shared/documents`, сохраняет через `StoreGeneratedFile` и кладёт в `RunAttachments`;
- одиночное создание тоже проходит через `propose_tasks`/`create_tasks` с одним элементом. Так защита от повтора действует для обоих путей, а skill `task-creation` дополняется правилами списка и постановщика.

*Альтернатива:* `create_tasks(items)` без черновика, а идемпотентность — по хэшу списка. Отвергнуто: правка «вторую не надо» и повторное «да» по хэшу неотличимы от осознанного повторного создания.

### 9. Уведомление постановщику
Обработчик `task.created` в `notifications` при `creatorId ≠ initiatorId` создаёт `task.created-on-behalf` для `creatorId` с инициатором `initiatorId`. Идемпотентность — по существующему ключу «событие + получатель + тип».

### 10. Electron: загрузка с прогрессом и обновление открытого чата
- Загрузка идёт через `XMLHttpRequest` (в `fetch` нет прогресса отправки) с `AbortController`-подобной отменой. Состояние вложений черновика живёт в сторе поля ввода.
- Запуск отправляет `fileIds` рядом с текстом. Событие `CUSTOM file-attached` добавляет карточку в формируемое сообщение.
- Уведомление `meeting-transcript.*` из существующего realtime-канала: если `object.id` совпадает с открытым чатом, история перечитывается; если нет — показывается обычное всплывающее уведомление с переходом в этот чат. Отдельного realtime-события для чата не вводим.

## Risks / Trade-offs

- **[Риск] Реестр активных запусков живёт в памяти.** При нескольких экземплярах бэкенда сообщение системы может попасть внутрь чужого запуска. → Сейчас бэкенд один экземпляр. В README фиксируем, что `ActiveRunRegistry` нужно вынести в Redis до горизонтального масштабирования.
- **[Риск] Падение между записью в checkpointer и в `chat_message`.** Тогда агент увидит сообщение о готовности дважды. → Безвредно для смысла. Сначала пишем checkpointer, потому что потеря сообщения в контексте агента хуже, чем дубль.
- **[Риск] Модель извлекает выдуманные задачи.** → Обязательное `evidence` и проверка цитаты по сегменту, температура 0, финальное подтверждение пользователем.
- **[Риск] Постановщик-не-собеседник позволяет ставить задачи «от чужого имени».** → Фиксируется инициатор, постановщик получает уведомление. Права проверяются для инициатора. Через HTTP задать создателя нельзя.
- **[Компромисс] Каждая смена имён создаёт новый файл.** Документов в хранилище становится больше. → Это небольшие документы с обычным сроком хранения, зато пользователь видит историю версий в чате.
- **[Риск] `graph.updateState` у `deepagents` требует собранный граф профиля.** → Отдельный метод `AgentProfileFactory.appendAssistantMessage(threadId, message)`, который собирает граф без инструментов (нужен только checkpointer) и покрыт интеграционным тестом с Postgres-checkpointer.
- **[Компромисс] Список задач передаётся текстом через оркестратор.** Возможна неточная пересказка. → Специалист по задачам в режиме `fork` видит исходный ответ специалиста по встречам. Оркестратору в промпте запрещено пересказывать список: он передаёт ссылку «список из предыдущего ответа».

## Migration Plan

1. Заархивировать `add-file-storage` (`openspec archive`), чтобы спеки `file-storage` и `meeting-transcription` легли в `openspec/specs/`.
2. Миграции по порядку: `022` (сегменты: перенос и удаление колонки), `023` (вложения чата), `024` (инициатор задачи), `025` (черновики задач). Все применяются без простоя. `022` переписывает таблицу расшифровок: на текущих объёмах это секунды.
3. Сначала выкатывается бэкенд. Старые клиенты не шлют `fileIds` и игнорируют `CUSTOM`, так что поток для них не меняется. Потом выходит Electron.
4. Откат: бэкенд откатывается вместе с обратными миграциями `025…022`. `022 down` собирает `segments JSONB` обратно из таблицы, имена спикеров при этом теряются: это осознанно. Сообщения системы и вложения при откате `023` удаляются вместе с колонками и таблицей.

## Open Questions

- Порог токенов для нарезки при извлечении задач и размер окна. Подбираются на реальных записях, на подход не влияют.
- Точные тексты сообщений системы и уведомлений. Уточняются в ui-design.
