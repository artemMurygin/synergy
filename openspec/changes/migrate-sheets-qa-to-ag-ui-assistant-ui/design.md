## Context

Мотивация и объём — см. `proposal.md`. Поведение — см. `specs/`.

Текущее состояние:
- Backend (NestJS, слои domain / application / infrastructure / interface): `AskQuestionUseCase` сохраняет вопрос, вызывает `SheetsAssistantPort.ask()` и сохраняет готовый ответ. Реализация `DeepAgentsSheetsAssistant` на каждый вопрос собирает агента через `createDeepAgent` (он уже возвращает скомпилированный граф LangGraph) и вызывает `agent.invoke`. Чекпойнты лежат в Postgres, `thread_id` равен `chat_session.id`.
- Сообщения для UI хранятся отдельно в `chat_message` (роль `user`/`agent`, текст, трассировка инструментов, длительность).
- Клиент (manager-helper, React 19, Vite, Tailwind 4): `use-chat.ts` делает `POST /sheets-qa/ask` и ждёт ответ целиком; список чатов — REST `chat-sessions`. Чат живёт только в side panel; страница options содержит лишь настройки (адрес бэкенда), `host_permissions` разрешают только localhost.

Ограничения: у assistant-ui адаптер списка тредов для AG-UI помечен экспериментальным; AG-UI передаёт в запуске `threadId`, `runId` и `messages`, события идут по SSE.

## Goals / Non-Goals

**Goals:**
- Единый путь запуска агента: AG-UI поверх SSE, один `threadId` на чат на всех уровнях (БД, чекпойнты, клиент).
- Не терять существующие чаты и не менять поведение агента (книги, субагенты, лимиты, скрытые данные, prompt caching).
- Клиент полностью на assistant-ui; собственный код остаётся только там, где нет готового: форма быстрого подбора, адаптивная раскладка, список чатов.

**Non-Goals:**
- Переписывание агента, промптов и инструментов; смена модели или провайдера.
- Подключение к идущему запуску и показ частей ответа после возврата в чат (сервер не переигрывает поток; это возможное следующее изменение).
- Возобновление запуска после падения или перезапуска сервера: запуск живёт в памяти процесса и погибает вместе с ним.
- Горизонтальное масштабирование запусков (реестр запусков в памяти процесса).
- Реализация собственного облачного хранилища assistant-ui.

## Decisions

**1. Агент остаётся на `deepagents`, наружу отдаётся поток LangGraph.**
`createDeepAgent` — это граф LangGraph, поэтому «перенос на LangGraph» сводится к смене способа вызова: вместо `invoke` — `streamEvents` (версия v2). Это снимает риск переписывания и сохраняет поведение субагентов. Правка относительно proposal: зависимость `deepagents` не удаляется.
Альтернатива — собственный `StateGraph`: даёт полный контроль над узлами, но заставляет заново писать оркестрацию субагентов без выгоды для задачи.

**2. Серверный мост LangGraph → AG-UI пишем сами в слое infrastructure.**
Порт `SheetsAssistantPort` меняется: `ask()` заменяется на `run(input): AsyncIterable<AgentEvent>` с доменными событиями (текстовый фрагмент, начало/конец вызова инструмента, ошибка). Преобразование доменных событий в события AG-UI (`RUN_STARTED`, `TEXT_MESSAGE_*`, `TOOL_CALL_*`, `RUN_FINISHED`/`RUN_ERROR`) и кодирование SSE — в слое interface через `@ag-ui/core` и `@ag-ui/encoder`. Так домен и application не знают про AG-UI.
Альтернатива — готовый LangGraph-адаптер AG-UI: рассчитан на LangGraph Platform и Python, а наш граф создаётся внутри NestJS-процесса.

**3. Управление чатами остаётся обычным REST, запуск — AG-UI.**
AG-UI описывает запуск, а не список чатов. Поэтому ресурс переименовывается из `chat-sessions` в `threads` (`POST/GET /threads`, `GET /threads/:id/messages`, `PATCH`, `DELETE`), а `POST /agent` принимает `RunAgentInput`. Старые маршруты `sheets-qa/ask` и `chat-sessions` удаляются без периода совместимости (единственный потребитель — расширение, собирается вместе с сервером).
История `GET /threads/:id/messages` отдаётся в формате сообщений AG-UI (пользователь, ассистент с `toolCalls`, результаты инструментов), чтобы клиент передавал её в runtime без преобразований.

**4. Запуск живёт независимо от соединения; сообщения сохраняются на сервере по итогам запуска.**
`POST /agent` создаёт запуск (`Run`) и подписывает на него SSE-ответ как одного из наблюдателей. Закрытие соединения только отписывает наблюдателя и запуск не останавливает. Агент работает в фоне до завершения, ошибки, отмены или таймаута.
Сервер не доверяет истории из `RunAgentInput`: контекст берётся из чекпойнта по `threadId`, из `messages` используется только последнее сообщение пользователя. Сообщение пользователя пишется при старте запуска, сообщение агента — только по успешному завершению (ошибка и отмена неполный ответ не сохраняют). Схема `chat_session` и `chat_message` не меняется, миграции данных нет: существующие чаты уже имеют нужный `thread_id`.
Альтернатива — отменять запуск при закрытии соединения: проще, но ответ теряется, если закрыть панель (см. proposal, поведение сегодня сохраняет ответ).

**5. Реестр активных запусков в памяти процесса.**
Сервис application хранит `threadId → Run`. `Run` содержит `AbortController` и ссылку на открытый SSE-ответ (если он есть). Запись создаётся при старте запуска и удаляется при его завершении, ошибке или отмене; закрытие соединения только обнуляет ссылку на ответ, а события дальше никуда не пишутся. Второй запуск в чате с записью получает 409. Лимит шагов (`recursionLimit`) и таймаут (`AbortSignal.timeout`) переносятся из текущей реализации и защищают от запусков, которых никто не ждёт.
Альтернатива — advisory lock в Postgres и очередь запусков: нужна только при нескольких инстансах, сейчас он один.

**5а. Отмена и признак активного запуска.**
- `POST /threads/:id/run/cancel`: идемпотентно отменяет запуск; если поток ещё открыт, он завершается событием с признаком отмены.
- `GET /threads` и `GET /threads/:id/messages` возвращают признак `running` из реестра.
- Удаление чата сначала отменяет активный запуск, затем удаляет данные; сообщение агента после удаления нигде не пишется.
- При остановке процесса (graceful shutdown) активные запуски отменяются.
Подключение к идущему запуску сознательно не делаем: снимок и живые события пришлось бы стыковать без пропусков и дублей, а возобновление в assistant-ui экспериментальное. Это возможное следующее изменение; контракт этого не закрывает, так как реестр запусков можно расширить снимком состояния.

**6. Клиент: `@assistant-ui/react` + `@assistant-ui/react-ag-ui` с `HttpAgent`.**
`useAgUiRuntime` подключается к `/agent`; `threadId` активного чата хранится как сейчас в `active-session` (chrome storage) и передаётся в `adapters.threadList` (`onSwitchToNewThread`, `onSwitchToThread` загружают историю с сервера).
Если у открытого чата `running`, панель показывает индикатор «агент отвечает», блокирует отправку и раз в несколько секунд перечитывает историю, пока `running` не станет `false`; затем показывает готовый ответ. Кнопка «Остановить» вызывает `run/cancel` (закрытие соединения запуск не останавливает), поэтому `onCancel` runtime-а обязан отправлять явную отмену. Список чатов, переименование и удаление остаются нашим UI поверх REST `threads` — адаптер для них не нужен и помечен экспериментальным. Компоненты сообщений, композера и прогресса инструментов берутся из примитивов assistant-ui; стили — Tailwind, в рамках нового дизайна.
Альтернатива — собственный клиент AG-UI без assistant-ui: меньше зависимостей, но придётся заново писать стриминг-состояние, остановку и повтор, ради которых затеян переход.

**7. Адрес бэкенда и права расширения не меняются.**
Запуск идёт из side panel (не из service worker), `fetch` к localhost уже разрешён. Заголовок `Accept: text/event-stream` и CORS-настройки сервера проверяются в задачах.

## Risks / Trade-offs

- [Адаптер списка тредов assistant-ui экспериментальный и может измениться] → зафиксировать точные версии пакетов; список чатов держим своим UI, адаптер используем только для переключения и загрузки истории.
- [Преобразование событий `streamEvents` в AG-UI: события субагентов и повторные вызовы могут дать лишние или дублирующиеся вызовы инструментов] → отдавать наружу только события верхнеуровневого агента и вызовы инструментов субагентов с пометкой; покрыть контрактными тестами на записанных потоках.
- [Запуск без наблюдателя тратит токены, если пользователь ушёл] → лимиты шагов и времени остаются; явная отмена и удаление чата останавливают запуск.
- [Запуск погибает вместе с процессом при перезапуске сервера] → висящих состояний в БД нет, сообщение агента пишется только по завершении; панель по `running=false` и отсутствию ответа позволяет повторить вопрос.
- [Опрос истории пока идёт запуск создаёт лишние запросы] → интервал в несколько секунд и только для открытого чата с `running=true`.
- [Пользователь не видит частичный ответ после возврата] → принято осознанно; UI показывает индикатор, готовый ответ появляется по завершении.
- [Гонка: запуск завершился между чтением истории и признаком `running`] → признак и история читаются одним запросом; сообщение агента записывается раньше, чем запись удаляется из реестра.
- [Утечка скрытых данных через события инструментов] → фильтрация на уровне инструментов остаётся (данные не попадают агенту), плюс тест, что поток не содержит скрытых ячеек.
- [Рост бандла расширения] → оценить размер сборки и подключать только нужные примитивы assistant-ui.
- [Ломающее изменение API] → сервер и расширение выкатываются вместе; расширение распространяется вручную, поэтому старые версии расширения перестанут работать до обновления.

## Migration Plan

1. Backend: добавить `POST /agent`, `run/cancel` и `threads`, оставив старые маршруты до готовности клиента; затем удалить `sheets-qa/ask` и `chat-sessions`.
2. Данные: схема БД не меняется, миграция не нужна; проверить, что существующий чат открывается и продолжает диалог (сценарий из спеки).
3. Клиент: перевести side panel на assistant-ui, убрать `use-chat`, `Message`, `ChatView` и API-клиент старых маршрутов.
4. Выкатить сервер и обновлённое расширение вместе. Откат: вернуть предыдущий коммит сервера и расширения (данные совместимы в обе стороны, так как схема не менялась).

## Open Questions

- Нужно ли показывать в UI вызовы инструментов субагентов отдельной вложенной группой или достаточно плоского списка (решается в `ui-design`, на спеки не влияет).
- Нужно ли позже подключение к идущему запуску с показом частей ответа (отдельное изменение).
- Нужна ли пометка «ответ был прерван перезапуском сервера» в истории (на спеки не влияет; сейчас вопрос остаётся без ответа).
