## Purpose

Надёжная публикация доменных событий бэкенда: событие записывается атомарно вместе с изменением, которое его породило, и доставляется каждому подписчику хотя бы один раз, даже если процесс упал.

## ADDED Requirements

### Requirement: Атомарная запись события вместе с изменением
Система SHALL записывать доменные события в той же транзакции БД, что и изменение агрегата, который их породил. Если транзакция откатилась, события MUST не сохраняться. Если транзакция закоммичена, события MUST быть сохранены. Публикация события вне транзакции MUST завершаться ошибкой, а не тихой записью вне транзакции.

#### Scenario: Изменение и событие коммитятся вместе
- **WHEN** use-case сохраняет агрегат и публикует его события в одной транзакции, и транзакция успешно завершается
- **THEN** в хранилище есть и изменение агрегата, и все его события

#### Scenario: Откат отменяет и событие
- **WHEN** после публикации события транзакция откатывается из-за ошибки
- **THEN** ни изменения агрегата, ни события в хранилище нет, и ни один подписчик его не получает

#### Scenario: Публикация вне транзакции
- **WHEN** код публикует событие, не открыв транзакцию
- **THEN** публикация завершается ошибкой и событие не сохраняется

### Requirement: Доставка каждому подписчику хотя бы один раз
Система SHALL доставлять каждое сохранённое событие каждому подписчику, зарегистрированному на его тип на момент публикации. Доставка MUST происходить хотя бы один раз, в том числе после перезапуска процесса. Повторная доставка того же события тому же подписчику MUST быть возможна, поэтому подписчики MUST быть идемпотентны. При нескольких экземплярах бэкенда одна доставка MUST не обрабатываться двумя экземплярами одновременно.

#### Scenario: Обычная доставка
- **WHEN** событие сохранено, и на его тип подписаны два подписчика
- **THEN** каждый подписчик получает событие, а обе доставки помечаются выполненными

#### Scenario: Падение процесса до обработки
- **WHEN** событие сохранено, а процесс завершился до того, как подписчик его обработал
- **THEN** после перезапуска любого экземпляра подписчик получает событие

#### Scenario: Конкурентные экземпляры
- **WHEN** два экземпляра бэкенда одновременно выбирают события для обработки
- **THEN** каждая доставка обрабатывается только одним из них

#### Scenario: Задержка обычной доставки
- **WHEN** событие закоммичено, и экземпляр, который его записал, работает нормально
- **THEN** подписчик получает событие не позже чем через настроенный интервал опроса (по умолчанию 1 секунда)

### Requirement: Независимые ретраи по подписчикам
Система SHALL вести доставку события отдельно для каждого подписчика. Ошибка одного подписчика MUST не приводить к повторной доставке другим подписчикам, уже обработавшим событие. Неудачная доставка MUST повторяться с возрастающей задержкой. После настроенного числа попыток (по умолчанию 10) доставка MUST получать статус «не доставлено» и больше автоматически не повторяться. Причина последней ошибки MUST сохраняться.

#### Scenario: Ошибка одного подписчика
- **WHEN** у события два подписчика, первый обработал его успешно, второй завершился ошибкой
- **THEN** повторно событие получает только второй подписчик, первый — нет

#### Scenario: Возрастающая задержка
- **WHEN** доставка подряд завершается ошибкой
- **THEN** каждая следующая попытка запланирована не раньше предыдущей, а интервал между попытками не уменьшается

#### Scenario: Исчерпан лимит попыток
- **WHEN** доставка завершилась ошибкой столько раз, сколько задано лимитом
- **THEN** она получает статус «не доставлено», сохраняет текст последней ошибки и больше не повторяется

#### Scenario: Неизвестный тип или повреждённые данные события
- **WHEN** у сохранённого события неизвестный тип или данные не проходят проверку схемы
- **THEN** доставка сразу получает статус «не доставлено» без повторов

### Requirement: Порядок в пределах агрегата
Система SHALL доставлять события одного агрегата одному подписчику в порядке их создания. Следующее событие агрегата MUST не доставляться подписчику, пока предыдущее не обработано или не получило статус «не доставлено». Между разными агрегатами порядок MUST не гарантироваться.

#### Scenario: Два события одной задачи
- **WHEN** у одного агрегата созданы события A, затем B, и доставка A подписчику пока завершается ошибкой
- **THEN** подписчик не получает B, пока A не будет обработано или не получит статус «не доставлено»

#### Scenario: Разные агрегаты
- **WHEN** доставка события агрегата X завершается ошибкой
- **THEN** события агрегата Y доставляются без ожидания

### Requirement: Очистка обработанных событий
Система SHALL удалять события, у которых все доставки выполнены и которые старше настроенного срока хранения (по умолчанию 7 дней). События хотя бы с одной доставкой в статусе «не доставлено» или ещё в работе MUST не удаляться.

#### Scenario: Старое обработанное событие
- **WHEN** все доставки события выполнены, и с его создания прошло больше срока хранения
- **THEN** событие удаляется при ближайшей очистке

#### Scenario: Событие с недоставленной доставкой
- **WHEN** у старого события есть доставка в статусе «не доставлено»
- **THEN** событие не удаляется

### Requirement: Наблюдаемость outbox
Система SHALL публиковать метрики:
- число обработанных доставок по подписчику и результату;
- текущее число ожидающих доставок по подписчику;
- задержку от создания события до успешной доставки.

Перевод доставки в статус «не доставлено» MUST логироваться на уровне ошибки с идентификатором события и именем подписчика.

#### Scenario: Доставка не удалась окончательно
- **WHEN** доставка получает статус «не доставлено»
- **THEN** в лог пишется ошибка с идентификатором события, именем подписчика и числом попыток, а метрика неудачных доставок этого подписчика увеличивается
