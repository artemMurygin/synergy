## Purpose

Доставка уведомлений в реальном времени по WebSocket во все открытые интерфейсы пользователя: аутентификация соединения, рассылка во все соединения пользователя, синхронизация прочтения и поведение при разрыве.

## ADDED Requirements

### Requirement: Аутентифицированное соединение
Система SHALL принимать WebSocket-соединения для уведомлений только с валидным access-токеном, переданным при установке соединения. Токен MUST не передаваться в URL. При отсутствующем, невалидном или истёкшем токене система MUST сообщать клиенту код причины (`token_invalid` или `token_expired`) и закрывать соединение. Пользователю, которому нужно сменить временный пароль, MUST отказывать с кодом `password_change_required`.

#### Scenario: Валидный токен
- **WHEN** клиент подключается с валидным access-токеном
- **THEN** соединение устанавливается и начинает получать события уведомлений этого пользователя

#### Scenario: Без токена или с невалидным токеном
- **WHEN** клиент подключается без токена или с подделанным токеном
- **THEN** клиент получает код `token_invalid`, и соединение закрывается

#### Scenario: Истёкший токен
- **WHEN** клиент подключается с истёкшим токеном
- **THEN** клиент получает код `token_expired`, и соединение закрывается

#### Scenario: Требуется смена пароля
- **WHEN** клиент подключается с токеном пользователя, которому нужно сменить временный пароль
- **THEN** клиент получает код `password_change_required`, и соединение закрывается

### Requirement: Соединение живёт не дольше токена
Система SHALL закрывать соединение, когда истекает срок действия access-токена, с которым оно установлено, и предварительно сообщать клиенту код `auth_expired`. После этого клиент MUST иметь возможность сразу переподключиться с новым токеном.

#### Scenario: Срок токена истёк во время соединения
- **WHEN** у открытого соединения наступает момент истечения его access-токена
- **THEN** клиент получает `auth_expired`, соединение закрывается, а повторное подключение с новым токеном принимается

### Requirement: Происхождение соединения
Система SHALL принимать соединения из браузерного окружения только с origin из списка разрешённых для аутентификации. Соединения без origin (нативные клиенты) MUST приниматься при валидном токене.

#### Scenario: Неразрешённый origin
- **WHEN** браузерная страница с неразрешённым origin пытается подключиться с валидным токеном
- **THEN** соединение отклоняется

#### Scenario: Расширение браузера
- **WHEN** подключается расширение manager-helper, чей origin есть в списке разрешённых
- **THEN** соединение принимается

### Requirement: Доставка во все соединения пользователя
Система SHALL отправлять событие `notification.created` с созданным уведомлением и актуальным числом непрочитанных в каждое открытое соединение получателя, на каком бы экземпляре бэкенда оно ни было открыто. Соединения других пользователей MUST не получать это событие. Повторная отправка того же уведомления MUST быть возможна, поэтому клиенты MUST распознавать повторы по идентификатору уведомления.

#### Scenario: Пользователь открыт в двух интерфейсах
- **WHEN** у пользователя открыты control-center и расширение manager-helper, и для него создаётся уведомление
- **THEN** оба соединения получают `notification.created` с этим уведомлением и одинаковым числом непрочитанных

#### Scenario: Соединения на разных экземплярах
- **WHEN** соединение получателя открыто на одном экземпляре бэкенда, а уведомление обрабатывается на другом
- **THEN** соединение получает `notification.created`

#### Scenario: Чужое уведомление
- **WHEN** создаётся уведомление для пользователя B
- **THEN** соединения пользователя A его не получают

#### Scenario: Задержка доставки
- **WHEN** создано уведомление, и соединение получателя открыто
- **THEN** соединение получает событие не позже чем через 2 секунды после создания уведомления при штатной работе

### Requirement: Синхронизация прочтения
Система SHALL после отметки уведомлений прочитанными в любом интерфейсе отправлять во все соединения этого пользователя событие `notification.read` с идентификаторами прочитанных уведомлений (или признаком «прочитаны все») и актуальным числом непрочитанных.

#### Scenario: Прочитано в одном интерфейсе
- **WHEN** пользователь отмечает уведомление прочитанным в control-center, а расширение тоже подключено
- **THEN** расширение получает `notification.read` с идентификатором этого уведомления и новым числом непрочитанных

#### Scenario: Прочитаны все
- **WHEN** пользователь вызывает «прочитать все»
- **THEN** все его соединения получают `notification.read` с признаком «прочитаны все» и числом непрочитанных 0

### Requirement: Восстановление после разрыва
Система SHALL считать БД источником истины: событие, не доставленное по WebSocket, MUST оставаться доступным через REST API. Клиент после каждого (пере)подключения MUST синхронизировать список и число непрочитанных через REST, чтобы получить пропущенное за время разрыва.

#### Scenario: Уведомление создано во время разрыва
- **WHEN** соединение клиента было разорвано, и в это время пользователю создали уведомление
- **THEN** после переподключения клиент видит это уведомление и актуальное число непрочитанных

### Requirement: Поддержание соединения
Система SHALL отправлять служебные сообщения поддержания соединения не реже чем раз в 25 секунд, чтобы среды, которые выгружают неактивный код (фоновый процесс расширения браузера), не закрывали открытое соединение.

#### Scenario: Тихий период
- **WHEN** в течение минуты пользователю не приходит ни одного уведомления
- **THEN** по соединению всё равно проходят служебные сообщения с интервалом не больше 25 секунд, и соединение остаётся открытым
