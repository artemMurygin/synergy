## Context

Мотивация описана в proposal.md (раздел Why). Ниже только то, что определяет подход.

- **Backend** (NestJS 12, Slonik/Postgres, Redis через `ioredis`, BullMQ) разложен по модулям в стиле DDD: `domain / application / infrastructure / interface`. В `shared/ddd` есть `DomainEvent`, `AggregateRoot.addEvent/pullDomainEvents` и порт `DomainEventPublisher`, но реализации у порта нет, и ни один агрегат событий не порождает. WebSocket в бэкенде нет. Стриминг агента идёт через SSE (`sheets-qa`).
- **Транзакции:** `SlonikTransactionRunner` (AsyncLocalStorage + `executor()`) лежит внутри модуля `auth`. Модуль задач транзакций не использует: `SlonikTaskRepository` пишет напрямую через пул, в том числе при сохранении задачи вместе с наблюдателями.
- **Аутентификация:** access-JWT (HS256, TTL 15 минут по умолчанию) проверяется глобальным `JwtAuthGuard`, который читает только заголовок `Authorization`. Guard не проверяет, отозвана ли сессия, и NestJS не запускает guard'ы на handshake WebSocket-шлюза. Список разрешённых origin задаётся в `AUTH_ALLOWED_ORIGINS`.
- **Несколько экземпляров:** мигратор уже рассчитан на одновременный старт нескольких экземпляров бэкенда (advisory lock). Значит, доставка не может полагаться на то, что соединение пользователя открыто на том же процессе, где создано уведомление, а обработка outbox должна быть безопасной при конкурентных обработчиках.
- **control-center (Electron):** токены хранятся только в main-процессе (`main/auth`). Renderer ходит в API через прокси `cc-api://backend/...`, который подставляет Bearer и пропускает только разрешённые префиксы (`ALLOWED_PREFIXES`). Прокси обслуживает только fetch и не умеет WebSocket.
- **manager-helper (Chrome MV3):**
  - Refresh-токен хранится в httpOnly-cookie. Access-токен у каждой части расширения свой и живёт в памяти (`shared/auth/access-token-store`).
  - Обновление токена сериализовано между частями расширения через Web Locks (`refresh-coordinator`), гонка ротации обрабатывается повтором (`RefreshRaceError`). О конце сессии части расширения узнают через `BroadcastChannel('mh-auth')`, сигнала «сессия началась» нет.
  - Service worker сейчас только отвечает на ping. Его выгружают примерно через 30 секунд без активности. С Chrome 116 отправка или получение сообщения по WebSocket сбрасывает этот таймер.
- **Правила проекта** (`.claude/rules/code-style.md`) важнее существующего кода. Порт называется с суффиксом `Port`, адаптер называется по роли, без названия технологии. `as` и `any` запрещены, внешние данные (в том числе payload из outbox) валидируются на границе. Операции над несколькими таблицами выполняются в транзакции. Логирование ведётся по `.claude/rules/logging.md`.

## Goals / Non-Goals

**Goals:**
- Единый путь «доменное событие → правило → уведомление → каналы». Новый тип события добавляется новым правилом, новый канал доставки добавляется новым адаптером. Ядро и модули-источники при этом не меняются.
- Гарантия «хотя бы один раз» на обоих шагах:
  - если изменение в модуле-источнике закоммичено, уведомление будет создано;
  - если уведомление создано, каждый канал получит его на обработку.
  Падение процесса в любой момент не приводит к потере.
- Postgres как единственный источник истины. Доставка в реальном времени лишь ускоряет показ: потеря WebSocket-сообщения не означает потерю уведомления.
- Синхронизация между интерфейсами: создание и прочтение уведомления сразу отражаются во всех открытых соединениях пользователя.
- Корректная работа с несколькими экземплярами бэкенда.

**Non-Goals:**
- Доставка «ровно один раз»: идемпотентность обеспечивают обработчики (см. п. 3).
- Глобальный порядок событий. Порядок гарантируется только в пределах одного агрегата (п. 3).
- Обмен через WebSocket в обе стороны: команды (отметка прочитанным и т. п.) идут только через REST, сокет только получает события.
- Отзыв WebSocket-соединения в момент logout на сервере. Соединение живёт не дольше access-токена, а клиент сам закрывает его при выходе.
- Хранение уведомлений ограниченное время и их очистка (очищается только обработанный outbox).

## Decisions

### 1. Модуль `notifications`: inbox как ядро, каналы как подписчики события `NotificationCreated`

Уведомление сохраняется в таблицу `notifications` всегда, и это и есть inbox пользователя. Он не считается каналом: REST API и счётчик непрочитанных работают от него.

В той же транзакции, где вставляется уведомление, в outbox пишется `NotificationCreatedEvent`. Каналы доставки подписаны на это событие и работают через порт `NotificationChannelPort { readonly channel: string; deliver(notification): Promise<void> }`. Каналы регистрируются как multi-provider под одним токеном. Для каждого канала заводится отдельный подписчик outbox, поэтому ретраи одного канала не затрагивают другие (п. 3).

В этом change один канал, `RealtimeChannel`: отправляет событие в комнату пользователя через WebSocket-шлюз. Telegram позже станет вторым адаптером и бесплатно получит от outbox ретраи и гарантию доставки. Привязка пользователя к чату — его внутреннее дело, ядро о ней не знает.

*Альтернативы:*
- Каждый модуль-источник сам вызывает «отправить уведомление». Отклонена: модуль задач стал бы знать о получателях и каналах.
- Вызывать каналы сразу после вставки уведомления, без второго события. Отклонена: при падении между вставкой и доставкой Telegram-канал потерял бы сообщение, и каналу пришлось бы строить собственную надёжность.

### 2. Триггеры через доменные события и правила

- `Task.create` порождает `TaskCreatedEvent` (`taskId`, `title`, `creatorId`, `assigneeId`). Класс события и его zod-схема лежат в публичном контракте модуля задач (`tasks/contracts`), и `notifications` импортирует только его, без внутренностей задач.
- Модуль `notifications` подписывает правила на события. Правило — функция `событие → NotificationDraft[]`. `TaskAssignedOnCreateRule` возвращает черновик для `assigneeId`, если ответственный задан и не совпадает с `creatorId`, и пустой список в остальных случаях. Логин автора для текста правило берёт через порт каталога пользователей.
- Событие называется по факту (`TaskCreated`), а не по намерению (`NotifyAssignee`). Так позже на смену ответственного можно повесить `TaskAssigneeChangedEvent` и ещё одно правило.

### 3. Transactional outbox

**Запись.** Порт в `shared/ddd` переименовывается в `DomainEventPublisherPort` по правилам именования. Его контракт: «записать события в текущую транзакцию». Адаптер `OutboxDomainEventPublisher` вставляет строки в `outbox_events` через `executor()` текущей транзакции. Вызов вне транзакции — ошибка программиста: адаптер бросает исключение, а не пишет молча через пул. Use-case выглядит так:

```
transactions.run(async () => {
  await tasks.save(task);
  await events.publish(task.pullDomainEvents());
});
```

Задача и событие записываются атомарно: либо обе, либо ничего.

**Общий `TransactionRunner`.** Порт `TransactionRunnerPort` и адаптер `TransactionRunner` (AsyncLocalStorage + `executor()`) переезжают из `auth` в `database/postgres` как общая инфраструктура. `auth` переключается на общий: это перенос без изменения поведения. Репозитории задач (`SlonikTaskRepository`, `SlonikTaskAttachmentRepository`) начинают писать через `executor()`. Попутно сохранение задачи с наблюдателями становится атомарным.

**Сериализация.** Строка outbox хранит:
- `id` — равен `DomainEvent.id`;
- `event_type` — стабильное строковое имя, например `tasks.task_created`;
- `aggregate_id`;
- `payload jsonb`;
- `metadata jsonb` (`correlationId`, `userId`, `timestamp`).

Каждый тип события регистрирует в реестре `имя → zod-схема payload → фабрика события`. Это обходится без `as`: обработчик получает уже провалидированный объект. Неизвестный тип или невалидный payload сразу помечают строку как `failed`, без ретраев.

**Обработка (relay).**
- `OutboxRelay` работает на каждом экземпляре. Пачку строк он забирает запросом `SELECT … WHERE status = 'pending' AND next_attempt_at <= now() ORDER BY created_at LIMIT N FOR UPDATE SKIP LOCKED` в короткой транзакции. Несколько экземпляров разбирают разные строки и не мешают друг другу.
- Подписка — это пара «тип события + имя подписчика». Обработка ведётся по строке на каждого подписчика: таблица `outbox_deliveries (event_id, subscriber, status, attempts, next_attempt_at, last_error)`. Её строки создаются при записи события: публикатор знает подписчиков из реестра.
- Так ретраи изолированы. Если упал Telegram-канал, повторяется только его доставка, а `RealtimeChannel` и правило уведомлений повторно не запускаются.
- Ретраи идут с экспоненциальным backoff: 1 с, 5 с, 30 с, 2 мин, 10 мин и т. д. После `OUTBOX_MAX_ATTEMPTS` (по умолчанию 10) строка получает статус `failed`, пишутся лог `error` и метрика. Ручной перезапуск — `UPDATE status = 'pending'`; утилита для этого вне рамок change.

**Порядок.** В пределах одного `aggregate_id` и подписчика доставки обрабатываются по `created_at`. Строка не берётся, если у того же агрегата и подписчика есть более ранняя необработанная. Между агрегатами порядок не гарантируется: это не нужно.

**Задержка.**
- Фоновый опрос: каждые `OUTBOX_POLL_INTERVAL_MS` (по умолчанию 1000).
- Быстрый путь: после commit `TransactionRunner` вызывает локальные after-commit-колбэки. Публикатор регистрирует колбэк «разбудить relay», и relay забирает новые строки сразу.
- Итог: на том же экземпляре задержка — единицы–десятки миллисекунд, в худшем случае — интервал опроса.
- *Отклонён* `LISTEN/NOTIFY`: требует отдельного постоянного соединения вне пула Slonik, а выигрыш над пробуждением после commit плюс опросом раз в секунду невелик.

**Идемпотентность обработчиков** (доставка «хотя бы один раз»):
- Правило уведомлений вставляет запись с `ON CONFLICT (source_event_id, recipient_id, type) DO NOTHING`. `NotificationCreatedEvent` пишется в outbox только для реально вставленных строк, и всё это в одной транзакции с отметкой доставки как `done`.
- `RealtimeChannel` при повторе пошлёт событие ещё раз. Клиент дедуплицирует по `notification.id`.
- Будущий Telegram-канал должен хранить факт отправки, например по `notificationId`. Это часть его контракта.

**Очистка.** Relay раз в час удаляет события, у которых все доставки в статусе `done` и которые старше `OUTBOX_RETENTION_DAYS` (по умолчанию 7). `failed` не удаляются.

*Альтернативы:*
- Публикация внутри процесса после commit. Отклонена: событие теряется при падении между commit и обработкой (решение пользователя).
- Отправить событие в BullMQ после commit. Отклонена: это та же двойная запись — commit в Postgres прошёл, а постановка в Redis нет. Outbox и нужен, чтобы её не было.
- BullMQ как исполнитель поверх outbox (relay кладёт задачи в очередь). Отклонён: второе хранилище состояния ради ретраев, которые и так реализуются одной таблицей. При росте нагрузки к этому можно вернуться, не меняя порт.
- Одна строка на событие вместо строки на подписчика. Отклонена: при сбое одного подписчика пришлось бы повторять всех, и все обработчики должны были бы выдерживать повторы, включая отправку в Telegram.

### 4. Транспорт: socket.io через `@nestjs/platform-socket.io` с Redis-адаптером

- Шлюз `NotificationsGateway` на namespace `/notifications`. На сервере и на клиентах разрешён только транспорт `websocket`, без long-polling.
- Каждое соединение после аутентификации входит в комнату `user:<userId>`. Отправка в комнату достигает всех соединений пользователя: несколько окон, Electron вместе с расширением, несколько устройств.
- Для нескольких экземпляров используется `@socket.io/redis-adapter` на существующем Redis через `ioredis`, отдельные pub/sub-клиенты. Адаптер подключается в `main.ts` через `app.useWebSocketAdapter`. Поэтому relay на любом экземпляре доставляет событие пользователю, подключённому к другому экземпляру.

*Альтернатива:* голый `ws` с `WsAdapter`. Пришлось бы самим писать комнаты, рассылку между экземплярами, heartbeat и переподключение на трёх клиентах. Цена принятого варианта — протокол socket.io поверх WS и зависимости: на бэкенде `@nestjs/websockets`, `@nestjs/platform-socket.io`, `@socket.io/redis-adapter`, на клиентах `socket.io-client`.

### 5. Аутентификация соединения

- Клиент передаёт access-токен в `handshake.auth.token`. Query-строка не используется, чтобы токен не попадал в логи прокси.
- В `handleConnection` шлюз проверяет токен через порт `ConnectionAuthenticatorPort`. Адаптер порта использует `AccessTokenService` из `auth`. При ошибке отправляется `error` с кодом (`token_invalid` или `token_expired`), и соединение закрывается.
- Пользователь с `mustChangePassword` получает отказ с кодом `password_change_required`, как и на REST.
- Сервер закрывает соединение в момент `exp` токена, предварительно отправив `auth_expired`. Клиент socket.io передаёт `auth` функцией, которая при каждом переподключении берёт свежий токен (с обновлением при необходимости). Поэтому переподключение после истечения токена происходит автоматически.
- Проверка origin: браузерные origin сверяются с `AUTH_ALLOWED_ORIGINS`. Соединения без `Origin` из Electron main пропускаются: в них нет cookie-аутентификации, и без валидного токена они всё равно не пройдут.

### 6. Протокол событий и восстановление после разрыва

Сервер отправляет клиенту:
- `notification.created` — `{ notification, unreadCount }`;
- `notification.read` — `{ notificationIds | all: true, unreadCount }`. Отправляется, когда пользователь прочитал уведомления в любом интерфейсе, чтобы счётчики везде совпадали.

Клиент сервер ничего не шлёт. Полезная нагрузка валидируется на клиенте zod-схемой.

`notification.read` отправляется сразу из use-case отметки прочитанным, без outbox. Это синхронизация вида, а не доставка уведомления: потерянное событие исправит следующая синхронизация по REST.

Пропущенное за время разрыва клиент не восстанавливает «дельтой». На каждое (пере)подключение он перезапрашивает через REST первую страницу и число непрочитанных. Кэш на клиенте дедуплицируется по `id`.

REST (все эндпоинты требуют access-токен и работают только с уведомлениями текущего пользователя):
- `GET /notifications?limit&page&unreadOnly`;
- `GET /notifications/unread-count`;
- `POST /notifications/{id}/read`;
- `POST /notifications/read-all`.

Точные контракты будут в specs.

### 7. Модель данных

Миграции: `016_outbox.sql`, `017_notifications.sql`.

**`outbox_events`:** `id uuid pk` (= id доменного события), `event_type`, `aggregate_id`, `payload jsonb`, `metadata jsonb`, `created_at`.

**`outbox_deliveries`:** `event_id fk`, `subscriber text`, `status` (`pending | done | failed`), `attempts int`, `next_attempt_at`, `last_error text null`, `processed_at null`; первичный ключ `(event_id, subscriber)`. Индексы:
- частичный `(next_attempt_at) where status = 'pending'` — выборка relay;
- `(subscriber, status)` — метрики и разбор `failed`.

**`notifications`:** `id uuid`, `recipient_id`, `type text` (например, `task.assigned`), `title`, `body`, `target_type` + `target_id` (ссылка на объект, сейчас `task`), `actor_id`, `source_event_id`, `created_at`, `read_at null`. Индексы:
- `(recipient_id, created_at desc)` — для списка;
- частичный `(recipient_id) where read_at is null` — для счётчика;
- уникальный `(source_event_id, recipient_id, type)` — идемпотентность правила.

Текст (`title`/`body`) формируется на сервере на русском в момент создания. Клиенты и будущий Telegram показывают его как есть, а `type` и `target` нужны для иконки и навигации. Если задачу переименуют, в старом уведомлении останется прежнее название — это осознанно: уведомление — снимок события.

### 8. control-center: соединение в main-процессе

Токен не покидает main, поэтому сокет живёт там: `main/notifications/notifications-socket.ts` использует `socket.io-client` с `auth` из `AuthService.getAccessToken`. Он подключается, когда сессия становится аутентифицированной, и закрывается при выходе (по `getSessionSignal`). События и состояние соединения (`connecting / online / offline`) уходят в renderer через `webContents.send`. Preload добавляет мост `notifications.onEvent`, `notifications.onConnectionState`.

Renderer:
- список и счётчик через TanStack Query (как `tasks.queries`) по REST через `cc-api`; в `ALLOWED_PREFIXES` добавляется `/notifications`;
- события из моста обновляют кэш;
- при переходе в `online` запросы инвалидируются (п. 6).

*Альтернатива:* выдавать renderer'у токен или одноразовый тикет. Отклонена: это ломает принятую в `add-electron-auth` модель, где renderer никогда не видит токен.

### 9. manager-helper: одно соединение в фоновом service worker

**Владелец соединения.** Сокет живёт в service worker (`src/background/notifications/`), а не в side panel. Соединение одно на всё расширение. Оно работает, пока браузер открыт и пользователь залогинен, независимо от того, открыта ли панель.

*Альтернатива:* сокет в панели плюс отдельный в SW. Отклонена: два соединения на пользователя и две логики синхронизации без выигрыша.

**Авторизация в SW.** SW использует тот же `shared/auth`:
- при старте восстанавливает сессию через refresh-cookie (`restoreSession`);
- свежий токен для `handshake.auth` берёт через `refreshAccessToken`;
- параллельное обновление токена с панелью уже безопасно благодаря Web Locks и повтору при гонке.

В `session-channel` добавляется сообщение `session-started`. Панель отправляет его после логина и смены пароля, SW на него подключается. По `session-ended` SW закрывает сокет, очищает бейдж и закрывает показанные уведомления.

**Жизнь SW.**
- Сервер шлёт ping socket.io каждые 20 с (`pingInterval`), что меньше 30-секундного порога выгрузки. Пока соединение живо, Chrome SW не выгружает. В манифесте задаётся `minimum_chrome_version: "116"`.
- Сторож: `chrome.alarms` раз в минуту будит SW и, если пользователь залогинен, а сокета нет, переподключает его.
- Подключение также запускается по `runtime.onStartup` и `runtime.onInstalled`.

**Системные уведомления.**
- Обычный случай: по `notification.created` SW проверяет, подключена ли открытая панель (п. «Связь с панелью»). Если нет, показывает `chrome.notifications.create` с `id` уведомления в качестве `notificationId` (тот же `id` не покажется дважды) и текстом `title/body` с сервера. Если панель открыта, системное уведомление не показывается: панель покажет своё всплывающее.
- Пропущенное за время, пока браузер был закрыт или SW мёртв: после каждого подключения SW запрашивает непрочитанные уведомления новее `lastSeenCreatedAt` из `chrome.storage.local`.
  - Если таких 1–3, показывает каждое.
  - Если больше, показывает одно сводное: «У вас N новых уведомлений».
  - После этого `lastSeenCreatedAt` сдвигается. Так при перезапуске браузера не будет лавины, а пропущенное не потеряется.
- Клик по уведомлению:
  - помечает его прочитанным (`POST /notifications/{id}/read`);
  - кладёт цель перехода (`target`) в `chrome.storage.session`;
  - пытается открыть панель через `chrome.sidePanel.open({ windowId })`.
  Панель при монтировании забирает цель из `chrome.storage.session` и открывает задачу. Если Chrome не даст открыть панель из обработчика клика, окно фокусируется, а цель дождётся следующего открытия панели. Клик по сводному уведомлению открывает панель на списке уведомлений.

**Бейдж.** `chrome.action.setBadgeText` показывает число непрочитанных: `99+` при переполнении, пусто при нуле и после выхода. Число обновляется по `unreadCount` из событий `notification.created` и `notification.read` и после каждой синхронизации. Так видно, что есть новое, даже когда системное уведомление уже закрыто.

**Связь с панелью.**
- Панель при открытии подключает к SW порт `chrome.runtime.connect({ name: 'notifications' })`. Пока порт открыт, SW считает панель открытой и пересылает в него события сокета и состояние соединения.
- Панель не держит своего сокета. Список и счётчик она берёт через REST (`authFetch`), а события из порта обновляют её кэш.
- Состояние «online» после переподключения SW приходит в порт, и панель перезапрашивает данные (п. 6).

**Манифест.**
- В `permissions` добавляются `notifications` и `alarms`.
- `host_permissions` не меняются: WebSocket из SW к хостам из `host_permissions` разрешён, а origin расширения уже есть в `AUTH_ALLOWED_ORIGINS`.
- Клиент socket.io в SW работает только по транспорту `websocket`: `XMLHttpRequest`, нужного для long-polling, в SW нет.

### 10. Наблюдаемость

Метрики Prometheus:
- `notifications_created_total{type}`;
- `notification_channel_failures_total{channel}`;
- gauge `notifications_ws_connections`;
- `outbox_deliveries_processed_total{subscriber,result}`;
- gauge `outbox_pending_deliveries{subscriber}`;
- `outbox_delivery_lag_seconds{subscriber}` — от `created_at` события до `done`.

Логи по `.claude/rules/logging.md`:
- подключение и отключение с `userId` и причиной, без токена;
- ошибки доставок outbox с `eventId`, `subscriber`, `attempt`;
- переход в `failed` на уровне `error`.

## Risks / Trade-offs

- **[Компромисс] Сложность.** Outbox добавляет две таблицы, relay с блокировками и backoff, реестр событий и перевод модуля задач на транзакции. → Всё это общая инфраструктура в `shared` и `database`: следующие события (аудит, CRM, Telegram) переиспользуют её бесплатно.
- **[Риск] Доставка «хотя бы один раз» даёт повторы.** → Правило идемпотентно по уникальному ключу, клиенты дедуплицируют по `id`. Для внешних каналов идемпотентность — явное требование контракта `NotificationChannelPort`.
- **[Риск] Ядовитое событие блокирует очередь агрегата** из-за упорядочивания внутри агрегата. → После `OUTBOX_MAX_ATTEMPTS` строка получает `failed` и перестаёт блокировать агрегат. Есть алерт по метрике `failed`.
- **[Риск] Изменение схемы payload** при уже лежащих в outbox событиях старой формы. → Имя события версионируется (`tasks.task_created.v2`). Обработчики старой версии живут, пока очередь по ней не опустеет. Невалидный payload сразу получает `failed`, а не бесконечные ретраи.
- **[Риск] Нагрузка опроса на БД.** → Запрос по частичному индексу раз в секунду на экземпляр, пачками. Интервал и размер пачки настраиваются.
- **[Риск] Соединение остаётся открытым после logout до истечения access-токена** (до 15 минут), если клиент не закрыл его сам. → Клиенты закрывают сокет при выходе. Сервер разрывает соединение по `exp`.
- **[Риск] Chrome всё-таки выгрузит SW** (обновление расширения, давление по памяти, политика браузера). → Сторож на `chrome.alarms` раз в минуту и дочитывание по `lastSeenCreatedAt`. Худший случай — системное уведомление придёт с опозданием до минуты, но не потеряется.
- **[Риск] `chrome.sidePanel.open` из клика по уведомлению** может быть недоступен: Chrome требует жест пользователя. → Цель перехода сохраняется в `chrome.storage.session`, окно фокусируется, задача откроется при следующем открытии панели. Проверяется при реализации на целевой версии Chrome.
- **[Компромисс] Системные уведомления только при закрытой панели.** Если панель открыта в другом окне браузера, пользователь увидит всплывающее уведомление в ней, а не системное. → Достаточно для первой версии. Учёт фокуса окна можно добавить позже, не меняя протокол.
- **[Компромисс] Минимальная версия Chrome 116.** → Сейчас это вышедшая давно стабильная версия. Расширение распространяется внутри компании, так что версия браузера под контролем.
- **[Риск] Ещё одна точка обновления токена (SW).** → Используется общий `refresh-coordinator` с Web Locks: обновление сериализовано между панелью и SW, а гонка ротации обрабатывается повтором.
- **[Риск] Redis недоступен** → `RealtimeChannel` не достучится до соединений на других экземплярах. → Ошибка публикации — повод для ретрая доставки через outbox. Уведомление в любом случае сохранено.
- **[Риск] Перенос `TransactionRunner` из `auth`** может задеть работающий логин и refresh. → Перенос без изменения поведения, существующие тесты `auth` прогоняются как регрессия.

## Migration Plan

1. Добавить миграции `016_outbox.sql` и `017_notifications.sql`. Они только добавляют таблицы и индексы, существующие данные не затрагиваются. Применяются мигратором при старте.
2. Выкатить бэкенд: общий `TransactionRunner`, outbox и relay, REST, шлюз, Redis-адаптер, публикацию событий из задач. Старые клиенты продолжают работать: новые эндпоинты им не нужны, а лишнее событие никто не слушает.
3. Выкатить control-center и manager-helper.
4. **Откат:**
   - откат клиентов не требует действий на сервере;
   - при откате бэкенда новые таблицы остаются неиспользуемыми и безвредными, а необработанные строки outbox будут дообработаны после повторного выката;
   - при необходимости таблицы удаляет отдельная миграция.

## Open Questions

- Срок хранения прочитанных уведомлений и фоновая очистка — можно решить позже, контракт API от этого не меняется.
- Ограничение на число одновременных соединений одного пользователя — понадобится только при злоупотреблениях.
- Утилита или эндпоинт для ручного перезапуска `failed`-доставок — пока достаточно SQL, нужен ли инструмент, решим по опыту эксплуатации.
