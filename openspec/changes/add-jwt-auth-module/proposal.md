## Why

API бэкенда и расширение manager-helper не защищены авторизацией: любой, кто знает адрес сервиса, может вызывать эндпоинты. Нужна классическая аутентификация по Bearer-токенам (access + refresh) с принудительной сменой выданного пароля при первом входе.

## What Changes

- Бэкенд: новый модуль авторизации (NestJS, PostgreSQL через Slonik) с эндпоинтами `login`, `refresh`, `logout`, `change-password`, `me`.
- Access-токен (JWT, короткоживущий) передаётся в заголовке `Authorization: Bearer <token>`. Глобальный guard проверяет его на всех эндпоинтах, кроме явно публичных (`/health`, `/docs`, `/openapi.json`, `login`, `refresh`).
- Refresh-токен непрозрачный, на сервере хранится только его хэш. Он ротируется при каждом обновлении; повторное использование уже заменённого токена отзывает всю цепочку сессии.
- Два способа передачи refresh. По умолчанию (расширение браузера): `httpOnly` cookie, `Secure` вне localhost, `SameSite=Strict`, `Path=/auth`; JS расширения токен не видит. Для клиентов с заголовком `X-Client-Type: desktop` (будущий Electron): refresh в теле запроса и ответа, cookie не ставится.
- Защита от CSRF для cookie-пути: белый список `Origin` (`chrome-extension://<id>`, ID закреплён через `key` в `manifest.json`), `SameSite=Strict`, узкий `Path`.
- Пользователи создаются сидером при первом разворачивании сервиса; каждому выдаётся временный пароль. Регистрации через API нет.
- У пользователя флаг `mustChangePassword`. Пока пароль не сменён, доступны только `change-password`, `me` и `logout`, остальные эндпоинты отвечают отдельной ошибкой. Новый пароль не должен совпадать с текущим.
- Расширение manager-helper: access-токен хранится только в памяти (переменная), refresh в `httpOnly` cookie, запросы идут с `credentials: 'include'`. Экран входа, автоматическое обновление по 401 с последовательными refresh между контекстами расширения, восстановление сессии при открытии панели, окно обязательной смены пароля после первого входа, выход. `host_permissions` расширения должны покрывать адрес бэкенда.
- Electron-приложение (`control-center`) в scope не входит: бэкенд поддерживает для него режим `desktop` (refresh в теле). Реализация клиента делается отдельным change.
- **BREAKING**: все существующие эндпоинты бэкенда (`sheets-qa`, `price-policy-rag`, `audit-agent`, `deal-sync` и др.) требуют валидный access-токен. Клиенты без авторизации перестают работать.

## Capabilities

### New Capabilities
- `user-auth`: бэкенд. Вход по логину и паролю, выпуск и проверка access-токена, два способа передачи refresh-токена (cookie и тело), защита cookie-пути от CSRF, ротация refresh-токена с обнаружением повторного использования, выход, сидирование пользователей с временным паролем, принудительная смена пароля при первом входе, ограничение частоты попыток входа.
- `auth-session`: расширение manager-helper. Токены (access в памяти, refresh в cookie), экран входа, автоматическое обновление токена, восстановление сессии, окно обязательной смены пароля, выход.

## Impact

- `backend/`: модули `auth` и `users`, SQL-миграция `db/migrations` (пользователи, сессии, refresh-токены), CLI-сидер пользователей, глобальный `JwtAuthGuard`, новые переменные окружения (секрет JWT, TTL токенов, начальные пользователи), throttling на `login`.
- Зависимости бэкенда: `@nestjs/jwt`, `argon2`, `@nestjs/throttler`, `cookie-parser`; настройка CORS с credentials для `chrome-extension://<id>`.
- `manager-helper/`: auth-слой в `src/shared`, экраны входа и смены пароля в sidepanel, Bearer во всех вызовах (`agent-client.ts`, `threads-api.ts`, `background`), страница options.
- Риск: поведение `SameSite`-cookie для запросов из расширения (host_permissions, блокировка сторонних cookie) слабо документировано; проверяется первой задачей (spike) до остальной работы клиента.
- `Cookie` на `localhost` общая для всех портов; закладываются уникальное имя cookie и `Path=/auth`.
- Открытые вопросы для design: TTL токенов, политика пароля, хранение refresh в Electron (`safeStorage`).
