## Context

Мотивация и состав изменения: см. `proposal.md`, требования: `specs/user-auth` и `specs/auth-session`.

Текущее состояние:
- Бэкенд: NestJS 12, PostgreSQL через Slonik (SQL-миграции в `db/migrations`, применяются при старте; Prisma используется только для MSSQL), модули разложены по слоям `domain/application/infrastructure/interface` с портами, конфигурация через zod-схему `shared/config/env.schema.ts`, ошибки через `shared/http/http-exception.filter.ts`. Авторизации нет, CORS не настроен.
- Единственный действующий клиент: расширение Chrome `manager-helper` (MV3: sidepanel, options, service worker, content-скрипты). Адрес бэкенда задаёт пользователь (`chrome.storage.sync`, по умолчанию `http://localhost:3000`), `host_permissions` покрывают localhost.
- Веб-клиента нет. `control-center` (Electron) пока заготовка и в scope не входит.
- Cookie из расширения: при наличии `host_permissions` на адрес бэкенда Chromium считает запросы расширения same-site, но поведение слабо документировано и может ломаться при блокировке сторонних cookie. Поэтому первая задача — spike с проверкой.
- Запросы к бэкенду делаются из `shared/agent-client.ts`, `shared/threads-api.ts` и background-скрипта, то есть из нескольких контекстов расширения с отдельной памятью.

## Goals / Non-Goals

**Goals:**
- Refresh-токен недоступен JS расширения (`httpOnly`).
- Режим `desktop` для будущего Electron без изменений API.
- Один общий слой авторизации в расширении вместо ручной подстановки токена в каждом вызове.
- Безопасная ротация refresh-токена при нескольких одновременно работающих контекстах расширения.

**Non-Goals:**
- Роли и права (пока все пользователи равны), SSO, регистрация, сброс пароля по e-mail, 2FA.
- Управление пользователями через API или UI (только сидер).
- Веб-клиент.
- Клиентская часть Electron.

## Decisions

### 1. Refresh: `httpOnly` cookie для расширения, тело для desktop
Для расширения refresh лежит в cookie `mh_refresh` (`HttpOnly`, `SameSite=Strict`, `Path=/auth`, `Secure` вне localhost). Расширению нужен `host_permissions` на адрес бэкенда, а запросы идут с `credentials: 'include'`. Для Electron позже: заголовок `X-Client-Type: desktop` переключает на refresh в теле (его хранит `safeStorage`), cookie не ставится.
CSRF: `refresh` и `logout` принимают только запросы с `Origin` из белого списка (`chrome-extension://<id>`; ID фиксируется через `key` в `manifest.json`), плюс `SameSite=Strict` и узкий `Path`. CORS: `Access-Control-Allow-Origin` с точным значением и `Allow-Credentials: true`.
Альтернативы: refresh в `chrome.storage.local` (токен читаем из JS расширения, нужна синхронизация контекстов, `TRUSTED_CONTEXTS`; остаётся запасным вариантом, если spike покажет, что cookie из расширения ненадёжны); `SameSite=None` (ослабляет защиту без необходимости).
Имя cookie уникально (`mh_refresh`), т.к. cookie на `localhost` общая для всех портов.

### 2. Access: JWT; refresh: непрозрачная случайная строка
- Access: JWT HS256 с `sub`, `jti`, `sid` (идентификатор сессии), `mcp` (признак `mustChangePassword`), TTL 15 минут. Проверка без обращения к БД, кроме проверки отключения пользователя (см. ниже).
- Refresh: 256 бит из CSPRNG, base64url, на сервере хранится SHA-256 хэш (случайная строка такой длины не требует медленного хэша). TTL 14 дней, абсолютный: после истечения нужен повторный вход.
Альтернативы: refresh тоже JWT (не даёт преимуществ, а отзыв всё равно требует БД); RS256 (асимметрия не нужна, проверяющая сторона одна).
TTL и секрет задаются через env (`AUTH_ACCESS_TTL`, `AUTH_REFRESH_TTL`, `JWT_SECRET`); конкретные значения можно менять без изменения спеков.

### 3. Модель данных (PostgreSQL, SQL-миграция `db/migrations/NNN_auth.sql`)
- `User`: `id`, `login` (уникальный, нижний регистр), `passwordHash`, `mustChangePassword`, `isActive`, `createdAt`, `passwordChangedAt`.
- `AuthSession`: `id`, `userId`, `createdAt`, `revokedAt`. Одна сессия соответствует одному входу на одном устройстве.
- `RefreshToken`: `id`, `sessionId`, `tokenHash` (уникальный), `expiresAt`, `usedAt`, `replacedById`. Цепочка токенов внутри сессии нужна для обнаружения повторного использования.
Пароли: argon2id. Отключение пользователя и отзыв сессии проверяются на `refresh`; access-токен остаётся действительным до конца своих 15 минут (осознанный компромисс).

### 4. Ротация и обнаружение повторного использования
`refresh` выполняется в транзакции с блокировкой строки токена. Токен со `usedAt` старше окна допуска (10 секунд) означает кражу: вся сессия отзывается. Токен со `usedAt` в пределах окна не отзывает сессию и получает ошибку «повторите» (`REFRESH_RACE`), по которой клиент перечитывает хранилище и использует уже полученные токены. Это страхует от гонок, которые клиентская синхронизация (п. 7) не покрыла, например после падения service worker.

### 5. Глобальный guard и публичные маршруты
`JwtAuthGuard` регистрируется как `APP_GUARD`. Публичные маршруты помечаются декоратором `@Public()`. Второй глобальный guard `PasswordChangeGuard` читает `mcp` из токена и пропускает только маршруты с `@AllowPendingPasswordChange()` (`change-password`, `me`, `logout`). Деталь отключения пользователя на каждый запрос не проверяется.
Альтернатива: guard на каждом контроллере (легко забыть новый контроллер, а требование спеков: защита по умолчанию).

### 6. Ограничение частоты входа
`@nestjs/throttler` с ключом по паре «IP + логин» и отдельным лимитом по IP на `login` и `change-password`. Хранилище: Redis (он уже используется для BullMQ), чтобы лимит переживал перезапуск. Значения (по умолчанию 5 неудачных попыток за 15 минут на логин) настраиваются через env. Успешный вход счётчик не сбрасывает мгновенно, чтобы не открывать перебор паролей по списку логинов.

### 7. Клиент: единый слой авторизации
- Модуль `shared/auth`: хранение access в переменной, `authFetch` (подстановка Bearer, обработка 401 и повтор), `login`, `logout`, `changePassword`, событие завершения сессии.
- Внутри контекста параллельные 401 делят один promise обновления.
- Между контекстами (панель, options, background) обновление идёт под `navigator.locks.request('auth-refresh', …)`. Cookie в браузере общая, поэтому после обновления в одном контексте второй просто обновляет ещё раз новой cookie и получает свой access-токен; повторное использование старого refresh исключено сериализацией.
- Завершение сессии рассылается через `BroadcastChannel`; остальные контексты переходят на экран входа.
- Content-скрипты запросов к бэкенду не делают и access-токена не получают: общаются с панелью и background через сообщения, как сейчас.
- Адрес бэкенда меняется пользователем: при смене адреса запрашиваются разрешения на новый хост (`chrome.permissions.request`), старая сессия сбрасывается.
Альтернатива: все запросы только через background (service worker выгружается, память для access-токена ненадёжна).

### 8. Политика пароля и смена
Минимум 10 символов, хотя бы одна буква и одна цифра, не совпадает с текущим паролем и логином. Проверка и на клиенте (быстрая ошибка), и на сервере (источник истины). Значения политики лежат в одном месте и не размазаны по контроллеру.
После смены пароля: все остальные сессии пользователя отзываются, текущей выдаётся новая пара токенов, `mcp` в новом access равен `false`.

### 9. Сидер
CLI-скрипт `backend/scripts/seed-users` (запуск вручную при первом развёртывании, в том числе в production; существующие `db/seeds` выполняются автоматически и только вне production, поэтому для паролей не подходят) читает список пользователей из `AUTH_SEED_USERS` (JSON: логин и необязательный временный пароль). Если пароль не задан, генерируется и один раз печатается в stdout. Существующие логины пропускаются. Пароли не пишутся в лог приложения (`nestjs-pino` с редактированием полей `password`, `authorization`, `refreshToken`).

## Risks / Trade-offs

- [Поведение `SameSite=Strict` для запросов расширения слабо документировано, может ломаться при блокировке сторонних cookie] → spike первой задачей на реальном Chrome (sidepanel и service worker); запасной вариант: refresh в теле и `chrome.storage.local` с `TRUSTED_CONTEXTS` (контракт `desktop` уже есть).
- [Cookie на `localhost` общая для всех портов] → уникальное имя `mh_refresh`, `Path=/auth`.
- [CSRF к `refresh`/`logout`] → белый список `Origin`, `SameSite=Strict`, узкий `Path`; запросы без `Origin` отклоняются.
- [Удалённый бэкенд требует разрешений на хост и HTTPS] → динамический запрос `host_permissions` при смене адреса; предупреждение при `http://` не для localhost.
- [Access действует до 15 минут после отключения пользователя] → короткий TTL; отключение немедленно блокирует `refresh`.
- [Ложный отзыв сессии при гонке refresh] → сериализация через Web Locks и окно допуска 10 с на сервере (п. 4); остаточный риск: пользователь входит заново.
- [BREAKING для всех клиентов] → расширение выкатывается раньше включения guard (флаг `AUTH_ENFORCED` на время перехода).
- [Перебор паролей] → throttler по логину и IP, argon2id, одинаковые ответы на неверный логин и пароль.

## Migration Plan

1. Миграция применяется автоматически при старте (`User`, `AuthSession`, `RefreshToken`), затем вручную запускается сидер и передача временных паролей пользователям.
2. Выпуск расширения с экраном входа.
3. Включение глобального guard.
Откат: отключить guard через конфигурацию и откатить расширение; таблицы авторизации можно оставить без вреда.

## Open Questions

- Конкретные значения TTL (15 минут / 14 дней), лимитов входа и политики пароля: принятые по умолчанию, меняются через env без правок спеков.
- Нужно ли расширению предупреждение при `http://` не для localhost: сейчас закладывается в ui-design.
