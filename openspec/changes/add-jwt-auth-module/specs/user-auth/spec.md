## Purpose

Аутентификация и авторизация доступа к API бэкенда по Bearer-токенам: вход по логину и паролю, короткоживущий access-токен, обновляемый refresh-токен и принудительная смена выданного временного пароля.

## ADDED Requirements

### Requirement: Защита эндпоинтов Bearer-токеном
Система SHALL требовать валидный access-токен в заголовке `Authorization: Bearer <token>` для всех эндпоинтов API, кроме публичных. Публичными MUST быть только `GET /health`, документация (`/docs`, `/openapi.json`), `login` и `refresh`. Новые эндпоинты MUST по умолчанию быть защищёнными.

#### Scenario: Запрос без токена
- **WHEN** клиент вызывает защищённый эндпоинт без заголовка `Authorization`
- **THEN** система отвечает 401 и не выполняет действие

#### Scenario: Просроченный или повреждённый токен
- **WHEN** клиент вызывает защищённый эндпоинт с просроченным, повреждённым или подписанным чужим ключом access-токеном
- **THEN** система отвечает 401 с кодом, по которому клиент отличает «токен истёк» от «токен недействителен»

#### Scenario: Публичный эндпоинт
- **WHEN** клиент вызывает `GET /health` без токена
- **THEN** система отвечает как обычно

### Requirement: Вход по логину и паролю
Система SHALL выдавать пару токенов (access и refresh) в ответ на корректные логин и пароль. Ответ MUST содержать access-токен, срок жизни access-токена и признак `mustChangePassword`; refresh-токен передаётся способом, определяемым типом клиента (см. «Способы передачи refresh-токена»). Пароли MUST храниться только в виде необратимого хэша.

#### Scenario: Успешный вход
- **WHEN** клиент отправляет верные логин и пароль
- **THEN** система возвращает access-токен, срок жизни access-токена и текущее значение `mustChangePassword`, а refresh-токен передаёт выбранным для клиента способом

#### Scenario: Неверные учётные данные
- **WHEN** клиент отправляет несуществующий логин или неверный пароль
- **THEN** система отвечает 401 с одинаковым сообщением в обоих случаях, не раскрывая, существует ли пользователь

#### Scenario: Отключённый пользователь
- **WHEN** вход пытается выполнить пользователь, помеченный как отключённый
- **THEN** система отвечает так же, как при неверных учётных данных

### Requirement: Ограничение частоты попыток входа
Система SHALL ограничивать число неудачных попыток входа для одного логина и для одного адреса клиента за интервал времени. При превышении лимита система MUST отвечать 429 с указанием времени до повторной попытки.

#### Scenario: Превышение лимита попыток
- **WHEN** клиент делает подряд больше допустимого числа неудачных попыток входа
- **THEN** система отвечает 429 и не проверяет пароль до истечения интервала

#### Scenario: Успешный вход после ожидания
- **WHEN** интервал ограничения истёк и клиент отправляет верные данные
- **THEN** система выполняет вход

### Requirement: Способы передачи refresh-токена
Система SHALL по умолчанию передавать refresh-токен только в cookie с атрибутами `HttpOnly`, `SameSite=Strict`, `Path=/auth` (и `Secure` вне localhost) и MUST не включать его в тело ответа. Для клиентов, явно заявивших тип `desktop` заголовком `X-Client-Type`, система SHALL передавать refresh-токен в теле ответа и принимать его в теле запроса, не устанавливая cookie.

#### Scenario: Вход cookie-клиента
- **WHEN** клиент без заголовка `X-Client-Type` успешно входит
- **THEN** ответ содержит заголовок `Set-Cookie` с `HttpOnly` и `SameSite=Strict`, а тело ответа не содержит refresh-токена

#### Scenario: Вход desktop-клиента
- **WHEN** клиент с `X-Client-Type: desktop` успешно входит
- **THEN** тело ответа содержит refresh-токен, а `Set-Cookie` отсутствует

#### Scenario: Неизвестный тип клиента
- **WHEN** клиент передаёт неизвестное значение `X-Client-Type`
- **THEN** система отклоняет запрос с ошибкой валидации

### Requirement: Защита cookie-эндпоинтов от CSRF
Эндпоинты, принимающие refresh-токен из cookie (`refresh`, `logout`), SHALL выполняться только для запросов, у которых заголовок `Origin` входит в настроенный белый список. Остальные запросы MUST отклоняться с 403 до любой работы с токеном.

#### Scenario: Разрешённый источник
- **WHEN** запрос `refresh` приходит с `Origin` из белого списка и валидной cookie
- **THEN** система выполняет обновление

#### Scenario: Чужой источник
- **WHEN** запрос `refresh` приходит с `Origin` не из белого списка
- **THEN** система отвечает 403, не ротирует токен и не отзывает сессию

#### Scenario: Запрос без Origin
- **WHEN** запрос `refresh` с cookie приходит без заголовка `Origin`
- **THEN** система отвечает 403

### Requirement: Обновление токенов с ротацией
Система SHALL по действующему refresh-токену (из cookie или из тела запроса в зависимости от типа клиента) выдавать новую пару токенов, при этом использованный refresh-токен MUST немедленно перестать быть действительным. На сервере refresh-токены MUST храниться только в виде хэша. Refresh-токен MUST иметь ограниченный срок жизни.

#### Scenario: Успешное обновление
- **WHEN** клиент отправляет действующий refresh-токен
- **THEN** система возвращает новый access-токен и новый refresh-токен, а старый refresh-токен больше не принимается

#### Scenario: Просроченный refresh-токен
- **WHEN** клиент отправляет refresh-токен с истёкшим сроком жизни
- **THEN** система отвечает 401 и клиент должен выполнить повторный вход

#### Scenario: Неизвестный refresh-токен
- **WHEN** клиент отправляет refresh-токен, которого система не выдавала
- **THEN** система отвечает 401

### Requirement: Обнаружение повторного использования refresh-токена
Система SHALL считать скомпрометированной сессию, если уже заменённый refresh-токен предъявлен повторно после короткого окна допуска на гонку параллельных запросов. В этом случае система MUST отозвать все refresh-токены этой сессии. Повторное предъявление в пределах окна допуска MUST не отзывать сессию.

#### Scenario: Повторное предъявление старого токена
- **WHEN** клиент предъявляет refresh-токен, который уже был заменён, и окно допуска истекло
- **THEN** система отвечает 401 и отзывает все токены этой сессии, так что действующий токен сессии тоже перестаёт приниматься

#### Scenario: Параллельное обновление в окне допуска
- **WHEN** два запроса с одним и тем же refresh-токеном приходят почти одновременно в пределах окна допуска
- **THEN** система не отзывает сессию и отвечает на второй запрос ошибкой, позволяющей клиенту повторить попытку с актуальным токеном

### Requirement: Выход
Система SHALL по запросу выхода отзывать refresh-токен текущей сессии, а для cookie-клиентов MUST также удалять cookie. Выход MUST быть идемпотентным.

#### Scenario: Выход из сессии
- **WHEN** авторизованный клиент вызывает выход
- **THEN** refresh-токен сессии перестаёт приниматься, а попытка обновления по нему возвращает 401

#### Scenario: Повторный выход
- **WHEN** клиент вызывает выход с уже отозванным refresh-токеном или без него
- **THEN** система отвечает успешно

### Requirement: Профиль текущего пользователя
Система SHALL возвращать авторизованному клиенту данные текущего пользователя: идентификатор, логин и `mustChangePassword`.

#### Scenario: Получение профиля
- **WHEN** клиент с валидным access-токеном запрашивает профиль
- **THEN** система возвращает идентификатор, логин и `mustChangePassword`, но не пароль и не его хэш

### Requirement: Сидирование пользователей
Система SHALL создавать пользователей сидером при первом развёртывании. Каждому пользователю сидер MUST назначать временный пароль и устанавливать `mustChangePassword = true`. Повторный запуск сидера MUST не перезаписывать существующих пользователей и их пароли. Публичной регистрации MUST не быть.

#### Scenario: Первый запуск сидера
- **WHEN** сидер запускается на пустой базе с заданным списком пользователей
- **THEN** создаются пользователи с хэшами временных паролей и `mustChangePassword = true`

#### Scenario: Повторный запуск сидера
- **WHEN** сидер запускается, когда пользователь с таким логином уже существует
- **THEN** существующий пользователь и его пароль остаются без изменений

### Requirement: Принудительная смена временного пароля
Система SHALL разрешать пользователю с `mustChangePassword = true` только смену пароля, получение профиля и выход. Остальные защищённые эндпоинты MUST отвечать 403 со специальным кодом `PASSWORD_CHANGE_REQUIRED`. Смена пароля MUST требовать текущий пароль и новый пароль, отличающийся от текущего и удовлетворяющий политике пароля. После успешной смены система MUST сбросить `mustChangePassword`, отозвать все прочие сессии пользователя и выдать новую пару токенов для текущей.

#### Scenario: Доступ до смены пароля
- **WHEN** пользователь с `mustChangePassword = true` вызывает защищённый эндпоинт, кроме смены пароля, профиля и выхода
- **THEN** система отвечает 403 с кодом `PASSWORD_CHANGE_REQUIRED`

#### Scenario: Успешная смена пароля
- **WHEN** пользователь отправляет верный текущий пароль и допустимый новый пароль
- **THEN** `mustChangePassword` становится `false`, система возвращает новую пару токенов, а прочие сессии пользователя отзываются

#### Scenario: Новый пароль совпадает с текущим
- **WHEN** новый пароль совпадает с текущим (временным)
- **THEN** система отклоняет запрос с ошибкой валидации и не меняет пароль

#### Scenario: Неверный текущий пароль
- **WHEN** пользователь отправляет неверный текущий пароль
- **THEN** система отвечает ошибкой, не меняет пароль и учитывает попытку в ограничении частоты

#### Scenario: Слабый новый пароль
- **WHEN** новый пароль не удовлетворяет политике пароля
- **THEN** система отклоняет запрос с ошибкой валидации и перечисляет нарушенные правила
