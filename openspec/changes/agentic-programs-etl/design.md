## Context

Мотивация и границы change описаны в `proposal.md`, наблюдаемое поведение — в `specs/`.

В backend уже есть NestJS, LangChain, OpenAI, BullMQ, Redis, PostgreSQL и Pino. Действующий `audit-agent` показывает целевой способ интеграции: application use-case зависит от портов, а LangChain, очередь, Google Sheets и Postgres остаются в инфраструктурных адаптерах.

Единица работы меняется с одного листа на группу из `backend/src/modules/price-policy-rag/tabels-links/groups.json`. Группа может содержать листы из разных Google-таблиц, а агент сам решает, какие диапазоны прочитать. Схема каталога и миграции `004`–`008` сохраняются.

## Goals / Non-Goals

**Goals:**

- изолировать агентный runtime за application-портом;
- дать агенту инструменты для выборочного чтения листов назначенной группы;
- получать структурированные записи каталога с происхождением;
- запускать, повторять и наблюдать синхронизацию на уровне группы;
- сохранить зависимости направленными к domain/application, чтобы менять agent runtime и внешние сервисы без переписывания use-case.

**Non-Goals:**

- не вводить отдельную карту колонок или набор парсеров по типам листов;
- не добавлять в этом change отдельные проверки точных значений, полноты выгрузки или транзакции на всю группу;
- не расширять схему каталога для FAQ без программы, альтернативных курсов, школы и ординатуры;
- не вводить human-in-the-loop и интерфейс ручного редактирования результата агента;
- не удалять сохранённые миграции и таблицу `sheet_mapping`.

## Decisions

### D1. Deep Agents JS как runtime агента

Адаптер агента будет использовать `createDeepAgent` из Deep Agents JS с моделью `ChatOpenAI`, набором инструментов и `responseFormat` для структурированного ответа. В первой версии не нужны filesystem backend, субагенты и QuickJS: контекст ограничен одной группой, а нужные данные агент читает через узкие tools.

Почему Deep Agents: встроенное планирование и управление контекстом подходят для неоднородных групп листов, но не заставляют заранее фиксировать маршрут чтения.

Альтернатива: собственный `StateGraph` в LangGraph. Он даёт больше контроля над узлами, checkpointing и retry policy, но заставляет кодировать граф для процесса, который по замыслу должен адаптироваться к содержимому группы. Кроме того, повторы запусков уже оркестрирует BullMQ.

### D2. Agent runtime и внешние сервисы скрыты за портами

Модуль `programs-etl` сохранит слои `domain`, `application`, `infrastructure` и `interface`.

- `application` владеет use-case групповой синхронизации, моделями workflow (группа, источник, fingerprint, provenance, mutation plan и состояние запуска) и портами агента, реестра групп, чтения Sheets, чтения и записи каталога, учёта запусков и метрик;
- `domain` содержит только бизнес-модель каталога программ и её инварианты без типов ETL workflow и импортов NestJS, LangChain, BullMQ и Google API;
- `infrastructure` реализует порты через Deep Agents, Google Sheets, Postgres, BullMQ и Prometheus;
- `interface` содержит BullMQ processor и scheduler как driver adapters.

В NestJS composition root порты регистрируются через явные DI-токены. Адаптеры не передают свои SDK-типы в application и domain.

Альтернатива: вызывать Deep Agents, Google API и SQL напрямую из одного NestJS-сервиса. Это короче, но связывает оркестрацию с SDK, усложняет тесты и замену agent runtime.

### D3. Агент читает листы и текущий каталог через узкие tools

Для каждого запуска agent adapter создаёт новый набор tools, замкнутый на `group_id` и `run_id`. Модель не передаёт `group_id` в каждом вызове и не может подменить его: область доступа задаётся при создании tools. Инструменты только читают данные и не меняют Google Sheets или каталог.

#### `list_group_sources`

Инструмент даёт агенту карту доступных источников перед выбором диапазонов. Он не обращается в Google API, а читает уже загруженное определение текущей группы.

**Вход:** пустой объект. Контекст группы уже привязан к экземпляру tool.

**Выход:**

- `group`: `id`, человекочитаемое название, `status` и `note` с пояснением связей между листами;
- `sources[]`: стабильный в рамках запуска `source_id`, `spreadsheet_id`, `sheet_id`, `title`, `role` и URL листа;
- источники возвращаются в порядке из `groups.json`, чтобы одинаковая группа давала стабильный контекст.

`role` и `note` являются подсказками для рассуждения, а не жёстким маршрутом: агент может читать любой лист текущей группы и сам выбирает порядок чтения. Если группа или её список источников не загружены, use-case завершается до запуска агента.

#### `read_sheet_range`

Инструмент читает один диапазон конкретного листа. Агент выбирает диапазон после `list_group_sources` и может вызывать tool повторно, чтобы читать большой лист частями или уточнять отдельные блоки.

**Вход:**

- `source_id` — идентификатор из `list_group_sources`; агент не передаёт Google-идентификаторы напрямую;
- `range` — A1-диапазон без названия листа, например `A1:Z200`;
- диапазон должен содержать явные границы строк; запрос всех строк вида `A:Z` не принимается.

**Выход:**

- `source`: `source_id`, `spreadsheet_id`, `sheet_id` и `title`;
- `requested_range` и `returned_range`, чтобы агент видел, какая часть запроса фактически прочитана;
- `rows[]`: `row_no` и `cells`, где ячейка содержит имя колонки и форматированное значение; пустые ячейки сохраняют позицию колонки;
- `truncated` и `next_range`: если ответ достиг конфигурируемого лимита ячеек, tool возвращает диапазон для следующего вызова.

Каждый ответ содержит координаты источника, необходимые structured response для происхождения. Лимит ячеек защищает контекст модели; он не меняет содержимое ячеек.

#### `search_catalog_records`

Инструмент ищет кандидатов в текущем каталоге, чтобы агент мог отличить новую запись от изменившейся существующей.

**Вход:** `record_type` и один или несколько поисковых признаков: организация, уровень, код направления, название, профиль, квалификация или `source_id`. Ответ ограничен небольшим числом наиболее близких кандидатов.

**Выход:** `record_id`, `record_type`, поля естественного ключа, человекочитаемые названия и краткий список привязанных источников. Tool не возвращает векторы, полные текстовые фрагменты или всю базу.

#### `get_catalog_record`

Инструмент загружает одну найденную запись по её `record_type` и `record_id`. Для программы ответ включает основные поля, предложения, цены, требования, метаданные фрагментов и связи с источниками. Полный текст фрагмента возвращается только при явном запросе конкретного раздела.

#### `list_source_records`

Инструмент возвращает записи каталога, уже связанные с заданным `source_id` или строкой источника. Он нужен, когда название или естественный ключ изменились: связь с источником позволяет найти прежний `record_id` и обновить запись, а не создать дубль.

Все три инструмента каталога read-only и работают через application-owned query port. Агент не получает SQL, имя таблицы или произвольный фильтр. `record_id`, который агент использует в плане обновления, должен быть получен через один из этих tools в текущем запуске.

#### Ошибки и наблюдаемость tools

- `SOURCE_NOT_IN_GROUP` — `source_id` не принадлежит текущей группе; ошибка не повторяется;
- `INVALID_RANGE` — диапазон не является допустимым ограниченным A1-диапазоном; ошибка не повторяется;
- `SOURCE_UNAVAILABLE` — Google Sheets не вернул лист или диапазон;
- `RATE_LIMITED` и `TIMEOUT` — временные ошибки Google API.
- `RECORD_NOT_FOUND` — запрошенной записи каталога больше нет; агент повторяет поиск или выбирает `create`;
- `CATALOG_UNAVAILABLE` — временная ошибка query-адаптера каталога.

Адаптер Google Sheets может кратко повторить временную ошибку внутри одного tool call. Если прочитать источник всё ещё нельзя, ошибка выходит из agent adapter и завершает групповой запуск в соответствии со спеком.

Для каждого tool call структурный лог содержит `group_id`, `run_id`, имя tool, длительность и код ошибки. Для Sheets-tools добавляются `source_id`, диапазон и число строк; для catalog-tools — `record_type`, `record_id` и число кандидатов. Содержимое ячеек и полные данные записей в лог не включаются.

Альтернатива: загружать все листы группы в prompt. Это упрощает tools, но увеличивает контекст, стоимость и риск превышения лимита модели.

### D4. `groups.json` остаётся реестром заданий

Адаптер реестра загружает `groups.json` и выдаёт application-слою группы со стабильным `group_id`, названием, статусом, заметкой и списком листов. В первой версии планировщик ставит в очередь только `ready`. `needs_matching`, `out_of_scope_schema` и `deferred` не запускаются; отдельный ручной вход для них в этот change не входит.

Альтернатива: перенести группы в Postgres. Отклонено для первой версии: группы редко меняются, а версионируемый JSON уже является источником правды.

### D5. Ежечасный scan ставит изменённые листы в групповую очередь

BullMQ scheduler каждый час запускает лёгкую задачу `scan-sources`. Она загружает наблюдаемые листы из `groups.json`, читает их содержимое пакетно и вычисляет стабильный `observed_hash` по форматированным значениям и координатам заполненных ячеек.

`observed_hash` сравнивается с `content_hash` в `source_sheet`. `content_hash` означает не «последний увиденный», а «последний успешно обработанный» отпечаток. Поэтому ошибка агента не поглощает изменение: на следующем scan лист снова будет изменённым.

Изменённые листы сопоставляются с группами. В очередь ставится одна задача `sync-group` на каждую затронутую группу, а не отдельная агентная задача на каждый лист. Данные job содержат:

- `group_id` и `run_id`;
- `changed_sources[]` с `source_id` и `observed_hash`;
- при явном повторе `previous_run_id`.

Если несколько листов одной группы изменились за один scan, они объединяются в один job. Агент получает список изменённых листов, но может читать и неизменённые листы той же группы, если они нужны для сопоставления.

`ScanProgramSourcesUseCase` не создаёт run и job самостоятельно: он передаёт `group_id` и `changed_sources` внутреннему `ScheduleProgramsGroupSyncService`. Этот application-сервис централизует создание run и идемпотентный enqueue для hourly scan и повторного запуска failed-run. Отдельного `StartProgramsSyncUseCase` нет, поскольку в change отсутствует ручной входной адаптер.

После успешного применения плана изменений `content_hash` каждого листа из `changed_sources` обновляется его `observed_hash`. До этого момента отпечаток не продвигается.

Повторы транзиентных ошибок выполняет BullMQ с ограниченным числом попыток и exponential backoff. Явный повтор после завершённой ошибки создаёт новый `run_id` и ссылается на предыдущий запуск.

Альтернатива: checkpointing в LangGraph/Deep Agents как основной механизм повтора. Отклонено: очередь уже даёт единую модель повторов для backend, а возобновление с промежуточного шага не требуется спеками.

### D6. История запусков хранится в Postgres

Новая миграция добавит таблицу запусков с `run_id`, `group_id`, `previous_run_id`, статусом, временем начала/завершения и краткой причиной ошибки. Таблица не дублирует payload или содержимое листов. Структурные логи и метрики включают `group_id`, `run_id`, фазу, длительность и исход.

Почему Postgres, а не только BullMQ: очередь имеет ограниченную ретенцию, а история нужна для повтора и наблюдаемости после удаления job.

Альтернатива: хранить историю только в Redis/BullMQ. Отклонено из-за ретенции и слабой пригодности для аудита запусков.

### D7. Запись каталога остаётся отдельным адаптером

Агент не выполняет запись сам. Его structured response содержит mutation plan с операциями `create` и `update`, типом записи, данными, ссылками на источники и, для `update`, существующим `record_id`. Application use-case передаёт этот план в порт записи каталога.

Postgres-адаптер маппит операции на существующие таблицы `organization`, `faculty`, `location`, `program`, `offer`, `price`, `entrance_requirement`, справочники и `content_chunk`. Для `create` он использует application-модель `ProgramMatchKey`, повторяющую два уникальных индекса существующей схемы, и возвращает новый ID; этот ключ обеспечивает поиск и идемпотентность ETL, но не заменяет UUID-идентичность доменной сущности `Program`. Для `update` адаптер изменяет запись по `record_id`. Зависимые операции в плане ссылаются на локальные ключи, чтобы полученный ID программы можно было передать её предложениям и фрагментам.

Текущий одиночный `source_row_id` не описывает запись, собранную из нескольких листов. Новая миграция добавит link-таблицы с реальными FK для связи записей каталога с `raw_row`, `group_id` и `last_seen_run_id`. Связь многие-ко-многим позволяет одной записи иметь несколько источников, а `list_source_records` — находить её по изменённому листу. Существующие `source_row_id` и миграция `004` не удаляются.

Запись выполняется по операциям репозитория; новая транзакционная граница на всю группу в этом change не вводится.

Альтернатива: дать агенту SQL-tools. Отклонено: это связывает модель с физической схемой БД, усложняет тесты и позволяет обойти application-границу.

### D8. Тесты разделены по границам

- domain-тесты проверяют инварианты каталога программ и его value objects;
- application-тесты проверяют типы workflow, переходы состояния запуска и групповую оркестрацию с in-memory портами;
- контрактные тесты адаптеров подменяют OpenAI и Google Sheets;
- интеграционные тесты прогоняют BullMQ, Postgres и повтор запуска на минимальной группе.

## Risks / Trade-offs

- **[Непредсказуемые tool calls и рост стоимости]** → ограничить число шагов, timeout запуска, размер ответа tool и конкурентность worker.
- **[Большой лист не помещается в один ответ]** → `read_sheet_range` возвращает ограниченные диапазоны; агент может читать лист частями.
- **[Связи между листами неоднозначны]** → передавать агенту `role`, `status` и `note` группы, а непредставимые отношения не записывать как сущности другого типа.
- **[Падение worker после внешнего побочного эффекта]** → BullMQ повторит job; операции записи должны быть идемпотентны по естественным ключам существующей схемы.
- **[Изменение контракта Deep Agents]** → зафиксировать совместимую версию и изолировать SDK в одном адаптере.
- **[Часть данных может быть записана до ошибки]** → принятый trade-off отражается в статусе запуска; повторная запись опирается на идемпотентные операции репозитория.

## Migration Plan

1. Добавить зависимости Deep Agents JS и Google Sheets SDK, миграции истории запусков и source-link таблиц, а также конфигурацию agent runtime и ежечасного scan.
2. Собрать `programs-etl` с портами и адаптерами, но держать scheduler выключенным конфигурацией.
3. Прогнать контрактные и интеграционные тесты, затем временно включить scheduler в тестовом окружении для одной группы `ready`.
4. После проверки логов, метрик, истории запуска и записанного каталога включить плановые запуски `ready`-групп с ограниченной конкурентностью.

Откат: отключить hourly scheduler и остановить worker групповой синхронизации. Таблицы истории запусков, source links и существующие миграции не удалять; уже записанные данные каталога остаются доступны.
