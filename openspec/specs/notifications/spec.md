# notifications Specification

## Purpose
Уведомления пользователей: правила, по которым события системы превращаются в уведомления; хранение уведомлений как личного inbox получателя; REST API для чтения и отметки прочитанным; расширяемая доставка по каналам.

## Requirements

### Requirement: Поля уведомления
Система SHALL хранить для каждого уведомления:
- идентификатор;
- получателя;
- тип (например, `task.assigned`);
- заголовок;
- текст;
- ссылку на объект: тип объекта и его идентификатор, сейчас типы `task`, `chat`, `request` и `bug`;
- инициатора, если он есть;
- время создания;
- время прочтения (пусто, пока уведомление не прочитано).

Заголовок и текст MUST формироваться на сервере на русском языке в момент создания и потом не меняться.

#### Scenario: Уведомление о назначении задачи
- **WHEN** создаётся уведомление о том, что пользователю назначена задача «Подготовить КП» пользователем `ivanov`
- **THEN** уведомление содержит тип `task.assigned`, заголовок и текст с названием задачи и логином инициатора, ссылку на объект типа `task` с идентификатором задачи, время создания и пустое время прочтения

#### Scenario: Переименование объекта после создания уведомления
- **WHEN** задачу, на которую ссылается уведомление, переименовали
- **THEN** заголовок и текст уведомления не меняются, а ссылка на объект по-прежнему ведёт на эту задачу

#### Scenario: Уведомление со ссылкой на заявку
- **WHEN** создаётся уведомление о решении по заявке
- **THEN** уведомление содержит ссылку на объект типа `request` с идентификатором заявки

#### Scenario: Уведомление со ссылкой на баг
- **WHEN** создаётся уведомление о смене статуса бага
- **THEN** уведомление содержит ссылку на объект типа `bug` с идентификатором бага

### Requirement: Уведомление ответственного при создании задачи
Система SHALL создавать уведомление типа `task.assigned` для ответственного, когда создаётся задача с ответственным. Если ответственный совпадает с создателем, уведомление MUST не создаваться. Если ответственный не указан, уведомление MUST не создаваться. Повторная обработка того же события создания задачи MUST не создавать второе уведомление тому же получателю.

#### Scenario: Задача назначена другому сотруднику
- **WHEN** пользователь A создаёт задачу с ответственным B
- **THEN** у B появляется одно непрочитанное уведомление `task.assigned` со ссылкой на эту задачу и инициатором A

#### Scenario: Задача назначена самому себе
- **WHEN** пользователь A создаёт задачу, указав ответственным себя
- **THEN** уведомление не создаётся

#### Scenario: Задача без ответственного
- **WHEN** пользователь создаёт задачу без ответственного
- **THEN** уведомление не создаётся

#### Scenario: Повторная обработка события
- **WHEN** событие создания задачи обрабатывается повторно
- **THEN** у ответственного по-прежнему одно уведомление об этой задаче

#### Scenario: Создание задачи не ломается из-за уведомлений
- **WHEN** создание уведомления временно завершается ошибкой
- **THEN** задача всё равно создаётся и `POST /tasks` отвечает 201, а уведомление появляется после успешного повтора

### Requirement: Список своих уведомлений
Система SHALL возвращать по `GET /notifications` страницу уведомлений текущего пользователя, новые первыми, с пагинацией (`limit`, `page`, как в остальных списках API) и общим числом записей. Система MUST поддерживать фильтр `unreadOnly=true`. Уведомления других пользователей MUST никогда не попадать в ответ.

#### Scenario: Первая страница
- **WHEN** у пользователя 30 уведомлений, и он запрашивает список с `limit=20`
- **THEN** система отвечает 200 и возвращает 20 самых новых уведомлений и общее число 30

#### Scenario: Только непрочитанные
- **WHEN** пользователь запрашивает список с `unreadOnly=true`
- **THEN** система возвращает только уведомления с пустым временем прочтения

#### Scenario: Чужие уведомления
- **WHEN** у пользователей A и B есть уведомления, и A запрашивает список
- **THEN** ответ содержит только уведомления A

#### Scenario: Недопустимые параметры
- **WHEN** клиент передаёт `limit` больше максимального или нечисловую страницу
- **THEN** система отвечает 400

### Requirement: Число непрочитанных
Система SHALL возвращать по `GET /notifications/unread-count` число непрочитанных уведомлений текущего пользователя.

#### Scenario: Есть непрочитанные
- **WHEN** у пользователя 3 непрочитанных и 5 прочитанных уведомлений
- **THEN** система отвечает 200 с числом 3

### Requirement: Отметка прочитанным
Система SHALL отмечать уведомление прочитанным по `POST /notifications/{id}/read` и все уведомления текущего пользователя — по `POST /notifications/read-all`. Обе операции MUST возвращать актуальное число непрочитанных. Повторная отметка уже прочитанного уведомления MUST быть успешной и не менять его время прочтения. Отметка чужого или несуществующего уведомления MUST отвечаться 404.

#### Scenario: Прочитать одно
- **WHEN** пользователь отмечает прочитанным своё непрочитанное уведомление
- **THEN** система отвечает 200, записывает время прочтения и возвращает число непрочитанных, уменьшенное на 1

#### Scenario: Повторное прочтение
- **WHEN** пользователь отмечает прочитанным уже прочитанное уведомление
- **THEN** система отвечает 200, время прочтения не меняется

#### Scenario: Чужое уведомление
- **WHEN** пользователь отмечает прочитанным уведомление другого пользователя
- **THEN** система отвечает 404 и не меняет уведомление

#### Scenario: Прочитать все
- **WHEN** пользователь вызывает `POST /notifications/read-all`
- **THEN** все его непрочитанные уведомления получают время прочтения, а система возвращает актуальное число непрочитанных (0, если за это время не появилось новых уведомлений)

### Requirement: Доступ к уведомлениям
Система SHALL требовать валидный access-токен для всех эндпоинтов уведомлений. Пользователь, которому нужно сменить временный пароль, MUST получать тот же отказ, что и на остальных защищённых эндпоинтах.

#### Scenario: Запрос без токена
- **WHEN** клиент вызывает любой эндпоинт уведомлений без access-токена
- **THEN** система отвечает 401

### Requirement: Расширяемая доставка по каналам
Система SHALL передавать каждое созданное уведомление всем подключённым каналам доставки, причём каждому хотя бы один раз. Ошибка доставки в одном канале MUST не влиять на другие каналы и на сохранность уведомления. Новый канал доставки MUST подключаться без изменения правил создания уведомлений и модулей — источников событий. Если каналы доставки недоступны, уведомление MUST оставаться доступным через REST API.

#### Scenario: Канал временно недоступен
- **WHEN** канал доставки реального времени завершился ошибкой для созданного уведомления
- **THEN** уведомление доступно в `GET /notifications`, а доставка через этот канал повторяется

#### Scenario: Один канал упал, другой работает
- **WHEN** подключены два канала, и один из них завершается ошибкой
- **THEN** второй канал доставляет уведомление, а повторяется только доставка через упавший канал

### Requirement: Уведомление о готовности расшифровки
Система SHALL создавать владельцу записи уведомление, когда в чат добавлено сообщение о результате расшифровки:
- тип `meeting-transcript.ready` для статусов `completed` и `no_speech`;
- тип `meeting-transcript.failed` для статуса `failed`.

Ссылка на объект MUST вести на чат (тип объекта `chat`, идентификатор чата). Заголовок и текст MUST содержать имя записи и MUST NOT содержать текст расшифровки. Если сообщение в чат не добавлено (запись не из чата или чат удалён), уведомление MUST NOT создаваться. Повторная обработка события MUST NOT создавать второе уведомление.

#### Scenario: Расшифровка готова
- **WHEN** в чат добавлено сообщение о готовой расшифровке `встреча.m4a`
- **THEN** у владельца появляется одно непрочитанное уведомление `meeting-transcript.ready` со ссылкой на этот чат и именем записи

#### Scenario: Запись загружена не через чат
- **WHEN** расшифровка записи, не отправленной ни в один чат, завершилась
- **THEN** уведомление не создаётся

### Requirement: Уведомление постановщика о задаче от его имени
Система SHALL создавать уведомление типа `task.created-on-behalf` для создателя (постановщика) задачи, если он отличается от инициатора. Инициатором в уведомлении MUST быть пользователь, фактически поставивший задачу. Ссылка MUST вести на задачу. Это уведомление MUST создаваться независимо от уведомления ответственному `task.assigned`. Если постановщик одновременно ответственный, MUST создаваться оба уведомления. Повторная обработка события MUST NOT создавать второе уведомление.

#### Scenario: Задача поставлена от имени Петра
- **WHEN** пользователь A через агента ставит задачу с постановщиком B и ответственным C
- **THEN** B получает уведомление `task.created-on-behalf` с инициатором A, C получает `task.assigned`

#### Scenario: Постановщик совпадает с инициатором
- **WHEN** пользователь создаёт задачу, где постановщик — он сам
- **THEN** уведомление `task.created-on-behalf` не создаётся

### Requirement: Уведомление автора о решении по заявке
Система SHALL создавать автору заявки уведомление, когда по его заявке принято решение:
- тип `request.accepted` при принятии в навык; заголовок и текст MUST содержать название заявки, название навыка и его текущий статус на русском языке;
- тип `request.rejected` при отклонении; заголовок и текст MUST содержать название заявки и причину отказа.

Ссылка на объект MUST вести на заявку (тип объекта `request`). Инициатором MUST быть разработчик, принявший решение. Если разработчик и автор — один человек, уведомление MUST NOT создаваться. Повторная обработка того же события MUST NOT создавать второе уведомление.

#### Scenario: Заявка принята
- **WHEN** разработчик принимает заявку «Сверка актов» в навык «Сверка актов»
- **THEN** у автора появляется одно непрочитанное уведомление `request.accepted` со ссылкой на заявку, названием навыка и статусом «Запланировано»

#### Scenario: Заявка отклонена
- **WHEN** разработчик отклоняет заявку с причиной «Уже есть в поставке»
- **THEN** у автора появляется одно непрочитанное уведомление `request.rejected`, текст содержит причину

#### Scenario: Автор сам разработчик
- **WHEN** разработчик принимает или отклоняет собственную заявку
- **THEN** уведомление не создаётся

#### Scenario: Повторная обработка события
- **WHEN** событие решения по заявке обрабатывается повторно
- **THEN** у автора по-прежнему одно уведомление об этом решении

### Requirement: Уведомление авторов о смене статуса навыка
Система SHALL создавать уведомление типа `request.status-changed` каждому автору заявки, привязанной к навыку, когда статус навыка меняется. Заголовок и текст MUST содержать название заявки, название навыка и новый статус на русском языке. Ссылка на объект MUST вести на заявку конкретного автора (тип `request`). Если у навыка несколько привязанных заявок одного автора, он MUST получить по одному уведомлению на каждую заявку. Автор, совпадающий с разработчиком, сменившим статус, уведомления MUST NOT получать. Заявки, которые отклонены или не привязаны к навыку, уведомлений MUST NOT порождать. Повторная обработка того же события MUST NOT создавать дубликаты.

#### Scenario: Навык переведён в разработку
- **WHEN** разработчик переводит навык с двумя привязанными заявками разных авторов в `in_dev`
- **THEN** каждый автор получает одно уведомление `request.status-changed` со статусом «В разработке» и ссылкой на свою заявку

#### Scenario: Навык запущен
- **WHEN** навык переходит в `launched`
- **THEN** авторы привязанных заявок получают уведомление со статусом «Запущено»

#### Scenario: Смена статуса разработчиком-автором
- **WHEN** разработчик меняет статус навыка, к которому привязана его собственная заявка
- **THEN** ему уведомление по этой заявке не создаётся

#### Scenario: Навык без привязанных заявок
- **WHEN** меняется статус навыка, к которому не привязана ни одна заявка
- **THEN** уведомления не создаются

#### Scenario: Повторная обработка события
- **WHEN** событие смены статуса навыка обрабатывается повторно
- **THEN** у каждого автора по-прежнему одно уведомление об этой смене

### Requirement: Доставка уведомлений о заявках по каналам
Система SHALL доставлять уведомления типов `request.under-review`, `request.accepted`, `request.rejected` и `request.status-changed` по тем же каналам, что и остальные уведомления, включая Telegram привязанного пользователя, без отдельной настройки. Ошибка доставки MUST NOT влиять на взятие заявки в работу, решение по заявке и смену статуса навыка.

#### Scenario: Уведомление в Telegram
- **WHEN** автор привязал Telegram, а его заявка принята
- **THEN** сообщение о решении доставляется и в приложение, и в Telegram

#### Scenario: Взятие в работу в Telegram
- **WHEN** автор привязал Telegram, а его заявку взяли в работу
- **THEN** сообщение о взятии доставляется и в приложение, и в Telegram

#### Scenario: Доставка недоступна
- **WHEN** канал доставки временно недоступен
- **THEN** решение по заявке сохраняется, уведомление доступно в `GET /notifications`, а доставка повторяется

### Requirement: Уведомление автора о взятии заявки в работу
Система SHALL создавать автору заявки уведомление типа `request.under-review`, когда разработчик берёт его заявку в работу. Заголовок и текст MUST содержать название заявки и полное имя взявшего разработчика (для пользователя без ФИО — логин). Ссылка на объект MUST вести на заявку (тип объекта `request`). Инициатором MUST быть взявший разработчик. Если взявший и автор — один человек, уведомление MUST NOT создаваться. Повторная обработка того же события MUST NOT создавать второе уведомление.

#### Scenario: Заявка взята в работу
- **WHEN** разработчик «Петров Пётр» берёт в работу заявку «Сверка актов»
- **THEN** у автора появляется одно непрочитанное уведомление `request.under-review` со ссылкой на заявку, её названием и именем «Петров Пётр»

#### Scenario: Разработчик взял свою заявку
- **WHEN** разработчик берёт в работу собственную заявку
- **THEN** уведомление не создаётся

#### Scenario: Повторная обработка события
- **WHEN** событие взятия заявки в работу обрабатывается повторно
- **THEN** у автора по-прежнему одно уведомление о взятии

### Requirement: Уведомление о новом комментарии к заявке
Система SHALL создавать уведомления типа `request.comment-added` при добавлении комментария к заявке:
- если комментарий написал автор заявки — каждому активному пользователю с ролью `developer`, кроме самого автора комментария;
- если комментарий написал не автор заявки (разработчик) — автору заявки.

Состав разработчиков MUST определяться в момент обработки события, а не в момент добавления комментария. Неактивные (уволенные) пользователи MUST NOT получать уведомления. Если подходящих получателей нет, уведомления MUST NOT создаваться, и это MUST NOT считаться ошибкой обработки. Заголовок MUST содержать название заявки, текст — полное имя автора комментария (без ФИО — логин) и начало текста комментария. Ссылка на объект MUST вести на заявку (тип объекта `request`). Инициатором MUST быть автор комментария. Повторная обработка того же события MUST NOT создавать второе уведомление тому же получателю. Правка комментария MUST NOT создавать уведомлений.

#### Scenario: Автор пишет — разработчики узнают
- **WHEN** автор заявки «Сверка актов» пишет комментарий, а в системе два активных разработчика
- **THEN** каждый разработчик получает одно непрочитанное уведомление `request.comment-added` со ссылкой на заявку, именем автора и началом текста

#### Scenario: Разработчик отвечает — автор узнаёт
- **WHEN** разработчик пишет комментарий к заявке другого сотрудника
- **THEN** автор заявки получает одно уведомление `request.comment-added`, другие разработчики уведомлений не получают

#### Scenario: Разработчик пишет в свою заявку
- **WHEN** разработчик, который сам автор заявки, пишет к ней комментарий
- **THEN** уведомления получают остальные активные разработчики, а он сам — нет

#### Scenario: Единственный разработчик пишет в свою заявку
- **WHEN** единственный разработчик пишет комментарий к собственной заявке
- **THEN** уведомления не создаются, событие считается обработанным

#### Scenario: Уволенный разработчик
- **WHEN** автор пишет комментарий, а один из разработчиков деактивирован
- **THEN** деактивированный разработчик уведомление не получает

#### Scenario: Повторная обработка события
- **WHEN** событие о комментарии обрабатывается повторно
- **THEN** у каждого получателя по-прежнему одно уведомление об этом комментарии

### Requirement: Доставка уведомлений о комментариях по каналам
Система SHALL доставлять уведомления типа `request.comment-added` по тем же каналам, что и остальные уведомления, включая Telegram привязанного пользователя, без отдельной настройки. Ошибка доставки MUST NOT влиять на сохранение комментария.

#### Scenario: Ответ в Telegram
- **WHEN** у автора заявки привязан Telegram, а разработчик ответил в ленте
- **THEN** уведомление доступно в приложении и доставляется в Telegram

#### Scenario: Доставка недоступна
- **WHEN** канал доставки временно недоступен
- **THEN** комментарий сохранён, уведомление доступно в `GET /notifications`, а доставка повторяется

### Requirement: Уведомление разработчиков о новом баге
Система SHALL создавать уведомление типа `bug.reported` каждому активному пользователю с ролью `developer`, кроме автора бага, когда сотрудник сообщает о баге. Состав разработчиков MUST определяться в момент обработки события. Заголовок MUST содержать название бага, текст — полное имя автора (без ФИО — логин), продукт и агента. Ссылка на объект MUST вести на баг (тип объекта `bug`). Инициатором MUST быть автор бага. Если подходящих получателей нет, уведомления MUST NOT создаваться, и это MUST NOT считаться ошибкой. Повторная обработка того же события MUST NOT создавать второе уведомление тому же получателю.

#### Scenario: Новый баг
- **WHEN** сотрудник «Иванов Иван» сообщает о баге «Сводка не приходит» по агенту Ассистент продукта Telegram-бот, а в системе два активных разработчика
- **THEN** каждый разработчик получает одно непрочитанное уведомление `bug.reported` со ссылкой на баг, его названием, именем автора, продуктом и агентом

#### Scenario: Баг от разработчика
- **WHEN** разработчик сам сообщает о баге
- **THEN** уведомления получают остальные активные разработчики, а он — нет

#### Scenario: Уволенный разработчик
- **WHEN** сотрудник сообщает о баге, а один из разработчиков деактивирован
- **THEN** деактивированный разработчик уведомление не получает

### Requirement: Уведомление автора о смене статуса бага
Система SHALL создавать автору бага уведомление типа `bug.status-changed` при каждой смене статуса бага. Заголовок MUST содержать название бага, текст — новый статус на русском и полное имя разработчика (без ФИО — логин), а для `wont_fix` — ещё и причину. Ссылка на объект MUST вести на баг. Инициатором MUST быть разработчик. Если статус сменил сам автор бага, уведомление MUST NOT создаваться. Повторная обработка того же события MUST NOT создавать второе уведомление.

#### Scenario: Баг исправлен
- **WHEN** разработчик «Петров Пётр» переводит баг «Сводка не приходит» в `resolved`
- **THEN** автор получает одно уведомление `bug.status-changed` со статусом «Исправлен», именем «Петров Пётр» и ссылкой на баг

#### Scenario: Не будет исправлен
- **WHEN** разработчик закрывает баг как `wont_fix` с причиной
- **THEN** текст уведомления автора содержит причину

#### Scenario: Разработчик меняет статус своего бага
- **WHEN** разработчик, который сам автор бага, меняет его статус
- **THEN** уведомление не создаётся

### Requirement: Уведомление о новом комментарии к багу
Система SHALL создавать уведомления типа `bug.comment-added` при добавлении комментария к багу:
- если комментарий написал автор бага — каждому активному пользователю с ролью `developer`, кроме самого автора комментария;
- если комментарий написал не автор бага (разработчик) — автору бага.

Состав разработчиков MUST определяться в момент обработки события. Неактивные пользователи MUST NOT получать уведомления. Если подходящих получателей нет, уведомления MUST NOT создаваться, и это MUST NOT считаться ошибкой. Заголовок MUST содержать название бага, текст — полное имя автора комментария (без ФИО — логин) и начало текста комментария. Ссылка на объект MUST вести на баг. Инициатором MUST быть автор комментария. Повторная обработка того же события MUST NOT создавать второе уведомление тому же получателю. Правка комментария MUST NOT создавать уведомлений.

#### Scenario: Автор пишет — разработчики узнают
- **WHEN** автор бага пишет комментарий, а в системе два активных разработчика
- **THEN** каждый разработчик получает одно уведомление `bug.comment-added` со ссылкой на баг, именем автора и началом текста

#### Scenario: Разработчик отвечает — автор узнаёт
- **WHEN** разработчик пишет комментарий к багу другого сотрудника
- **THEN** автор бага получает одно уведомление `bug.comment-added`, другие разработчики — нет

#### Scenario: Единственный разработчик пишет в свой баг
- **WHEN** единственный разработчик пишет комментарий к собственному багу
- **THEN** уведомления не создаются, событие считается обработанным

### Requirement: Доставка уведомлений о багах по каналам
Система SHALL доставлять уведомления типов `bug.reported`, `bug.status-changed` и `bug.comment-added` по тем же каналам, что и остальные уведомления, включая Telegram привязанного пользователя, без отдельной настройки. Ошибка доставки MUST NOT влиять на подачу бага, смену статуса и сохранение комментария.

#### Scenario: Смена статуса в Telegram
- **WHEN** у автора бага привязан Telegram, а баг исправлен
- **THEN** уведомление доступно в приложении и доставляется в Telegram

#### Scenario: Доставка недоступна
- **WHEN** канал доставки временно недоступен
- **THEN** баг сохранён, уведомление доступно в `GET /notifications`, а доставка повторяется
