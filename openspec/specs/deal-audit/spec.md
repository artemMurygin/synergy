# deal-audit Specification

## Purpose

Проверяет полноту обязательных полей сделки с помощью AI-агента и сохраняет результат аудита.

## Requirements

### Requirement: Получение полной сделки
При обработке задачи аудита система SHALL получить из CRM полную карточку сделки по id из задачи.

#### Scenario: Сделка найдена
- **WHEN** обрабатывается задача с id существующей сделки
- **THEN** карточка загружена и передана на проверку

#### Scenario: Сделка удалена
- **WHEN** сделки с таким id в CRM нет
- **THEN** аудит помечается как пропущенный с причиной «сделка не найдена», задача не повторяется

### Requirement: Проверка обязательных полей
Система SHALL проверять через AI-агента заполненность и осмысленность обязательных полей: ФИО, телефон, образовательная программа, форма обучения, источник лида, этап воронки. Агент MUST вернуть структурированный результат: общий вердикт и список проблемных полей с пояснением.

#### Scenario: Все поля заполнены
- **WHEN** в сделке заполнены все обязательные поля
- **THEN** вердикт «в порядке», список проблем пуст, уведомление не отправляется

#### Scenario: Есть пустые поля
- **WHEN** в сделке не заполнены телефон и форма обучения
- **THEN** вердикт «есть нарушения», в списке оба поля с пояснением

#### Scenario: Поле заполнено бессмысленно
- **WHEN** поле «телефон» содержит текст, не похожий на номер
- **THEN** поле попадает в список проблем с пояснением

### Requirement: Уведомление как инструмент агента
Система SHALL предоставлять агенту инструмент уведомления, принимающий Telegram username ответственного и текст сообщения. Инструмент MUST добавлять задание в очередь уведомлений и не отправлять сообщение сам. Система SHALL также предоставлять агенту инструмент `getUserTelegramAccountById` (см. `employee-notification`), с помощью которого агент получает username по `responsibleId` из сделки. Порядок вызовов: сначала поиск username, затем уведомление.

#### Scenario: Агент вызывает инструмент при нарушениях
- **WHEN** агент нашёл проблемы в сделке
- **THEN** агент получает username через `getUserTelegramAccountById`, вызывает инструмент уведомления с username и текстом, и в очередь добавлено задание

#### Scenario: Username не найден
- **WHEN** `getUserTelegramAccountById` вернул «не найден»
- **THEN** агент не вызывает инструмент уведомления

#### Scenario: Нарушений нет
- **WHEN** агент не нашёл проблем
- **THEN** инструмент не вызывается

#### Scenario: Некорректный ответ агента
- **WHEN** ответ агента не соответствует ожидаемой структуре
- **THEN** попытка считается неудачной и повторяется по политике ретраев очереди

### Requirement: Сохранение результата аудита
Система SHALL сохранять в Postgres результат каждого аудита: id сделки, версия сделки, вердикт, список проблем, время проверки.

#### Scenario: Результат сохранён
- **WHEN** аудит сделки завершён
- **THEN** в Postgres есть запись с вердиктом и найденными проблемами

### Requirement: Повторы обработки
При временных сбоях (CRM, LLM, БД) система SHALL повторять обработку задачи с нарастающей задержкой до лимита. Для версии сделки, по которой аудит уже сохранён, повторная обработка MUST NOT выполнять проверку заново.

#### Scenario: Сбой LLM
- **WHEN** вызов LLM завершился ошибкой
- **THEN** задача повторяется по политике ретраев

#### Scenario: Версия уже проверена
- **WHEN** для версии сделки результат аудита уже сохранён
- **THEN** проверка не выполняется, уведомление не создаётся повторно
