# auth-session Specification

## Purpose

Клиентская часть авторизации в расширении manager-helper: вход, хранение и автоматическое обновление токенов, восстановление сессии, обязательная смена временного пароля и выход.

## Requirements

### Requirement: Экран входа
Расширение SHALL показывать экран входа с полями логина и пароля, если нет действующей сессии. Остальной интерфейс панели MUST быть недоступен до входа.

#### Scenario: Первое открытие панели
- **WHEN** пользователь открывает боковую панель без сохранённой сессии
- **THEN** показывается экран входа, а чаты и поиск недоступны

#### Scenario: Ошибка входа
- **WHEN** пользователь вводит неверные данные
- **THEN** расширение показывает сообщение об ошибке и остаётся на экране входа

#### Scenario: Превышен лимит попыток
- **WHEN** сервер отвечает 429
- **THEN** расширение показывает, через сколько можно повторить попытку, и блокирует отправку формы на это время

### Requirement: Хранение токенов
Расширение SHALL хранить access-токен только в памяти контекста расширения и MUST не записывать его в постоянное хранилище. Refresh-токен MUST находиться только в `httpOnly` cookie, управляемой браузером, и MUST быть недоступен JavaScript расширения. Запросы к эндпоинтам `login`, `refresh`, `logout` и `change-password` MUST отправляться с передачей cookie. Content-скрипты MUST не иметь доступа к access-токену.

#### Scenario: Закрытие панели
- **WHEN** панель закрывается и открывается снова
- **THEN** access-токена в памяти нет, и расширение получает новый, обновив сессию по cookie

#### Scenario: Доступ из content-скрипта
- **WHEN** content-скрипт на странице пытается получить токен
- **THEN** расширение не отдаёт ему access-токен, а refresh-токен ему недоступен

### Requirement: Авторизация запросов к бэкенду
Расширение SHALL добавлять заголовок `Authorization: Bearer <access>` ко всем запросам к защищённым эндпоинтам бэкенда, включая запросы из панели, страницы настроек и фонового скрипта.

#### Scenario: Запрос с токеном
- **WHEN** панель запрашивает список чатов, пока сессия действует
- **THEN** запрос уходит с заголовком `Authorization: Bearer <access>`

### Requirement: Автоматическое обновление токена
Расширение SHALL при ответе 401 «токен истёк» один раз обновить сессию и повторить исходный запрос. Параллельные запросы, получившие 401, MUST дожидаться одного общего обновления. Обновления из разных контекстов расширения (панель, настройки, фон) MUST выполняться строго последовательно, чтобы одна и та же cookie не предъявлялась серверу параллельно.

#### Scenario: Обновление при 401
- **WHEN** запрос получает 401 «токен истёк», а сессия действительна
- **THEN** расширение обновляет токены и повторяет запрос, пользователь не видит ошибки

#### Scenario: Несколько запросов одновременно
- **WHEN** три запроса одновременно получают 401 «токен истёк»
- **THEN** выполняется ровно один запрос обновления, и все три запроса повторяются с новым токеном

#### Scenario: Два контекста одновременно
- **WHEN** панель и фоновый скрипт одновременно обнаруживают истёкший токен
- **THEN** обновления выполняются одно за другим, и каждый контекст получает собственный действительный access-токен

#### Scenario: Обновление невозможно
- **WHEN** сервер отвечает 401 на обновление
- **THEN** расширение очищает access-токен из памяти и показывает экран входа

### Requirement: Восстановление сессии
Расширение SHALL при открытии панели пытаться восстановить сессию по cookie без ввода пароля и показывать экран входа только если сервер ответил 401. Если сервер недоступен, расширение MUST не показывать экран входа.

#### Scenario: Успешное восстановление
- **WHEN** пользователь открывает панель, а cookie с refresh-токеном действительна
- **THEN** панель открывается в рабочем состоянии без экрана входа

#### Scenario: Сервер недоступен
- **WHEN** при восстановлении сессии нет связи с сервером
- **THEN** расширение показывает ошибку подключения с возможностью повторить, не показывая экран входа

### Requirement: Обязательная смена временного пароля
Расширение SHALL после входа с `mustChangePassword = true`, а также при ответе 403 `PASSWORD_CHANGE_REQUIRED`, показывать окно смены пароля, которое нельзя закрыть без смены или выхода. В окне пользователь вводит текущий пароль, новый пароль и его подтверждение. Расширение MUST проверять совпадение подтверждения и отличие нового пароля от текущего до отправки.

#### Scenario: Первый вход
- **WHEN** пользователь входит с временным паролем
- **THEN** сразу открывается окно смены пароля, остальной интерфейс недоступен

#### Scenario: Успешная смена
- **WHEN** пользователь вводит верный текущий и допустимый новый пароль
- **THEN** окно закрывается, расширение сохраняет новую пару токенов и открывает рабочий интерфейс

#### Scenario: Подтверждение не совпадает
- **WHEN** новый пароль и подтверждение различаются
- **THEN** расширение показывает ошибку и не отправляет запрос

#### Scenario: Новый пароль равен текущему
- **WHEN** пользователь вводит новый пароль, равный временному
- **THEN** расширение показывает ошибку и не отправляет запрос

#### Scenario: Отказ от смены
- **WHEN** пользователь нажимает «Выйти» в окне смены пароля
- **THEN** сессия завершается, и показывается экран входа

### Requirement: Выход
Расширение SHALL предоставлять действие выхода, которое отзывает сессию на сервере (сервер удаляет cookie) и очищает access-токен из памяти. Если сервер недоступен, access-токен из памяти MUST всё равно быть очищен, а пользователю показано, что сессия на сервере могла остаться активной.

#### Scenario: Выход при доступном сервере
- **WHEN** пользователь нажимает «Выйти»
- **THEN** сервер отзывает сессию и удаляет cookie, расширение очищает токен и показывает экран входа

#### Scenario: Выход без связи
- **WHEN** пользователь нажимает «Выйти», а сервер недоступен
- **THEN** расширение всё равно очищает токен из памяти и показывает экран входа с предупреждением

### Requirement: Единый выход во всех контекстах
Расширение SHALL при завершении сессии (выход или неудачное обновление) в любом контексте уведомлять остальные открытые контексты расширения и переводить их на экран входа.

#### Scenario: Выход в одном контексте
- **WHEN** пользователь выходит в панели, пока открыта страница настроек
- **THEN** страница настроек больше не выполняет авторизованных запросов и показывает требование войти
