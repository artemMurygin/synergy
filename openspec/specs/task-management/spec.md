# task-management Specification

## Purpose

Управление задачами через REST API бэкенда: создание, просмотр, фильтрация, изменение и удаление задач с ответственным, наблюдателями, статусом и дедлайном.

## Requirements

### Requirement: Поля задачи
Система SHALL хранить для каждой задачи: идентификатор, название, описание, статус, дедлайн, создателя, ответственного, список наблюдателей, время создания, время последнего изменения и время закрытия. Название MUST быть строкой длиной от 1 до 200 символов после обрезки пробелов. Описание MUST быть необязательным и не длиннее 10000 символов. Дедлайн MUST быть необязательным моментом времени в формате ISO 8601 с часовым поясом. Ответственный MUST быть необязательным и единственным. Наблюдателей MUST быть не более 50, повторы MUST игнорироваться.

#### Scenario: Задача с минимальным набором полей
- **WHEN** клиент создаёт задачу, указав только название
- **THEN** система создаёт задачу со статусом `todo`, пустым описанием, без дедлайна, без ответственного и без наблюдателей, а создателем становится текущий пользователь

#### Scenario: Пустое или слишком длинное название
- **WHEN** клиент создаёт или изменяет задачу, указав пустое название или название длиннее 200 символов
- **THEN** система отвечает 400 и не меняет данные

#### Scenario: Повторы среди наблюдателей
- **WHEN** клиент передаёт один и тот же идентификатор наблюдателя несколько раз
- **THEN** система сохраняет его один раз

### Requirement: Создание задачи
Система SHALL создавать задачу по запросу `POST /tasks` и возвращать созданную задачу. Создателем MUST становиться пользователь из access-токена; значение, переданное в теле запроса, MUST игнорироваться. Ответственный и наблюдатели MUST ссылаться на существующих активных пользователей.

#### Scenario: Успешное создание с участниками
- **WHEN** клиент создаёт задачу с названием, описанием, дедлайном, ответственным и тремя наблюдателями
- **THEN** система отвечает 201 и возвращает задачу со всеми переданными полями, статусом `todo` и создателем из токена

#### Scenario: Несуществующий или отключённый пользователь
- **WHEN** клиент указывает ответственного или наблюдателя, которого нет среди активных пользователей
- **THEN** система отвечает 422 с кодом, указывающим на неизвестного пользователя, и не создаёт задачу

#### Scenario: Попытка задать создателя
- **WHEN** клиент передаёт в теле запроса поле создателя, отличное от текущего пользователя
- **THEN** система сохраняет создателем текущего пользователя

### Requirement: Получение задачи
Система SHALL возвращать задачу по `GET /tasks/{id}` вместе с ответственным, наблюдателями и метаданными вложений. Пользователи в ответе MUST содержать идентификатор и логин.

#### Scenario: Существующая задача
- **WHEN** авторизованный клиент запрашивает существующую задачу
- **THEN** система отвечает 200 и возвращает все поля задачи, список наблюдателей и список вложений без содержимого файлов

#### Scenario: Несуществующая или удалённая задача
- **WHEN** клиент запрашивает идентификатор, которого нет, или задачу, помеченную удалённой
- **THEN** система отвечает 404

### Requirement: Список задач с фильтрами
Система SHALL возвращать страницу задач по `GET /tasks` с пагинацией (`limit`, `page`, как в остальных списках API) и общим числом записей. Система MUST поддерживать фильтры по статусу, создателю, ответственному, наблюдателю, признаку просрочки и подстроке в названии, а также сортировку по дедлайну, времени создания и времени изменения. Фильтры MUST комбинироваться по «И». Просроченной считается задача с дедлайном в прошлом и статусом не `done`. По умолчанию система MUST сортировать задачи по времени создания, новые первыми. Удалённые задачи MUST не попадать в список.

#### Scenario: Задачи, где я ответственный
- **WHEN** клиент запрашивает список с фильтром по ответственному, равным идентификатору текущего пользователя
- **THEN** система возвращает только задачи с этим ответственным

#### Scenario: Просроченные задачи
- **WHEN** клиент запрашивает список с фильтром `overdue=true`
- **THEN** система возвращает только задачи с дедлайном в прошлом и статусом `todo` или `in_progress`

#### Scenario: Пагинация
- **WHEN** клиент запрашивает страницу с `limit=10`
- **THEN** система возвращает не более 10 задач и общее число задач, подходящих под фильтры

#### Scenario: Недопустимое значение фильтра
- **WHEN** клиент передаёт неизвестный статус или `limit` больше максимального
- **THEN** система отвечает 400

### Requirement: Изменение задачи
Система SHALL частично изменять задачу по `PATCH /tasks/{id}`: изменяются только переданные поля. Создатель MUST не меняться. Поле `watcherIds`, если передано, MUST заменять список наблюдателей целиком. Передача `null` для дедлайна или ответственного MUST снимать значение. Время последнего изменения MUST обновляться при каждом изменении.

#### Scenario: Смена ответственного
- **WHEN** клиент передаёт новый `assigneeId`
- **THEN** система обновляет ответственного, не затрагивая остальные поля

#### Scenario: Снятие дедлайна
- **WHEN** клиент передаёт `deadline: null`
- **THEN** система сохраняет задачу без дедлайна

#### Scenario: Замена наблюдателей
- **WHEN** клиент передаёт `watcherIds` с новым списком
- **THEN** система сохраняет ровно этот список, остальные наблюдатели удаляются

#### Scenario: Пустое изменение
- **WHEN** клиент отправляет PATCH без полей
- **THEN** система отвечает 400

### Requirement: Статусы задачи
Система SHALL поддерживать статусы `todo`, `in_progress` и `done` и MUST разрешать переход между любыми двумя статусами. При переходе в `done` система MUST записывать время закрытия; при выходе из `done` MUST сбрасывать его. Повторная установка того же статуса MUST не менять время закрытия.

#### Scenario: Закрытие задачи
- **WHEN** клиент меняет статус задачи с `in_progress` на `done`
- **THEN** система сохраняет статус и время закрытия, равное моменту изменения

#### Scenario: Повторное открытие
- **WHEN** клиент меняет статус закрытой задачи на `in_progress`
- **THEN** система сбрасывает время закрытия

#### Scenario: Тот же статус
- **WHEN** клиент повторно устанавливает `done` у уже закрытой задачи
- **THEN** время закрытия остаётся прежним

### Requirement: Удаление задачи
Система SHALL удалять задачу по `DELETE /tasks/{id}` как мягкое удаление: задача помечается удалённой и перестаёт быть видимой через API, данные сохраняются в БД. Повторное удаление MUST быть отвечено 404.

#### Scenario: Успешное удаление
- **WHEN** клиент удаляет существующую задачу
- **THEN** система отвечает 204, а последующие запросы этой задачи отвечают 404 и она не входит в списки

#### Scenario: Повторное удаление
- **WHEN** клиент удаляет уже удалённую задачу
- **THEN** система отвечает 404

### Requirement: Доступ к задачам
Система SHALL требовать валидный access-токен для всех эндпоинтов задач. На текущем этапе любой аутентифицированный пользователь MUST иметь возможность читать, изменять и удалять любые задачи. Проверка прав MUST быть выделена так, чтобы ролевую модель можно было добавить без изменения контракта API.

#### Scenario: Запрос без токена
- **WHEN** клиент вызывает любой эндпоинт задач без access-токена
- **THEN** система отвечает 401

#### Scenario: Чужая задача
- **WHEN** аутентифицированный пользователь, не являющийся создателем, ответственным или наблюдателем, читает или изменяет задачу
- **THEN** система выполняет действие
