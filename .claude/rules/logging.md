# Логирование

## Как вызывать
- В классах внедряется `PinoLogger` из `nestjs-pino`, в конструкторе вызывается `setContext(ClassName.name)`.
- Сигнатура всегда `logger.<level>({ поля }, 'сообщение')`: объект первым, текст вторым.
- `console.*` и штатный `Logger` из `@nestjs/common` не используются.

## Сообщение
- Короткое, на английском, постоянное: `'Audit failed'`, а не ``` `Audit ${runId} failed` ```.
- Переменные данные передаются полями, а не вшиваются в текст.
- Без точки в конце и без эмодзи.

## Поля
- Имена в `camelCase`, едины по всему проекту: `runId`, а не `run_id` или `auditId`. Новое поле сначала сверяется с существующими.
- Идентификаторы называются по сущности: `runId`, `userId`, `jobId`.
- Единицы измерения указываются в имени: `durationMs`, `sizeBytes`.
- Ошибка передаётся только под ключом `err`: pino сериализует его в `type`, `message`, `stack`. Не `error`, не `exception`, не `err.message` строкой.
- Служебные поля `level`, `time`, `pid`, `hostname`, `context`, `msg`, `req`, `res` не переопределяются.

## Уровни
| Уровень | Когда |
|---|---|
| `fatal` | приложение не может продолжать работу |
| `error` | операция не выполнена, нужна реакция |
| `warn` | подозрительно, но работа продолжается (ретрай, деградация) |
| `info` | ключевые события жизненного цикла: старт и завершение аудита, смена статуса |
| `debug` | детали для отладки, в проде выключены |
| `trace` | очень подробная диагностика |

Ошибку логирует тот слой, который её обрабатывает. Если исключение пробрасывается дальше (`throw err`), логируется один раз, чтобы не получать дубли на каждом уровне.

## requestId и correlationId
Оба идентификатора формирует `resolveRequestIds` (`src/shared/context/request-id.ts`) один раз на запрос.

| | `requestId` | `correlationId` |
|---|---|---|
| Что это | один HTTP-запрос к этому сервису | одна бизнес-операция целиком, может охватывать несколько запросов и сервисов |
| Откуда берётся | всегда новый `randomUUID()` на сервере; входящий заголовок игнорируется | заголовок `x-correlation-id`, иначе входящий `x-request-id`, иначе равен `requestId` |
| Заголовок ответа | `x-request-id` | `x-correlation-id` |

- Входящие значения принимаются только если непустые и не длиннее 128 символов.
- Контекст запроса (`AsyncLocalStorage`) заполняет `RequestContextMiddleware`. Читать его можно через `RequestContext.getIds()`, `getRequestId()` и `getCorrelationId()`. Вне запроса, например в воркере очереди, `getIds()` возвращает `undefined`, а остальные методы `'unknown'`.
- В логгере настроен `mixin` (`src/shared/logger/app-logger.module.ts`): каждая запись, написанная в рамках запроса, автоматически получает поля `requestId` и `correlationId`. Это относится и к `request completed` от `pino-http`, и к логам из кода. Передавать эти поля вручную не нужно и не следует, иначе ключи задвоятся.
- Вне запроса (фоновые задачи без родительского запроса) идентификаторов в логах нет: `mixin` ничего не добавляет.
- Задачи BullMQ переносят контекст запроса автоматически: при постановке `BullmqAuditQueue.enqueue` кладёт `RequestContext.getIds()` в поле `requestIds` payload (`AuditJobData`), а `AuditProcessor.process` восстанавливает контекст через `RequestContext.run`. Поэтому логи воркера содержат те же `requestId` и `correlationId`, что и запрос, поставивший задачу, и `BaseError` в воркере получает верный `correlationId`. Новые очереди и процессоры делаются по тому же образцу, поля вручную не добавляются.
- Для поиска сквозной операции используется `correlationId`, для разбора одного обращения — `requestId`.

## Что нельзя логировать
- Секреты и персональные данные: токены, пароли, `OPENAI_API_KEY`, `authorization`, `cookie`.
- Тела запросов и ответов целиком, особенно промпты и результаты LLM: достаточно размера и идентификатора.
- Маскирование настроено через `redact` в `src/shared/logger/app-logger.module.ts`: `req.headers.authorization`, `req.headers.cookie`, `res.headers["set-cookie"]`, `*.password`, `*.apiKey`. Маска `*.password` ловит один уровень вложенности. Новые чувствительные поля добавляются в `paths`.

## Формат и доставка
- Формат один: JSON, одна запись на строку. `pino-pretty` используется только в dev.
- Поиск в Loki: лейбл `app`, далее `| json | context="..." | correlationId="..."`.
- Путь доставки в Loki должен быть один: сейчас активны и `pino-loki`, и `promtail`, записи могут дублироваться.
