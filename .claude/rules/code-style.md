# NestJS: код-стайл

## Именование
- Файлы: `kebab-case` с суффиксом роли: `create-user.dto.ts`, `jwt-auth.guard.ts`, `orders.service.ts`.
- Классы: `PascalCase` (`OrdersService`), интерфейсы без префикса `I`, enum — `PascalCase`, значения — `UPPER_SNAKE_CASE`.
- Переменные и методы: `camelCase`. Константы уровня модуля: `UPPER_SNAKE_CASE`.
- Булевы переменные начинаются с `is`/`has`/`can`/`should`.
- Методы сервисов называем глаголами: `findById`, `create`, `markAsPaid`.

## Именование переменных
- Имя отражает смысл, а не тип: `activeOrders`, а не `arr` или `data`. Запрещены безликие имена: `data`, `res`, `tmp`, `obj`, `item`, `val`, `foo`, `x` (кроме общепринятых `i`/`j` в коротких циклах и `e` в коротких колбэках).
- Только английский язык, без транслита (`orders`, а не `zakazy`). Доменные термины используются единообразно по всему проекту (например, всегда `counterparty`, не вперемешку с `contractor`/`partner`).
- Без сокращений, кроме общеизвестных (`id`, `url`, `dto`, `req`, `res` в контексте HTTP, `ctx`). Не `usr`, `cnt`, `mgr` — а `user`, `count`, `manager`.
- Не кодировать тип в имени: без венгерской нотации и суффиксов (`userObj`, `nameStr`, `itemsArray`).
- Булевы: префиксы `is`, `has`, `can`, `should`, `needs` (`isActive`, `hasAccess`). Без отрицаний в имени: `isEnabled`, а не `isNotDisabled`.
- Коллекции — во множественном числе (`users`), одиночные значения — в единственном (`user`). Для Map/Record: `userById`, `ordersByStatus`.
- Числа с единицами измерения — единицу указывать в имени: `timeoutMs`, `ttlSeconds`, `sizeBytes`, `priceKopecks`.
- Даты и время: `createdAt`, `updatedAt`, `expiresAt`, `startDate` — суффикс `At` для момента времени, `Date` для календарной даты.
- Константы: `UPPER_SNAKE_CASE` для значений уровня модуля (`DEFAULT_PAGE_SIZE`, `MAX_RETRY_ATTEMPTS`). Магические числа и строки выносятся в именованные константы.
- Функции и методы — глаголы (`calculateTotal`, `sendNotification`), обработчики событий — `handle<Event>` / `on<Event>`, геттеры-проверки — по правилам булевых.
- Приватные поля класса — без префикса `_`, область видимости задаётся модификатором `private`.
- Длина имени пропорциональна области видимости: в узком блоке допустимо короткое имя, у полей класса и экспортируемых значений — полное и описательное.
- Generic-параметры: `T` для единственного, иначе осмысленные `TEntity`, `TDto`, `TResult`.
- Имена переменных не затеняют (shadowing) внешние и не совпадают с глобалами (`name`, `status`, `event` в глобальном контексте).

## TypeScript
- `strict: true`.
- **Использование `any` запрещено** — ни явное (`: any`, `as any`, `<any>`, `any[]`, `Promise<any>`, `Record<string, any>`), ни неявное (параметры без типа, `noImplicitAny` включён).
  - Неизвестный тип → `unknown` + сужение (type guard, `instanceof`, валидация через zod/class-validator).
  - Нужна гибкость → generics (`<T>`), union-типы, `Record<string, unknown>`.
  - Данные от внешних API, БД и очередей описывать интерфейсами/DTO и валидировать на границе системы.
  - Для `catch` использовать `catch (error: unknown)` и сужать тип перед использованием.
  - Не обходить запрет через `// eslint-disable`, `@ts-ignore`, `@ts-expect-error` и двойное приведение `as unknown as T`. Если без этого никак — отдельный комментарий с обоснованием и согласование в code review.
  - В ESLint включены правила `@typescript-eslint/no-explicit-any: error`, `no-unsafe-assignment`, `no-unsafe-member-access`, `no-unsafe-call`, `no-unsafe-return`, `no-unsafe-argument`.
- **Использование `as` (приведение типов) запрещено** — ни `value as Type`, ни `<Type>value`, ни `as unknown as T`, ни non-null assertion `!`.
  - Сужение типа — через type guard (`typeof`, `instanceof`, `in`, пользовательские предикаты `value is T`), discriminated union и проверки на `null`/`undefined`.
  - Данные из внешних источников (HTTP, БД, очереди, Redis, `JSON.parse`) валидировать на границе (class-validator, zod) и получать уже типизированный результат, а не приводить тип.
  - Корректировать типы нужно в источнике: правильные generics (`repository.findOne<T>`, `Promise<T>`), точные сигнатуры, `satisfies` для проверки соответствия без приведения.
  - Допустимые исключения: `as const` и переименование в импортах (`import { a as b }`). Остальные случаи — только с комментарием-обоснованием и согласованием в code review.
  - В ESLint включены правила `@typescript-eslint/consistent-type-assertions` (`assertionStyle: 'never'`) и `@typescript-eslint/no-non-null-assertion`.
- Явные типы возвращаемых значений у публичных методов сервисов и контроллеров.
- `readonly` для зависимостей и неизменяемых полей.
- `import type` для типов; не использовать `enum` там, где достаточно union-типа литералов.
- Предпочитать `const`, не использовать `var`. Не мутировать аргументы функций.
- Не использовать non-null assertion (`!`) без комментария-обоснования.

## Контроллеры
- Контроллер тонкий: только маршрутизация, валидация входа и вызов сервиса. Бизнес-логики и работы с БД в нём нет.
- Все входные данные описываются DTO с `class-validator` / `class-transformer`; глобальный `ValidationPipe` с `whitelist: true`, `forbidNonWhitelisted: true`, `transform: true`.
- Ответы возвращаются через response-DTO, а не сырые entity (не светить внутренние поля).
- Документировать эндпоинты через `@nestjs/swagger` (`@ApiTags`, `@ApiOperation`, `@ApiResponse`).
- HTTP-коды задаются явно (`@HttpCode`), где отличаются от дефолтных.

## Ошибки
- Бросать Nest-исключения (`NotFoundException`, `BadRequestException`, `ConflictException` …) или собственные доменные исключения, унаследованные от `HttpException`.
- Не глотать ошибки: пустой `catch` запрещён. Либо обработать, либо пробросить с контекстом.
- Единый глобальный `ExceptionFilter` формирует формат ответа об ошибке.
- Сообщения об ошибках для клиента не содержат внутренних деталей (стек, SQL).

## База данных (PostgreSQL)
- Изменения схемы — только через миграции, никакого `synchronize: true` вне локальной разработки.
- Операции, затрагивающие несколько таблиц, выполняются в транзакции.
- Исключать N+1: явные `join`/`relations`, выборка только нужных полей.
- Для списков — пагинация обязательна. Индексы под частые фильтры и сортировки.

## Асинхронность, очереди, кэш
- Везде `async/await`; не смешивать с `.then()`. Не оставлять «висящие» промисы — либо `await`, либо явная обработка.
- Независимые операции — через `Promise.all`.
- Задачи BullMQ/RabbitMQ идемпотентны; у процессоров — retry/backoff и обработка failed-задач.
- Ключи Redis строятся по единой схеме `<service>:<entity>:<id>` и всегда с TTL, если это кэш.

## Конфигурация и секреты
- Конфиг только через `@nestjs/config` с валидацией (Joi/zod) при старте. `process.env` напрямую не использовать.
- Секреты не попадают в код и логи. Все переменные окружения описаны в `.env.example`.

## Логирование
- Использовать `Logger` из Nest с контекстом (`new Logger(OrdersService.name)`), не `console.log`.
- Уровни: `error` — сбои, `warn` — деградация, `log` — важные события, `debug` — отладка.
- Не логировать персональные данные, токены, пароли.

## Форматирование и линтинг
- Prettier + ESLint (`@typescript-eslint`), правила обязательны к прохождению перед коммитом (husky + lint-staged).
- Одинарные кавычки, точка с запятой, trailing comma, ширина строки 100–120.
- Порядок импортов: node/внешние пакеты → `@nestjs/*` → внутренние алиасы → относительные.
- Функции короткие и делают одно дело; ранний `return` вместо глубокой вложенности.
- Комментарии объясняют «почему», а не «что». Мёртвый и закомментированный код удаляется.
