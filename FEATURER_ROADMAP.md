# Featurer — роадмап реализации

Внутренний веб-портал для всего, что связано с ИИ-агентами департамента: приём заявок, оценка, прозрачность статусов, каталог агентов, поддержка.

- Бэкенд — новый модуль в `backend/src/modules`. Переиспользуем `auth`, `notifications` (outbox → правила → уведомления), `telegram`.
- Фронт — `featurer/` на стеке control-center: React 19, Vite, TanStack Query/Table, zustand, Tailwind 4, дизайн-кит `design/synergy-design.pen`.
- Каждый этап — сквозной срез (бэкенд + веб) и отдельный OpenSpec change. После каждого этапа остаётся рабочий результат.

## Э0. Tracer bullet

Самый тонкий сквозной срез: один путь «идея → решение → запуск → автор узнал» через все слои. Код остаётся в проекте как каркас, следующие этапы его наращивают, а не переписывают.

```
 Сотрудник                 Портал / API                     Разработчик
 ─────────                 ────────────                     ───────────
 1 входит (своя учётка) ─▶ auth (cookie mh_refresh)
 2 подаёт идею ──────────▶ request: new, экономия ч/мес
 3 «Мои заявки»            «На рассмотрении»
                           очередь заявок ◀──────────────── 4 открывает
                           решение ◀────────────────────── 5 принять → навык
                                                              (выбрать или создать)
                                                              или отказать с причиной
                           skill: planned → in_dev → launched ◀ 6 двигает навык
 7 видит статус ◀───────── статус заявки = f(статус навыка)
   уведомление ◀────────── outbox → notification rule → in-app + Telegram
```

**Задействованные слои:** миграции, домен (заявка, навык, вывод статуса), события outbox, правило уведомлений, Telegram (уже есть), HTTP API, веб-портал (вход, форма, «Мои заявки», очередь, решение, статус навыка).

**Сознательные упрощения** (снимаются в Э1–Э7):

| Упрощение в Э0 | Где закрывается |
|---|---|
| Роль одна — `developer`, назначается через seed или SQL. Отделов и ФИО нет | Э1 |
| Продукты и агенты заводятся seed'ом. Навык создаётся прямо при решении по заявке | Э3: агент и продукт тоже создаются при решении по заявке. Ручного CRUD каталога нет |
| Анкета минимальная: название, описание, частота, минут за раз, сколько людей. Экономия в часах считается на фронте | остаётся как есть, не развивается |
| Решений два: принять с привязкой к навыку или отказать с причиной. Без оценки трудозатрат и без решений «новый агент / новый продукт» | Э3 |
| Комментариев нет. Причина отказа видна автору | Э4 |
| Уведомления в приложение и Telegram без глубоких ссылок на заявку в control-center и manager-helper | Э4 |
| Нет багов, инструкций, доступов | Э5, Э7 |
| Минимальный UI на токенах дизайн-кита, без полировки | по ходу |

**Критерий готовности:** на стенде сотрудник подаёт идею, разработчик принимает её в навык и доводит навык до `launched`, а автор на каждом шаге видит новый статус в портале и получает сообщение в Telegram.

Change: `add-featurer-tracer-bullet`

## Этапы

| # | Этап | Результат | Вопросы, которые надо решить к началу этапа | Change |
|---|---|---|---|---|
| 1 | **Фундамент** | Можно войти в портал своей учёткой. Админка в портале ведёт людей и доступы: заводит сотрудников (ФИО, отдел, должность, email), выдаёт и снимает роли `developer` и `admin`, увольняет и возвращает. Отделы справочные: плоский список, `head` лишь справочное поле и прав не даёт. Файл начальной загрузки (`AUTH_SEED_FILE`) — одноразовая загрузка в режиме «только новые», дальше источник правды админка. Сброса пароля нет: временный пароль виден один раз при создании. Каркас портала: вход, навигация, layout | Решено: свои таблицы, без синхронизации; роли — флаги `developer` и `admin` (`employee` — любой вошедший, `head` — справочное поле отдела); SameSite у `mh_refresh` не меняется (портал и API на одном домене), в `AUTH_ALLOWED_ORIGINS` добавляется origin портала | `add-featurer-foundation` (реализация и проверка завершены, ручной прогон на стенде 20.1 и ревью 21 впереди) |
| 2 | **Каталог** | Все видят продукты, агентов и их навыки. Разработчик ведёт навыки по статусам `planned → in_dev → testing → launched`. Роадмап — это вид на навыки. Истории статусов нет: хранится только текущий статус и время его смены. У агента своего статуса нет: он выводится из навыков (есть навык `launched` → «Работает», иначе «В разработке»). Разработчик всегда двигает только навык. Статус навыка `rework` («Доработка»): `testing → rework`, `launched → rework`, `rework → testing`. Архив: навык и агент архивируются и восстанавливаются; у агента это признак «в архиве», а не статус. Архивный агент скрывается вместе с навыками, восстановление не возвращает ранее архивированные навыки | Решено: агенту статус не нужен, `rework` и архив остаются | `add-featurer-catalog-roadmap` (артефакты есть, нужно убрать историю статусов и статус агента) |
| 3 | **Идеи** | Новая заявка попадает в статус `under_review`, когда разработчик берёт её в работу. Разработчик оценивает трудозатраты и выносит решение: принять в существующий или новый навык, принять с созданием нового агента (и при необходимости нового продукта) или отказать. Принятая заявка привязывается к навыку (N:1, как в Э0), её статус дальше выводится автоматически | Где хранится оценка и видит ли её автор. Когда заявка переходит в `under_review`: явным действием или при открытии. Как решения «новый агент / новый продукт» ложатся на каталог: недостающие продукт, агент и навык создаются одной транзакцией с принятием, `slug` генерируется из названия | — |
| 4 | **Диалог** | Лента публичных комментариев под заявкой: пишут автор и разработчик. Новый комментарий уведомляет вторую сторону в приложении и в Telegram, уведомление ведёт на заявку | Новая цель уведомления `request`. Кого уведомлять, если разработчиков несколько | `add-featurer-request-comments` |
| 5 | **Поддержка** | Баг привязан к продукту и агенту, у него свой жизненный цикл (`open → in_progress → resolved / won't fix`). Переписка работает так же, как в Э4 | Решено: отдельная сущность и своя лента комментариев, видят автор и разработчики | `add-featurer-bug-reports` (реализован, в архиве) |
| 7 | **Справка** | Инструкции к агентам (markdown). Доступы отделов к продуктам | Решено: одна инструкция на агента (пишет разработчик); доступ — только справочная пометка, задаёт администратор | `add-featurer-agent-guides` |
| 8 | **Эффект** *(после MVP)* | Дашборд сэкономленных часов и рублей, время до первой реакции и до запуска, активность по отделам | — | — |
| 9 | **Открытое API** *(после MVP)* | Подача заявок голосом и через чат-агентов в control-center и Telegram | — | — |

## Убрано из плана (решение 2026-11-15)

| Что | Почему / чем заменяется |
|---|---|
| Э6 «Дубликаты», склейка заявок и статус `duplicate` | Разработчик отклоняет заявку и указывает в причине ID уже реализованного навыка. Если навык ещё в работе, заявку можно принять в существующий навык |
| История статусов агентов и навыков | Хранится только текущий статус и `statusChangedAt` |
| Автоматический расчёт экономии в ₽, ставка часа (на департамент, на отдел или от оценщика) | Остаётся только расчёт часов на фронте из Э0, без развития |
| Связь заявок с навыками N:M | Остаётся N:1 из Э0 |
| Собственный статус агента, отдельное действие «запустить агента», запрет запускать навык при незапущенном агенте | Статус агента выводится из навыков, двигается только навык |
| Внутренние заметки в комментариях | Все комментарии публичные |
| Статус `needs_info` и цикл «нужны уточнения ↔ автор ответил» | Вопросы и ответы идут обычными комментариями Э4 |

## Почему такой порядок

- **Каталог идёт до идей.** Принятая заявка должна куда-то привязываться, иначе не будет авто-статуса, а это ключевой принцип продукта. Каталог небольшой, так что задержка выйдет короткой.
- **Э3 и Э4 разделены,** чтобы change оставались обозримыми. Портал есть смысл открывать сотрудникам после Э4: без переписки вопросы по заявкам уйдут в личные сообщения.
- **Э5 опирается на комментарии из Э4.**

## Модель статусов (уточняется в Э2–Э3)

```
  Заявка (идея)                                     Навык
  ─────────────                                     ─────
  new ──▶ under_review ──┬─▶ rejected  (с причиной;
                         │             дубликат → ID навыка в причине)
                         └─▶ accepted ──link──▶ ┌──────────┐
                                                │ planned  │
   статус заявки = f(статус навыка)             │ in_dev   │
   после accepted автор видит:                  │ testing  │
     «Запланировано / В разработке / Запущено»  │ launched │
                                                └──────────┘
```
