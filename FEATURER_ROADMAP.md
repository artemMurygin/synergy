# Featurer — роадмап реализации

Внутренний веб-портал для всего, что связано с ИИ-агентами департамента: приём заявок, оценка, прозрачность статусов, каталог агентов, поддержка.

- Бэкенд — новый модуль в `backend/src/modules`. Переиспользуем `auth`, `notifications` (outbox → правила → уведомления), `telegram`.
- Фронт — `featurer/` на стеке control-center: React 19, Vite, TanStack Query/Table, zustand, Tailwind 4, дизайн-кит `design/synergy-design.pen`.
- Каждый этап — сквозной срез (бэкенд + веб) и отдельный OpenSpec change. После каждого этапа остаётся рабочий результат.

## Э0. Tracer bullet

Самый тонкий сквозной срез: один путь «идея → решение → запуск → автор узнал» через все слои. Код остаётся в проекте как каркас, следующие этапы его наращивают, а не переписывают.

```
 Сотрудник                 Портал / API                     Разработчик
 ─────────                 ────────────                     ───────────
 1 входит (своя учётка) ─▶ auth (cookie mh_refresh)
 2 подаёт идею ──────────▶ request: new, экономия ч/мес и ₽
 3 «Мои заявки»            «На рассмотрении»
                           очередь заявок ◀──────────────── 4 открывает
                           решение ◀────────────────────── 5 принять → навык
                                                              (выбрать или создать)
                                                              или отказать с причиной
                           skill: planned → in_dev → launched ◀ 6 двигает навык
 7 видит статус ◀───────── статус заявки = f(статус навыка)
   уведомление ◀────────── outbox → notification rule → in-app + Telegram
```

**Задействованные слои:** миграции, домен (заявка, навык, вывод статуса), события outbox, правило уведомлений, Telegram (уже есть), HTTP API, веб-портал (вход, форма, «Мои заявки», очередь, решение, статус навыка).

**Сознательные упрощения** (снимаются в Э1–Э7):

| Упрощение в Э0 | Где закрывается |
|---|---|
| Роль одна — `developer`, назначается через seed или SQL. Отделов и ФИО нет | Э1 |
| Продукты и агенты заводятся seed'ом. Навык создаётся прямо при решении по заявке | Э2 |
| Анкета минимальная: название, описание, частота, минут за раз, сколько людей. Ставка часа берётся из env | Э3 |
| Решений два: принять с привязкой к навыку или отказать с причиной. Без «нужны уточнения» и без оценки трудозатрат | Э3, Э4 |
| Комментариев и внутренних заметок нет. Причина отказа видна автору | Э4 |
| Уведомления в приложение и Telegram без глубоких ссылок на заявку в control-center и manager-helper | Э4 |
| Нет багов, дубликатов, инструкций, доступов | Э5–Э7 |
| Минимальный UI на токенах дизайн-кита, без полировки | по ходу |

**Критерий готовности:** на стенде сотрудник подаёт идею, разработчик принимает её в навык и доводит навык до `launched`, а автор на каждом шаге видит новый статус в портале и получает сообщение в Telegram.

Change: `add-featurer-tracer-bullet`

## Этапы

| # | Этап | Результат | Вопросы, которые надо решить к началу этапа | Change |
|---|---|---|---|---|
| 1 | **Фундамент** | Можно войти в портал своей учёткой. Админка в портале ведёт людей и доступы: заводит сотрудников (ФИО, отдел, должность, email), выдаёт и снимает роли `developer` и `admin`, увольняет и возвращает. Отделы справочные: плоский список, `head` лишь справочное поле и прав не даёт. Файл начальной загрузки (`AUTH_SEED_FILE`) — одноразовая загрузка в режиме «только новые», дальше источник правды админка. Сброса пароля нет: временный пароль виден один раз при создании. Каркас портала: вход, навигация, layout | Решено: свои таблицы, без синхронизации; роли — флаги `developer` и `admin` (`employee` — любой вошедший, `head` — справочное поле отдела); SameSite у `mh_refresh` не меняется (портал и API на одном домене), в `AUTH_ALLOWED_ORIGINS` добавляется origin портала | `add-featurer-foundation` (реализация и проверка завершены, ручной прогон на стенде 20.1 и ревью 21 впереди) |
| 2 | **Каталог** | Все видят продукты, агентов и их навыки. Разработчик ведёт навыки по статусам `planned → in_dev → testing → launched`. Роадмап — это вид на навыки | Набор статусов навыка. Нужен ли агенту статус | — |
| 3 | **Идеи** | Сотрудник подаёт идею за 2 минуты, экономия (часы/мес и ₽) считается сама. Разработчик оценивает и выносит решение. Принятая заявка привязывается к навыку, и её статус дальше выводится автоматически. Экран «мои заявки» | Связь заявок с навыком N:1 или N:M. Ставка часа: одна на департамент, своя для каждого отдела или вводит оценщик. Как решения «новый агент / новый продукт» ложатся на каталог | — |
| 4 | **Диалог** | Лента комментариев с внутренними заметками. Цикл «нужны уточнения ↔ автор ответил». Уведомления о смене статуса и ответах приходят в приложение и в Telegram | Новая цель уведомления `request`. Какие события уведомляют кого | — |
| 5 | **Поддержка** | Баг привязан к продукту и агенту, у него свой жизненный цикл (`open → in_progress → resolved / won't fix`). Переписка работает так же, как в Э4 | Общая сущность `request` с полем `kind` или отдельная | — |
| 6 | **Дубликаты** | Склейка дубликатов: разработчик объединяет похожие заявки, авторы видят, что их идея учтена в другой заявке | Что видит автор склеенной заявки. Можно ли расклеить | — |

## Почему такой порядок

- **Каталог идёт до идей.** Принятая заявка должна куда-то привязываться, иначе не будет авто-статуса, а это ключевой принцип продукта. Каталог небольшой, так что задержка выйдет короткой.
- **Э3 и Э4 разделены,** чтобы change оставались обозримыми. Но портал есть смысл открывать сотрудникам только после Э4: без ответов и уведомлений повторится «предложил и не знаю, что стало».
- **Э5 и Э6 не зависят друг от друга.** Их можно делать в любом порядке. Э5 опирается на комментарии из Э4.

## Модель статусов (черновик, уточняется в Э2–Э3)

```
  Заявка (идея)                                     Навык
  ─────────────                                     ─────
  new ──▶ under_review ──┬─▶ needs_info ──▶ (автор ответил) ─▶ under_review
                         ├─▶ rejected  (с причиной)
                         ├─▶ duplicate
                         └─▶ accepted ──link──▶ ┌──────────┐
                                                │ planned  │
   статус заявки = f(статус навыка)             │ in_dev   │
   после accepted автор видит:                  │ testing  │
     «Запланировано / В разработке / Запущено»  │ launched │
                                                └──────────┘
```

## Текущее состояние кода (на 2026-11-15)

- Э0 (`add-featurer-tracer-bullet`) в архиве, спеки синхронизированы.
- Э1 (`add-featurer-foundation`) реализован в рабочей ветке, не закоммичен: таблицы `auth_departments` и профили сотрудников (миграции 031-033), роль `admin`, admin-API (`/admin/employees`, `/admin/departments`), расширенный `GET /auth/me` (ФИО, должность, отдел), начальная загрузка из файла (`AUTH_SEED_FILE`, «только новые»), админка в портале, имя автора в очереди заявок. Полная регрессия (20.4) и ручной прогон на стенде (20.1) ещё не выполнены.
- Вход через cookie `mh_refresh` (`SameSite=Strict`) и `OriginGuard` общие с manager-helper; origin портала добавляется в `AUTH_ALLOWED_ORIGINS` при выкате.
- Отзыв роли действует не позднее `AUTH_ACCESS_TTL`: роль берётся из access-токена.
- Известное расхождение: `id` отделов из файла загрузки текстовые, а admin-API принимает для отделов только UUID.
- Цели уведомлений: `task` и `chat`. Для Э4 нужна `request`.
